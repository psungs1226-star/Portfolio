# V3 — 두 웹 레퍼런스와 GSAP 제작 방향

작성: 2026-09-15. 사용자가 지정한 [Mark Progano](https://mprogano.com/)와 [Kelly Tokas Framer 템플릿](https://www.framer.com/marketplace/templates/kelly-tokas/)의 실제 화면·구조를 확인했다. Kelly 템플릿의 실제 [미리보기](https://kellytokas.framer.ai/)도 확인했다. 이 문서는 `REVISION-V2.md`의 시각 방향보다 우선한다. `BUILD-BRIEF.md`의 사실·자료 경로·기술 안정성·검수 항목은 유지한다.

## 핵심 판정

- Mark Progano의 첫 화면은 한 문장의 일부를 세리프, 다른 일부를 굵은 산세리프로 다르게 대우해 생각의 중심을 글자 자체에서 만든다. 그의 작업 섹션은 과장된 대형 카드보다 제목을 먼저 보고 관심 있는 항목을 펼치는 방식이다.
- Kelly Tokas는 첫 화면에 긴 정보나 지표를 넣지 않는다. 넓은 공백 뒤에 실제 작업 이미지를 큰 면으로 연결하고, 상세 케이스로 이어진다.
- 우리 페이지에는 **소개 문장 한 개 + 그룹바이의 독립적인 웹용 프로젝트 표지 한 개**로 첫 인상을 만들고, 스크롤로 필요할 때 사업 판단을 공개하는 것이 적합하다.
- 두 사이트의 실제 색·로고·표현·그리드·템플릿 파일을 복제하지 않는다. 사용자의 목적과 자료에 맞는 별도 디자인을 만든다. Kelly 템플릿은 Single-Use 라이선스 상품으로 소개되어 있으므로 구매 파일이나 구성 코드를 무단 사용하지 않는다.
- 이미지 프롬프트 작성 및 후속 5.6 작업에 `design-agent`를 적용하지 않는다. 이 문서의 두 시안은 사용자 지시를 기준으로 직접 구성했다.

## 이미지 시안

- `reference-v3-A-type.png`: 세리프 소개 첫 문장 + 굵은 고딕 둘째 문장, 차가운 백색 배경, 짙은 녹색 포트폴리오 표지, 프로젝트가 오른쪽 큰 면으로 들어온다.
- `reference-v3-B-case.png`: 백색과 넓은 여백, 고딕 소개, 토마토색 포트폴리오 표지, 실제 문서 근거를 작은 보조 면에 둔다.

**시안 텍스트의 예외:** 생성 결과에 문서 내용·다음 작업 제목·영문 보조 표기가 임의로 들어갈 수 있다. HTML 구현의 정확한 문구는 아래 카피와 원본 자료를 사용한다. 생성 이미지를 페이지 전체 배경이나 문서 증거로 사용하지 않는다.

## 5.6에 전달할 단일 시작 프롬프트

> `REFERENCE-DIRECTION-V3.md`를 먼저 읽고, `BUILD-BRIEF.md`는 콘텐츠 사실과 기술 검수에만 참고해 BD 중심 포트폴리오를 구현해줘. 시각 방향은 [V3-A / V3-B]다. `REVISION-V2.md`와 충돌하는 시각·배치 지시는 V3가 우선한다. design-agent는 프롬프트 작성과 작업에 적용하지 마. `gsap-scrolltrigger-storytelling`과 `gsap-scrolltrigger`를 이용해 그룹바이 프로젝트 내부의 판단을 스크롤 장면으로 연결해줘. 첫 화면과 그룹바이 진입 장면을 실제 1440px·390px 브라우저에서 먼저 구현·검수하고, 이후 전체 랜딩을 완성해줘. 원본 덱 표지는 상세 근거로 남기고, 랜딩 프로젝트 표지는 새 HTML/CSS/SVG로 제작해 '포트폴리오용 표지'로 취급해줘. 대표 화면의 모든 카피·링크·모바일·모션 감소 설정까지 확인한 실행 결과를 전달해줘. 공개 배포는 별도 요청이 있을 때 진행해줘.

## 첫 화면: 글자와 작업이 만나는 방식

확정 카피:

```
피성환
사업개발 · 제품 기획 · AI 활용
사업을 기획하고,
필요한 제품을 만듭니다.
작업 보기 ↗
```

첫 화면의 실제 화면 높이 900px 기준 상단 55~60%에 소개를 놓고, 하단 40~45%에 그룹바이 작업이 시작하도록 한다. 콘텐츠가 900px에서 끝나지 않아도 된다. 72%, 수익 추정, Expert 평가는 첫 화면 밖이다. 이름은 작은 헤더에서 한 번만 보인다. 제목은 기본 HTML 텍스트이며 로드나 스크롤 애니메이션 실패 때도 보인다.

### A의 타입 결합

- `사업을 기획하고,`: 한글 명조. 화면에서 편안하게 읽히는 중간 굵기. 실제 1440px 시작값 72~94px.
- `필요한 제품을 만듭니다.`: 한글 고딕. 약 700~800. 실제 1440px 시작값 72~92px. 첫 줄보다 1~2열 안쪽에서 시작해 의미 전환을 시각화한다.
- 한글 서체를 억지로 italic 변형하지 않는다. 특정 글자 하나만 폰트를 바꾸는 장식도 하지 않는다. 줄 단위 대비가 핵심이다.
- font-synthesis none. 실제 glyph, 줄바꿈, 획 두께를 1440·390px에서 확인한다. 모바일에서는 들여쓰기와 굵기 관계를 보존하되 두 줄 다 화면폭에 맞게 34~46px으로 재구성한다.
- A의 짙은 녹색 표지는 새 코드로 제작한다. 정확한 텍스트는 아래 프로젝트 표지 규칙을 따른다.

### B의 여백과 작업 전시

- 흰색의 높은 밝기와 의도적인 공백. 소개는 고딕 70~86px 시작, 두 줄 사이의 높이와 왼쪽 인덱스 `01`이 리듬을 만든다.
- 작업이 아래부터 화면폭 약 70~75%로 들어온다. 프로젝트 캡션은 표지 바깥의 오른쪽 좁은 열에 둔다. 작은 문서 근거는 캡션 아래에서 시작.
- B의 토마토색은 프로젝트의 독립 웹용 표지에만 크게 사용한다. 이후 모든 케이스를 붉은 카드로 반복하지 않는다.
- 모바일에서는 넓은 공백을 그대로 줄이는 대신 소개→프로젝트명→표지→근거 순서로 재배치한다.

## 그룹바이의 웹용 프로젝트 표지

실제 덱 표지가 그대로 랜딩의 큰 시각 면이 되면 발표자료의 인상이 남는다. 별도의 **포트폴리오용 표지**를 HTML/CSS/SVG로 만든다.

표지의 실제 텍스트는 이 세 개만:

```
AI 실무능력시험
사업 가설 · 채용 연결 · 실행 준비
01 / GROUPBY CASE
```

표지 외부의 카피:

```
그룹바이 신사업 제안
공개자료 기반 독립 제안
```

표지가 원본 제안서 표지인 것처럼 보이는 'PDF page 01' 표기 금지. 실제 덱·세일즈 1페이저는 본문 검증 장면에서 직접 링크하고 필요한 경우 작은 문서 축소본으로 보여준다. 그룹바이 로고·기업 목록·서명·시장 규모 그래프를 새 표지에 지어내지 않는다. 표지의 강한 활자만으로 시각 면을 잡는다.

## 본문: 짧은 쇼케이스 이후 실제 판단

### 구간 1 — 관찰

한 문장: `서류에서 드러나지 않는 실무 역량을 어떻게 확인할까.`

HTML 텍스트로 표본 설명과 `약 72%`를 작은 보조 근거로 둔다. 원본의 공고 1,000건 표본임을 바로 옆에 붙인다. 이 구간은 정적이다. 숫자를 카운트업하거나 시장 성과로 보이게 하지 않는다.

### 구간 2 — 사업 구조

한 문장: `평가를 채용 연결로 이어가는 구조를 설계했습니다.`

4단계 `실무 과제 → 역량 확인 → 기업 컨택 → 채용 성사`를 타이포와 가는 기준선으로 구성한다. 유료 지점인 `우선 컨택권`, `성사 수수료`만 한 단계씩 드러난다. 거대한 화살표나 동그란 아이콘 네 개는 없다. 컴포넌트는 실제 텍스트라 복사·검색·스크린리더 접근이 가능하다.

### 구간 3 — 실행 자료

한 문장: `첫 영업에 필요한 자료와 검증 순서를 준비했습니다.`

실제 세일즈 1페이저와 2주 계획 중 검증 가능한 원본을 하나씩 크게 보여준다. `타겟 기업 20곳 / 세일즈 1페이저 / 2주 실행 계획`. 상태 `제안 단계 · 실제 운영 성과 없음`. `제안서 보기 ↗ / 세일즈 1페이저 ↗`. 타겟 목록은 민감정보·출처 확인 후 노출 범위를 정한다.

위 3구간의 화면은 텍스트와 증거를 한 번에 모두 꺼내놓지 않는다. 한 단계의 핵심 문장 하나와 근거 하나만 우선 배치하고 다른 내용은 다음 스크롤 위치에서 이어진다. 그러나 링크와 사실을 opacity 0에만 의존해 숨겨서는 안 된다. GSAP이 없으면 세로 문서 흐름으로 모두 읽힌다.

## 두 GSAP 스킬을 강하게 활용할 위치

목표는 모션의 양이 아니라 **'판단이 바뀌면 화면의 무엇이 달라지는가'를 정확히 보여주는 것**이다.

1. **프로젝트 표지의 handoff:** 첫 화면 하단의 포트폴리오용 표지가 다음 구간에서 넓어지며 상세 내용의 배경으로 이어진다. 표지를 포함하는 wrapper만 잠시 고정하고 그 안의 child를 transform. 약 0.7~1.0 viewport의 추가 스크롤에서 끝낸다. 제목·상태·PDF 링크는 계속 보인다.
2. **단일 pinned decision stage:** 관찰→사업 구조→실행의 3비트를 timeline label `observe`, `model`, `execute`로 묶는다. 같은 증거 프레임 안에서 실제 자료가 바뀌고, 왼쪽 핵심 문장도 바뀐다. `pin: true`, `scrub: 0.4~0.6`. 전체 추가 스크롤은 약 1.6~2.0 viewport부터 시작해 실제 읽기 시간을 봐서 조정. 각 비트가 읽히는 체류 구간을 확보.
3. **가로 동기화:** 사업 구조 4단계는 pinned decision stage의 내부 track에서 왼쪽으로 이동. 내부 가로 이동은 `ease: 'none'`, x거리는 `scrollWidth - clientWidth`로 계산. **pin은 바깥 stage, x는 내부 track**. 외부 timeline 안에 ScrollTriggered child tween을 중첩하지 않는다. 단계별 강조를 timeline 위치로 제어하거나 containerAnimation을 사용할 때 하위 pin/snap을 만들지 않는다.
4. **자료 강조:** 실제 1페이저의 한 부분을 가는 사각 윤곽으로 강조하되 자료 자체를 가짜 UI로 그리지 않는다. 그 영역의 요지를 HTML로 옆에 적는다. 문서가 작아지거나 잘려 판독 불가능해지면 오버레이를 빼고 원본 열기 링크로 연결.
5. **장면 전환:** 폭·높이·top을 매 스크롤마다 바꾸지 않고 transform·opacity·색 대비로 전환. 마스크나 blur는 읽는 문장을 가리지 않는 짧은 handoff 한 번만 허용.

추가 고정 구간은 총 2개를 넘지 않는다. intro 전체 pin 없음. reduced-motion과 1100px 이하에서는 모든 장면을 정적인 세로 흐름으로 재구성한다. 키보드 Tab 이동이 가로 track의 화면 밖 링크를 찾아갈 때 위치가 따라오는지 확인한다. 섹션 앵커 진입, 뒤로가기, 리사이즈, 이미지만 늦게 로드되는 상황에서 ScrollTrigger.refresh와 정리 기능을 확인한다. 플러그인은 초기 등록 한 번, React라면 gsap.context 또는 useGSAP에서 cleanup. 브라우저 스크롤 자체를 가로채지 않는다.

## 메인 이후

프로젝트 카드 6장을 균등 배치하지 않는다. 그룹바이 다음에는 **제품 구현**을 한 섹션으로 놓고 사주 다이어리와 인사ON의 실제 화면을 두 개의 다른 크기·비율로 보여준다. 그 뒤 AX 예선 상위 10% / 별도 APEX Expert / Fieldbook을 얇은 텍스트 목록으로 정리한다. 소개·이메일·이력서로 끝낸다. 자료의 자세한 기술·가정·한계는 사례 페이지/PDF로 연결한다.

## 통과 조건

- 1440×900에서 소개와 첫 작업의 시각 관계가 한 번에 이해된다.
- A/B 중 어느 안이든 첫 화면을 숫자나 도표를 삭제해도 고유한 디자인으로 인식된다.
- 390px에서 활자의 자형·줄바꿈·작업 진입이 의도적이다. 데스크톱을 축소만 하지 않는다.
- 포트폴리오용 표지와 실제 덱 표지의 차이를 UI에서 알 수 있다.
- 그룹바이의 제안 상태를 계약·매출·시장 검증처럼 보이게 하지 않는다.
- pin 중 오래 제자리에 갇히는 느낌이 없고, 빠르게 스크롤해도 순서가 뒤섞이지 않는다.
- 느린 스크롤·빠른 스크롤·역방향·모션 감소·JS 실패에서 내용과 링크 접근이 된다.
- 첫 화면/프로젝트 진입/3비트 각각의 실제 브라우저 스크린샷을 검토한다. 이미지 생성 시안은 렌더링 검수의 대체물이 아니다.

V3 시안은 사용자가 비교할 후보이며 완성된 웹 화면 또는 승인된 디자인은 아니다.
