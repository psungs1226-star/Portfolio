# V2 — 웹 포트폴리오 미감 재설계

이 문서는 BUILD-BRIEF.md의 시각·배치·모션 지시보다 우선한다. 기존 시안 A/B는 사용자가 발표자료 같다고 지적했으므로 승인된 디자인이 아니다. 기존 명세의 사실·자산 경로·기술 안정성·접근성 검수는 유지한다.

## 사용자 제약

- BD를 메인으로 유지한다.
- 카피는 담백하게 유지한다.
- 자료 정리만 잘한 페이지로 끝내지 않는다. 구성과 활자에서 디자인 감각이 보여야 한다.
- 프롬프트 작성에 design-agent 스킬을 적용하지 않는다. 이 작업의 이미지 프롬프트와 후속 제작 지시에도 해당 스킬을 적용하지 않는다.
- V2 두 이미지는 위 마지막 지시 이후 직접 작성한 이미지 프롬프트로 생성했다. 앞서 생성한 초대형 이름의 청보라 시안은 최종 V2 세트에 포함하지 않는다.

## 5.6에게 전달할 프롬프트

> REVISION-V2.md를 먼저 읽고 BUILD-BRIEF.md에서 사실·원본 자료·기술 검수 항목을 참고해 구현해줘. 시각·배치·모션이 충돌하면 V2를 우선해줘. 선택 방향은 [V2-A / V2-B]다. design-agent는 프롬프트 작성과 이 작업에 적용하지 마. GSAP 두 스킬은 사용해. 발표자료처럼 큰 지표와 도표를 차례로 늘어놓지 말고, 소개에서 실제 프로젝트로 이어지는 웹 포트폴리오를 만들어줘. 원본 표지의 내용은 보존하되 이미지 생성 결과를 실제 원본처럼 사용하지 마. 첫 화면과 이어지는 대표 작업을 먼저 실제 브라우저에서 검수한 후 전체를 연결해줘. 모바일·모션 감소 설정도 검수하고 실행 가능한 결과와 스크린샷을 전달해줘.

## 1. 기존 안의 문제

1. 큰 이름, 큰 72%, 도표, 문서 세 장이 비슷한 강도로 경쟁했다.
2. 매 섹션을 제목+설명+증거로 정렬해 발표자료의 정보 전개를 그대로 웹에 옮겼다.
3. 긴 전체 페이지를 한 장에 축소해 활자의 실제 크기·여백·스크롤 연결을 판단하기 어려웠다.
4. 흰색/먹색만 바꾼 두 안의 구조가 비슷했다.

## 2. 바뀐 화면 순서

**짧은 소개 → 그룹바이 대표 작업을 크게 전시 → 핵심 판단 3개를 압축 → 제품 작업 → 짧은 평가·소개·연락**

그룹바이가 메인이라는 것은 설명 문단의 개수가 아니라 첫 번째 배치·산출물의 크기·시선 점유율로 표현한다.

- 첫 화면: 소개 두 줄, 작은 역할, 링크. 이름은 헤더에서 충분히 인지되므로 별도 거대 이름을 반복하지 않는다.
- 첫 화면 하단 또는 다음 화면 초입: 대표 작업의 큰 시각 면. 제목과 독립 제안 상태는 이미지 밖 HTML로 제공한다.
- 그 다음: '관찰 / 사업 구조 / 실행 준비'를 한 구간에 압축한다. 72%는 보조 근거로 내려 32~48px 정도로 표시. 더 이상 첫 인상이나 전체 페이지의 대표 그래픽이 아니다.
- 대표 작업을 열면 원본 PDF 또는 상세 사례로 연결한다. 메인에 덱 전체를 재구성하지 않는다.

## 3. V2-A — 갤러리

파일: reference-v2-A-gallery.png

- 온기가 아주 옅은 백색 배경, 오른쪽으로 옮긴 명조 소개, 왼쪽의 작은 역할 문구.
- 하단에서 대표 작업이 화면 폭의 약 75~80%를 차지한다. 다음 작업이 일부 보여 탐색 방향을 암시한다.
- 작품 주변의 옅은 라벤더 면은 문서를 읽는 구간과 구분하는 배경이다. 모든 프로젝트를 똑같은 파스텔 카드로 만들지 않는다.
- 다음 작업은 실제 사주 다이어리 화면 등으로 교체. 시안처럼 같은 표지를 반복하지 않는다.
- 갤러리 캡션: 번호 13px, 작업명 24~28px, 상태 14px. 소개는 1440px 기준 약 56~64px, 2줄, 중간 굵기. 본문은 고딕.
- 시안 명조는 자형 참고일 뿐 동일 글꼴을 보장하지 않는다. 실제 글꼴의 '사업을 기획하고' 자형을 보고 골라야 한다. 붓글씨처럼 보이거나 획이 너무 가늘면 고딕으로 대체한다.
- 모바일에서는 소개를 왼쪽 정렬로 재배치하고 프로젝트를 세로로 배치한다. 옆으로 넘겨야 핵심 내용을 볼 수 있는 구조 금지.

### A의 움직임

- 소개 영역은 정적. 처음부터 완전히 읽힌다.
- 데스크톱 갤러리 한 구간만 pin. 기본적으로 그룹바이→제품 구현 대표 화면까지 짧게 이동한다. x 이동 거리는 실제 overflow 기반, ease none, scrub 0.4 시작값.
- 다음/이전 버튼과 키보드 탐색도 제공한다. 휠을 가로채지 않는다. 콘텐츠가 화면에 모두 들어가면 pin을 만들지 않는다.
- 갤러리와 사업모델에 각각 가로 이동을 중복 적용하지 않는다. A에서는 기존 사업모델 가로 이동 지시를 폐기한다.
- 사업 판단 3개는 갤러리 뒤 정적 읽기 구간으로 제공한다.

## 4. V2-B — 색면과 대표 작업

파일: reference-v2-B-color.png

- 청보라색 단색의 넓은 첫 화면. 좌측 정렬의 중간 굵기 고딕 소개와 작은 역할.
- 아래의 따뜻한 백색 캡션 면과 검은 원본 표지가 하나의 직선 경계를 공유한다. 프레임·카드·패딩으로 조각내지 않는다.
- 작은 헤더 이름 외에 거대 이름 없음. 소개 64~76px 시작, line-height 1.25~1.35. 극단적인 얇은 획은 실제 화면에서 대비·선명도를 보고 조정한다.
- 표지는 object-fit: contain 기본. 원본 전체를 보존한다. 시안의 생성 텍스트는 원본 PNG로 교체한다.
- 청보라를 전체 페이지에 반복하지 않는다. 대표 작업 상세로 들어가면서 백색/검정의 실제 자료 색으로 자연스럽게 이어진다.
- 모바일에서는 색면 소개→짧은 작업 캡션→표지 순서로 쌓는다.

### B의 움직임

- 스크롤 초입에서 실제 대표 표지가 화면 안으로 들어오는 한 번의 동작에 집중한다.
- 표지 wrapper를 잠깐 고정하고 안쪽 이미지와 캡션을 함께 이동시켜 자연스럽게 본문으로 이어준다. 이름과 카피에 글자별 효과를 넣지 않는다.
- 대표 작업 구간을 지난 후 필요하면 사업 구조의 4단계 가로 이동을 한 번 사용. 4단계는 텍스트 중심으로, 원형 아이콘이나 선박형 인포그래픽처럼 꾸미지 않는다.
- 전체 pin은 최대 2개, 각 추가 스크롤은 약 1화면 전후를 출발점으로 실제 브라우저에서 조정한다.

## 5. 실제 산출물의 취급

- V2는 원본 그룹바이 표지를 입력 이미지로 사용했지만 생성 도구가 내부 글자·선·비율을 바꿀 수 있다. 구현은 반드시 원본 `Groupby_BD/assets/proposal-cover.png`를 쓴다.
- 원본 표지 자체가 발표자료처럼 보이는 점은 남아 있다. 포트폴리오에서 더 높은 미감이 필요하면 '대표 작업용 썸네일'을 별도로 HTML/CSS로 디자인할 수 있다. 그때는 `그룹바이 신사업 제안 / AI 실무능력시험 / 공개자료 기반 독립 제안`만 사용하고, 실제 PDF 표지라고 주장하지 않는다. 고객사 로고·매출 수치를 임의로 추가하지 않는다.
- 전체 사이트를 생성 이미지로 붙이지 않는다. 실제 활자·실제 링크·실제 원본을 배치한다.

## 6. 통과 판단

- 첫 화면이 자료의 목차처럼 보이면 재설계한다.
- 72%를 지워도 페이지의 시각적 인상이 유지돼야 한다.
- 1440×900에서 단번에 소개 문장과 첫 작업으로 시선이 이어져야 한다.
- 두 개의 큰 글자 블록이 동시에 경쟁하면 하나를 줄인다.
- 원본 산출물을 작게 여러 장 넣기보다 한 장을 충분한 크기로 보여준다.
- 표지와 목업을 제외한 여백도 역할을 갖는다. 빈 곳을 소문구·아이콘·영문 슬로건으로 채우지 않는다.
- 정지 시안은 모션의 완성도를 증명하지 않는다. 실제 브라우저에서 느린 스크롤·빠른 스크롤·역스크롤·모바일을 확인한다.

현재 두 안은 검토 후보이며 승인된 최종 방향이 아니다.
