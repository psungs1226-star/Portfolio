# Design Fieldbook

디자인 이론 전체(원칙·색상·타이포·레이아웃·UI 패턴·접근성·디자인 시스템·스타일 29종)와 모션 도메인을 다루는 자급자족 필드북. 아래 핵심 수치는 모든 작업에 공통으로 적용되고, 그 외 상세 이론은 `references/`에 있다 — 해당하는 작업일 때만 그 파일을 읽는다.

## 작업 진입 순서

1. **방향 판단** — 사용자 지정 여부 확인, 없으면 추론 (§작업 시작 전)
2. **레퍼런스 결정** — 이 작업에 필요한 챕터를 목록화 (§챕터 포인터)
3. **계획** — 콘텐츠 우선순위·스타일·레이아웃·색상 수·색상 조합을 한 문단으로 (§작업 시작 전)
4. **이미지 시안** — 계획을 이미지 3장으로 뽑아 비교하고 1개를 레퍼런스로 확정한 뒤 톤앤매너·레이아웃을 계획에 되먹인다. `장르: 마케팅`이면 기본 실행, 앱·문서는 사용자가 요청할 때만, codex CLI가 없거나 실행 실패면 생략하고 5로 간다 (§`references/draft-images.md`)
5. **토큰 생성 → 즉시 1차 게이트** — 토큰을 손으로 고르지 않는다. `tokens.py`에 시드 색과 톤을 넣어 받은 블록을 붙여넣고 `gate.py --static-only`를 돌린다 (§토큰은 계산해서 받는다)
6. **구현** — 전 챕터 공통 수치 적용 + 2에서 정한 챕터만 로드해 상세 반영
7. **게이트 루프** — `gate.py` 실행. **독립 에이전트의 미적 검토(필수)가 먼저고, 그걸 통과해야 코드 게이트(0 FAIL)로 넘어간다.** 코드 게이트 수렴 후 육안 확인까지 마쳐야 완료다 (§완료 전 — 게이트 루프)

**토큰의 지위 — 이론과 사례를 구분하라**: `references/`에 실린 실측 토큰값(오렌지 액센트 hex, 타입 스케일 10/11/…/34px, radius 0/2/4px, 섹션 리듬 110px 등)은 이론이 아니라 **Fieldbook 사이트라는 하나의 사례 시스템**이다. 산출물에 이 값을 복사하면 모든 결과물이 Fieldbook 문서 사이트처럼 보인다 — 가져갈 것은 역할 구조(fill/text 분리, 역할 기반 스케일, 토큰 5그룹, 리듬의 토큰화)이고, 값은 프로젝트의 장르(랜딩/앱/문서)와 스타일(`references/styles.md`에서 선택)에 맞게 새로 정한다. 아래 "공통 수치"만이 장르 무관 규범이다.

## 작업 시작 전 — 방향 판단과 계획

`references/`를 열기 전에 먼저 이 요청이 어떤 디자인 방향을 원하는지 판단한다.

- **사용자가 방향을 명시했다면** 그대로 따른다("미니멀하게", "브루탈리즘으로", "트렌디하게", "절제되게" 등).
- **명시하지 않았다면** 아래 TPO 판정으로 톤을 먼저 확정한다. 감으로 고르지 않는다.

### TPO 판정 — 톤을 수치로 확정한다

"상황에 맞게"는 지켜지지 않는다. 실제로 g라운드에서 계획에 "절제"라고 적어놓고 채도 100%의 형광 라임을 칠했다 — 산문 규칙만으로는 실행자가 자기 계획과 반대로 가도 아무것도 막지 못한다. 아래 3축에 **콘텐츠에서 근거를 찾아** 답하고, 나온 톤의 수치 밴드를 그대로 지킨다.

**A. 판돈** — 이 화면을 보고 독자가 무엇을 결정하며, 틀리면 무엇을 잃는가.
- `신뢰` — 채용·투자·거래·의료·법률·금융. 잃는 것이 돈이나 경력이다
- `주목` — 캠페인·이벤트·커뮤니티·엔터. 안 보고 지나치는 것이 유일한 손실이다

**B. 어조** — 본문에서 가장 자주 반복되는 **문장 유형**을 센다. 인상이 아니라 문장을 센다.
- `유보형` — "측정하지 않았습니다" "주장하지 않습니다" "확정하지 않습니다" "가정하지 않습니다" 같은 한계·조건·검증 문장이 반복
- `단정형` — 선언·초대·확신 문장이 반복

**C. 밀도** — 표·수치·비교가 많아 정독 대상인가(`고밀도`), 훑고 지나가는가(`저밀도`).

**D. 장르** — `마케팅`(랜딩·포트폴리오·브랜드) / `앱`(대시보드·어드민·툴) / `문서`(레퍼런스·아티클). 톤과 별개 축이고, **게이트가 장르마다 다른 잣대를 쓴다.** 다크 대시보드로 검증해보니 "radius 중간값 · 하드섀도 없음 · 그라데이션 없음"은 마케팅 페이지에선 커밋 부족이지만 밀도 높은 앱 UI에선 올바른 선택이었다 — 장르 없이 한 잣대를 강요하면 오탐이 된다.

| 장르 | 타입 스케일 상한 | 스타일 커밋 | 이 장르의 슬롭 |
|---|---|---|---|
| 마케팅 | 10종 | **필수** (최소 1축 극단) | 커밋이 없는 것 = 무난한 회색 UI |
| 앱 | 14종 | 요구하지 않음 | 값이 제각각인 것 → radius·shadow 각 4종 이하 |
| 문서 | 12종 | 요구하지 않음 | 위와 같음 |

**판정 규칙**(위에서부터 먼저 걸리는 것을 적용):
1. B가 `유보형` → **절제**. 어조가 판돈을 이긴다 — 한계를 공개하는 문장을 형광으로 외치면 화면과 글이 서로 싸운다
2. A가 `신뢰` → **절제**
3. A가 `주목` + B가 `단정형` → **임팩트**
4. 그 외 → **중립**

**톤 → 수치 밴드.** 지표는 HSL 채도가 아니라 **크로마 `(max−min)/255`**다 — HSL S는 최대 채널이 255이기만 하면 아무리 밝아도 1.00이라, 산성 라임(`#C4F000`)과 평범한 다크 UI 액센트 블루(`#4C9AFF`)가 둘 다 S=1.00으로 나와 구별되지 않는다. 크로마로 재면 0.94 vs 0.70으로 갈린다.

| 톤 | 액센트 크로마 | 추가 제약 |
|---|---|---|
| 절제 | **≤ 0.78** | 형광 금지 — 크로마 > 0.85 이면서 `0.35 ≤ L ≤ 0.75` |
| 중립 | 0.20 – 0.90 | — |
| 임팩트 | ≥ 0.45 | 액센트 계열은 여전히 색상환 1갈래 |

크로마 **하한은 주 액센트(`--acc`)에만** 적용한다 — 컨테이너·틴트·on-color는 낮은 게 정상이다. 상한은 전 단계에 적용한다.

**액센트 면적은 톤만으로 못 정한다 — 장르와 함께 본다.** 세 장르 프로브에서 전부 밴드를 벗어났고 셋 다 그 장르에선 정상이었다(문서 4.7% · 앱 0.8% · 캠페인 46.7%). 같은 톤이라도 장르가 바뀌면 적정 면적이 한 자릿수 배로 달라진다.

| 면적 % | 절제 | 중립 | 임팩트 |
|---|---|---|---|
| 마케팅 | 5–15 | 8–25 | 15–55 |
| 앱 | 0.5–8 | 2–12 | 5–18 |
| 문서 | 0.5–8 | 2–12 | 5–18 |

밀도가 높으면 위계를 크로마가 아니라 **명도 단계와 컨테이너 톤**으로 만든다(`references/color.md` "콘텐츠 내부 강조"). 크로마를 따로 깎지는 않는다 — 그건 면적이 이미 재고 있는 것을 이중으로 세는 것이라, 문서 사이트의 표준 링크 블루(`#0A5FB4`, 크로마 0.67)마저 걸렸다.

형태(radius)는 톤에서 나오지 않는다 — 각짐은 기술적·공격적, 둥긂은 친근·부드러움으로 읽힐 뿐 신뢰도와는 무관하다. **사용자가 형태를 명시했으면 그대로 따르고**, 없으면 선택한 스타일의 정의를 따른다.

### 계획 — 한 문단으로

방향과 톤을 확정했으면, 구현에 들어가기 전에 아래 5가지를 한 문단으로 적는다 — Plan 모드가 이미 켜져 있거나 사용자가 "그냥 바로 만들어줘"처럼 계획 단계를 건너뛰라고 명시하지 않는 한 생략하지 않는다:
  0. **로드할 레퍼런스**: 이 작업에 어떤 챕터가 필요한지 목록으로 적는다(아래 챕터 포인터 기준) — styles는 어느 카테고리 파일까지, motion은 어느 절까지인지도 함께. 계획에 적은 목록과 실제로 읽은 파일이 일치해야 한다
  1. **콘텐츠 우선순위**: 이 콘텐츠에서 가장 먼저 보여줄 것과 압축·제외할 것을 정한다 — 표준 템플릿(히어로→타임라인→통계 그리드→카드 그리드 같은 안전한 기본값)을 그대로 따르지 않고, 이 콘텐츠만의 핵심 메시지가 섹션 배정에 반영되게 한다
  2. **스타일**: **메인 레퍼런스 8종 또는 조합 프리셋 3종에서 먼저 고른다** — `material` `material-you` `brutal` `neobrutal` `glass` `neumorph` `clay` `memphis` / `preset:refined-product` `preset:editorial-kinetic` `preset:bento-showcase`. 이 밖으로 나가려면 이유를 적는다. 금지 7종(아래)은 후보에서 제외. DNA 8축 중 어떤 축을 극단(0 또는 4–5)으로 밀지까지 정한다(`references/styles.md`). **프리셋을 골랐다면 DNA 극단 축 대신(또는 함께) 결정적 동작 2~3개를 계획에 그대로 적는다** — 이름만 고르고 동작을 빠뜨리면 산출물이 baseline과 수렴한다(`references/styles/contemporary.md`)
  3. **레이아웃**: `references/layout.md` 14종 중 1에서 정한 우선순위에 따라 섹션별로 어떤 패턴을 배정할지. 배정 결과를 패밀리 단위로 세어 연속 반복·종수 상한을 확인하고, 동종 항목이 4개 이상이면 대표 1개의 차등 방식(전폭/`span 2`/패밀리 교체)을 여기서 정한다
  4. **색상 수**: 브랜드 액센트 1개 원칙(아래 참고)은 유지하되, 표·비교·카테고리 구분이 있는 콘텐츠라면 시맨틱/중립 명도 차를 몇 단으로 쓸지까지 정한다 — "액센트 1개 + 무채색"만으로 끝내지 않는다(`references/color.md` "콘텐츠 내부 강조" 참고)
  5. **색상 조합**: 위 TPO 판정이 내놓은 톤(절제/중립/임팩트)과 그 수치 밴드. 여기서 판정을 뒤집지 않는다
  6. **모션**: signature motion을 **하나만** 정한다(`references/motion.md` §5.3). `장르: 마케팅`이면 `없음`을 쓸 수 없다 — entrance 연출 1회 + signature 1개가 바닥선이고(§2.6), 직접 설계하지 않을 거면 §7 카탈로그에서 골라 번호로 적는다(예: `entrance=§7.1 / signature=§7.4 배포시간 게이지`). 앱·문서는 `없음` 가능. 여기서 "쓸지 말지"를 반드시 답한다 — 이 칸을 만들기 전에는 챕터 포인터가 "애니메이션을 넣을 때 → motion.md"라고만 되어 있었고, **넣기로 이미 결정한 뒤를 전제하는 문장이라 결정 자체를 아무도 묻지 않았다.** 그 결과 산출물 6개 연속으로 `@keyframes` 0개가 나왔다. 나머지는 상태 전이(hover/press/포커스)만 두고, 정한 값은 `tokens.py`가 내놓은 `--dur-*`/`--ease-*`를 쓴다
  7. **이미지**: 어느 자리가 이미지로 실제 시각적 효과를 내는지(제품/작업물 실제 스크린샷, 히어로의 정체성 표현, 사람·장소 등 콘텐츠 고유의 실물) **먼저 정하고**, 그 외 자리는 "비어 보여서" 채우지 않는다. 후보가 없으면 `없음`이라고 적는다 — 이 칸도 비워 두는 선택지가 없다. 우선순위: ①이미 가진 실제 스크린샷·사진(가장 먼저 소진) ②정체성을 증명해야 하는 히어로 한 곳 ③그 외엔 생성하지 않는다. "설명 문단 옆이 허전하다"는 생성 이유가 안 된다 — 문단은 타이포그래피로 채우는 것이지 그림으로 채우는 게 아니다

이 계획이 이후 각 `references/` 챕터를 적용할 때의 기준이 된다 — 챕터를 읽으며 계획과 어긋나는 지점이 나오면 계획을 수정한다.

**이 절과 `references/draft-images.md`는 다른 단계다**: 아래 "이미지를 실제로 생성해야 할 때"는 **완성된 페이지 안에 들어갈 콘텐츠 이미지**(히어로 비주얼·제품 컷)를 만드는 구현 단계고, `references/draft-images.md`는 **페이지 전체의 시안(draft)**을 만들어 방향을 고르는 계획 직후 단계다. 시안 PNG는 페이지에 삽입하지 않는다.

**이미지를 실제로 생성해야 할 때 — 톤앤매너 강제**: 위 7번에서 자리를 정한 뒤 이미지 생성 도구(별도 이미지 생성 스킬·모델)를 호출한다면, 그 프롬프트에 **반드시** 아래 네 가지를 이 페이지의 실제 값 그대로 박아 넣는다 — "적당히 어울리게"라고만 지시하면 십중팔구 범용 스톡 이미지가 나온다:

- **선택한 스타일명과 DNA 극단 축** (예: "material-you, 톤: 부드러운 tonal 그라데이션, 각짐 없음")
- **액센트 hex와 배경/표면 톤** — 이미지 생성기가 스스로 배색을 고르게 두지 않는다. 페이지의 `--acc`/`--bg`/`--surface`를 그대로 팔레트 제약으로 넘긴다
- **이 콘텐츠 고유의 구체적 주제** — 회사명·제품명·실제 업무 행위(예: "인사 규정 조문을 검색하는 화면", "ETF 적립 백테스트 그래프")처럼 다른 프로젝트에 그대로 옮겨도 말이 되면 안 된다(`references/motion.md` §5.4 replaceability test와 같은 기준을 이미지에도 적용)
- **금지 목록을 명시적으로 포함**: 추상 지오메트릭 라인아트·원/사각형 도형, 손잡는 사람들, 전구 아이디어 아이콘, 로켓 발사, 떠다니는 3D blob/구체 — 전부 "AI가 만든 비즈니스 이미지"의 가장 흔한 디폴트라 콘텐츠와 무관하게 채워진 필러로 즉시 읽힌다

생성된 이미지는 1단계(미적 독립 검토)의 "이미지·일러스트 관련성" 축에서 다시 검토받는다 — 통과 못 하면 이미지를 다시 만들거나 그 자리를 없앤다, 프롬프트만 살짝 고쳐 재시도를 반복하지 않는다.

**계획을 산출물 안에 심는다(필수)**: 계획을 대화에만 적으면 구현이 그것과 어긋나도 아무도 모른다. 아래 블록을 생성한 HTML의 `<style>` 맨 위에 넣는다 — `verify.py`가 이 선언과 실제 CSS를 대조해 어긋나면 FAIL을 낸다.

```css
/* plan
   판돈: 신뢰 | 어조: 유보형 | 밀도: 고밀도 | 장르: 마케팅
   톤: 절제
   스타일: material-you
   레이아웃: split / bento / magazine / table / card / timeline
   모션: entrance=§7.1 / signature=CTA 확인 체크 1회 / 나머지 상태 전이만
   이미지: 히어로 1곳(제품 스크린샷) — 그 외 없음
   시안: draft-b(material-you 변주) — 콘텐츠 위계가 가장 정확
*/
```

`톤:`은 `절제`/`중립`/`임팩트`, `장르:`는 `마케팅`/`앱`/`문서` 중 하나여야 한다. `시안:`은 채택한 시안 파일명 + 변주 축 + 채택 근거 한 줄을 적고, 시안 단계를 건너뛰었으면 `시안: 생략(<사유>)`이라고 적는다(`references/draft-images.md`). `모션:`과 `이미지:`는 각각 signature motion 1개(마케팅은 entrance 연출도 함께) 또는 이미지 배치 위치를 적거나 `없음`이라고 적는다 — **둘 다 비워 두는 선택지가 없고, `장르: 마케팅`의 `모션:`에는 `없음`도 쓸 수 없다**(`references/motion.md` §2.6 바닥선). 선언한 톤의 크로마 밴드를 실제 액센트 토큰이 지켜야 하고, 장르에 따라 적용되는 검사가 달라진다.

## 스타일 방향 — 메인 레퍼런스와 금지

- **메인 레퍼런스 8종 또는 조합 프리셋 3종**(방향 미지정 시 여기서 먼저 고른다): `material` · `material-you` · `brutal` · `neobrutal` · `glass` · `neumorph` · `clay` · `memphis`. 깊이·질감·색을 적극적으로 쓰는 계열이고, 카테고리 파일에 그림자 공식·보더 비율 등 **구현 스펙**이 붙어 있다
- **조합 프리셋 3종**(8종과 동등한 후보): `preset:refined-product` · `preset:editorial-kinetic` · `preset:bento-showcase` — 스타일(조형 언어)과 다른 층위의 검증된 조합(레이아웃+타이포+색+모션 한 판). 각 프리셋의 **결정적 동작**을 이행하지 않으면 금지 7종과 동일 판정이다 → `references/styles/contemporary.md`
- **금지 7종**(후보로 올리지 않는다): `swiss` · `bauhaus` · `destijl` · `construct`(순수주의 기하학 — 100년 전 인쇄 조형이라 웹에서 구식으로 읽힌다) / `minimal` · `flat` · `corporate`(DNA 8축이 전부 중간값 — "모던하고 깔끔하게"에 AI가 뱉는 무난한 회색 UI 그 자체). 사용자가 이름을 직접 지정했을 때만 예외로 하되, 슬롭 위험을 먼저 알리고 대체안을 함께 낸다. 사유·대체 스타일은 `references/styles.md` "금지 스타일" 절
- **레시피의 hex를 복사하지 않는다**: 카테고리 파일의 구현 스펙에 실제 색값이 있지만 그건 Fieldbook 목업의 실측값이다. 가져갈 것은 **관계**(그림자 겹수·방향, 보더와 오프셋 비율, 투명도 단계, 배경/표면 톤 차)이고, 색 자체는 브랜드·주제에 맞게 정한 뒤 그 관계를 재현한다. 색 조합은 `references/color.md`의 패턴 7종과 대비 기준을 따른다 — **어울리는 조합이 먼저고, 스타일은 그 조합을 어떤 구조로 배치할지를 정한다**

## 토큰은 계산해서 받는다 — 손으로 고르지 않는다

```
python3 <스킬 경로>/scripts/tokens.py '<시드 hex>' <톤> [--density 고밀도]
```

**정하는 것은 두 가지뿐이다 — 시드 색조와 톤(TPO 판정 결과).** 나머지 값은 전부 계산으로 결정된다: 액센트 램프 6단, 잉크 3단, 배경·**섹션 밴드**·표면·구분선, 다크 밴드용 2단, 타입 스케일 8토큰, 여백 6단. 스크립트가 emit 전에 대비·델타·채도 밴드를 실측해 하나라도 미달이면 아예 내놓지 않는다.

이렇게 하는 이유는 **게이트에 걸린 것 중 상당수가 판단 실패가 아니라 값 하나를 잘못 고른 것**이었기 때문이다 — 구분선을 배경과 같은 계열로 잡아 1.00:1이 되거나, 절제를 선언하고 채도 100% 시드를 쓰거나, 배경/표면 델타가 10 미만이거나. 전부 계산으로 나오는 값인데 감으로 고르고 나중에 게이트가 잡는 구조였다. 계산해서 받으면 그 실패 유형 자체가 사라진다.

- 시드 채도가 톤 밴드를 넘으면 **색조는 유지한 채 밴드 안으로 내려서** 내놓는다. 넘긴 채로 나가지 않는다
- 이 시드로는 밴드를 만족하는 램프가 안 나오면 exit 1 — 그때는 시드 색조를 바꾼다
- **섹션 밴드는 `--band`, 액센트 면 위 보조 텍스트는 `--on-acc-2`** — 액센트 램프의 옅은 틴트(`--acc-cont-2`)를 그 자리에 쓰지 않는다. 표면용으로 계산된 값이라 배경과 델타 6, 액센트 면 위 3.85:1이 나온다(i라운드에서 둘 다 났다)
- 흰 글씨가 fill 위에서 4.5:1을 겨우 넘기는 액센트면 스크립트가 노트를 띄운다 — 그때는 **액센트 면 안의 위계를 색으로 만들려 하지 않는다.** 크기·weight·여백으로 만든다
- `radius`·그림자는 여기서 정하지 않는다. 선택한 스타일의 정의를 따른다
- 브랜드 색이 이미 정해져 있어 밴드를 못 지킨다면, 그건 톤 판정을 다시 하라는 신호다

## 전 챕터 공통 수치 (항상 적용)

- **한글 줄바꿈**: `body { word-break: keep-all; overflow-wrap: break-word; }`를 전역으로 건다 — 안 걸면 "문제를"이 "문 / 제를"처럼 음절 단위로 끊긴다(`references/typography.md`)
- **액센트 컬러**: 화면 전체의 5–12%만 사용. 채도 있는 액센트는 **색상환에서 한 갈래만** — 파랑+틸+앰버처럼 3갈래로 벌리지 않는다. 구분이 더 필요하면 시맨틱 토큰(`--ok`/`--warn`/`--err`/`--info`)이나 중립 명도 차를 쓴다(다색이 정의인 `memphis`·`neobrutal`은 예외)
- **간격 그리드**: 모든 spacing 값은 2px 배수. 홀수값(3/5/7/9px) 금지. 값을 매번 감으로 고르지 않는다 — 6단 여백 스케일을 쓰고 인접 티어끼리 최소 1.5배 차이를 둔다(`references/layout.md` "여백 스케일")
- **레이아웃 다양성**: 마케팅 장르는 동일 레이아웃 패밀리 연속 2섹션까지, 콘텐츠 섹션 6개 이상이면 패밀리 3종 이상(`references/layout.md` "섹션 레이아웃 패밀리 반복 상한"). 앱·문서 장르는 미적용
- **대비**: 본문 4.5:1, large text(24px+ 또는 18.66px+ bold) 3:1, AAA 7:1. **틴트 배경 위에 같은 색조의 원색을 얹지 않는다** — 앰버 `#F59E0B`를 앰버 틴트 `#FDECC8` 위에 놓으면 1.84:1이다. 칠하는 색과 읽는 색을 분리한다(`references/color.md` "Painting vs Reading Color")
- **타입 스케일**: font-size 종류는 **10개 이하**, 인접 단계는 **최소 1.125배** 차이. 14/15/16/17/18/19px처럼 붙여 놓으면 스케일이 아니라 감이다. 인라인 `style="font-size:..."`에 px 하드코딩 금지 — 역할 토큰만(`references/typography.md`)
- **스타일 커밋**: radius·보더·그림자 중 최소 한 축은 극단으로 민다 — radius ≤2px 또는 ≥24px / 카드 보더 ≥3px / 그림자 alpha ≥0.18 또는 blur 0 하드 오프셋. 전부 중간값이면 그게 금지 7종(`minimal`/`flat`/`corporate`) 그 자체다(`references/styles.md`). 알파 층으로 깊이를 만드는 경우(`preset:refined-product`)는 알파 보더·얕은 표면이 커밋 신호로 안 잡히므로 정적 배경 그라데이션 또는 표면 `backdrop-filter`를 함께 쓴다
- **구조적 구분**: 섹션·행 경계에 헤어라인 1px만 쓰지 않는다. 페이지 전체에 한 군데만 적용하고 끝내지 않는다 — **섹션 전환마다, 그리고 배경 위에 얹히는 카드·그리드가 배경과 맞닿는 경계마다** 왼쪽 보더·틴트 배경·채워진 면 중 하나를 겹친다(`references/color.md` "행·구분선도 색의 자원이다")
- **구분 장치는 실제로 보여야 한다**: 구분선 색 vs 그 아래 면 대비 **3:1 이상**(WCAG 1.4.11). 섹션 배경 밴드는 페이지 배경과 **RGB 델타 10 이상** — 델타 5짜리 밴드는 코드에만 있고 화면에는 없다. 톤을 못 벌리면 밴드 대신 다른 장치(액센트 면·표면 그림자)로 바꾼다
- **배경이 명도 극단이면 기준이 다르다**(페이지 배경 휘도 > 0.85 또는 < 0.2일 때 자동 적용): 순백 문서 사이트나 순흑 대시보드는 표면을 벌릴 여지가 없어 델타 6~8에 보더를 병행하는 것이 관용이다(GitHub 문서 `#F6F8FA` on `#FFF`가 델타 7). 배경/표면 델타는 **6 이상 + 표면에 보더 병행**을 허용한다 — 둘 다 약하면 경계를 만드는 장치가 없는 것이다
- **구분선은 대비식만으로 판정하지 않는다**: 대비식은 명도 양 극단에서 체감과 어긋난다 — 순백 위 `#D6DAE0`(1.31:1)도 순흑 위 `#2C353D`(1.40:1)도 실제로는 또렷이 보인다. **대비 3:1 또는 RGB 델타 18 중 하나만 만족하면** 통과로 본다
- **터치 타겟**: 44×44px + 8px 간격 (WCAG 2.2 최소 24×24px)
- **모션 방향성**: 등장 = decelerate(ease-out), 퇴장 = accelerate(ease-in), 이동 = standard(in-out). `ease-in`으로 등장시키는 것 금지
- **모션 바닥선**: 마케팅 장르는 entrance 연출 1회(≤600ms·최대 5요소) + 상호작용 요소 전부의 상태 전이 + signature motion 1개가 최소치. 앱·문서는 상태 전이만으로 충분(`references/motion.md` §2.6, 완성 코드는 §7)
- **슬롭 시그니처 7종** (코드명만 — 정의·대안은 `references/motion.md`): `SLOP-FADE-UP-ALL`, `SLOP-STAGGER-ALL`, `SLOP-HOVER-LIFT-ALL`, `SLOP-TYPEWRITER`, `SLOP-COUNTUP`, `SLOP-PARALLAX-HERO`, `SLOP-AMBIENT-LOOP`
- **모션 4-gate 순서**: Frequency → Purpose → Speed → Function (판정 절차는 `references/motion.md`)

## 완료 전 — 게이트 루프

**한 번에 통과하는 것을 목표로 하지 않는다.** 이건 선형 절차가 아니라 수렴할 때까지 도는 루프다.

```
python3 <스킬 경로>/scripts/gate.py <생성한 HTML 경로>
```

이 드라이버가 **먼저 미적 독립 검토를 확인하고, 통과해야만 `verify.py`·`render_audit.py`(코드 게이트)를 돌린다.** 순서가 이렇게 된 이유: 여백 우선순위·밀도·이미지 관련성·그리드 응집력 같은 구도 자체가 틀리면, 그 위에서 대비·spacing 값을 아무리 맞춰도 나중에 구조를 갈아엎으면서 버려질 작업이다. 싼 판단(전체적으로 방향이 맞는가)을 비싼 폴리싱(숫자 단위 미세조정)보다 먼저 끝낸다. **회차 간 상태도 기억한다.** 0 FAIL이 될 때까지 고치고 다시 실행한다. exit code가 0이 아니면 완료가 아니다.

루프가 상태를 갖는 이유는 하나다 — 예전에는 매 실행이 직전 실행을 몰라서, g라운드에서 고친 "좁은 폭에서 카드 우측이 비는" 결함이 g2에서 그대로 재발했는데도 아무도 재발로 인지하지 못했다. 드라이버는 매 회차 findings를 `신규 / 잔존 / 해결 / 재발`로 갈라준다.

**루프를 빠져나가는 법이 두 가지 있고, 둘을 구분해야 한다:**

- **신규·잔존** — 그 자리를 고친다. 정상적인 반복이다
- **재발, 또는 3회차 이상 잔존** — **국소 수정을 반복하지 않는다.** 같은 결함이 회차나 라운드를 넘어 돌아온다는 건 산출물이 아니라 **스킬 쪽에 원인이 있다**는 신호다. 토큰 층·규칙·레퍼런스를 고치거나, 그 부분의 설계(레이아웃 패턴·구조)를 바꾼다. 드라이버가 이 두 경우를 ⚠로 따로 띄운다

**루프를 앞으로 당긴다**: 토큰과 `/* plan */` 블록만 쓴 시점에서 `gate.py --static-only`를 한 번 돌린다(렌더 게이트를 건너뛰어 빠르다). 대비·채도 밴드·타입 스케일·여백 티어는 전부 토큰 단계에서 판정 가능하다 — 본문을 다 쓴 뒤에 토큰을 갈아엎는 것보다 훨씬 싸다.

**주의 — 게이트가 있다고 1차를 대충 만들지 않는다.** "어차피 게이트가 잡는다"는 태도는 회차만 늘린다. 게이트는 놓친 것을 잡는 장치이지, 규칙을 대신 기억해주는 장치가 아니다.

아래 네 단계를 **이 순서 그대로** 통과해야 수렴이다 — 순서를 바꾸지 않는다. **1단계가 실제 완료 기준이고, 2~3단계(코드 게이트)는 1단계를 통과한 뒤에야 의미가 있다.** 구도가 틀린 화면 위에서 대비·spacing 값부터 맞추는 건 나중에 구조를 갈아엎으며 버릴 폴리싱이다.

> **왜 코드 게이트만으로는 안 되는가 — e라운드 사례**: 그 라운드 산출물은 `16 pass · 0 fail`을 받고도 화면이 망가져 있었다. 지표 타일이 1.84:1이라 안 읽히고, 섹션 밴드는 배경과 1.05:1이라 섹션 전환이 안 보이고, 액센트가 3색으로 흩어져 스타일 정체성이 없었다. **통과한 이유는 전부 "규범은 이 문서에 있는데 재는 검사가 없거나, 있는 검사가 가드에 걸려 스킵됐다"였다.** 그래서 스크립트에 대비·타입 스케일·액센트 색 수·스타일 커밋·반응형 검사를 추가했고, 소스만으로는 원리적으로 못 재는 것(레이아웃 기하·캐스케이드 이후의 실제 색)을 위해 렌더링 검증 스크립트도 넣었다 — 그런데 이 둘은 전부 **숫자로 환원되는 것만** 잰다. "카드 그리드에서 하나가 톤 안 맞게 튄다" "이 일러스트가 콘텐츠와 무관한 스톡컷이다" "여백이 중요도가 아니라 균일함만 따른다"는 원리적으로 못 잰다 — 실제로 코드 게이트를 9라운드 수렴시킨 산출물이 ①CTA 3개가 위계 없이 나열되고 ②콘텐츠와 무관한 추상 스톡 일러스트가 채워지고 ③카드 그리드 안에 단색 배너 하나가 톤 안 맞게 끼어들고 ④같은 급의 프로젝트 카드들이 서로 다른 밀도로(스크린샷+설명+한계 vs 텍스트만 vs 빈 회색 박스) 처리된 채로 "완료"로 보고된 적이 있다. 그래서 미적 판단을 코드 게이트보다 **앞에** 둔다 — 뒤에 부록으로 붙여두면 이미 만들어진 것을 정당화하는 자문자답이 된다.

**1. 미적 응집력 — 독립 검토 (필수, 자기 자신이 하면 안 된다, 코드 게이트보다 먼저)**

**이 화면을 만든 에이전트 본인이 이 단계를 수행하지 않는다.** 자기 작업은 관대하게 보인다 — 방금 만든 선택 하나하나가 그 순간엔 다 이유가 있어 보이기 때문이다. `Agent` 툴로 별도 세션을 fresh context로 띄우고, 렌더링된 화면만 보여준 뒤 아래 조건으로 적대적으로 검토하게 한다:

- 코드 정합성(대비·spacing 배수·터치 타겟 등)은 신경 쓰지 말라고 지시한다 — 그건 2~3단계가 따로 확인한다. 이 검토는 오직 "보기에 괜찮은가"만 본다
- 긍정적으로 시작하지 말고 결함부터 찾으라고 지시한다 — "좋은 점부터 말해줘"를 넣지 않는다. 검토자가 만든 사람을 배려할 이유가 없다
- 판정 축을 명시적으로 준다: **여백 우선순위**(리듬이 중요도를 반영하는가, 균일하게 뿌려져 있는가) · **밀도 일관성**(선언한 밀도를 페이지 전체가 지키는가, 섹션마다 따로 노는가) · **이미지·일러스트 관련성**(콘텐츠와 실제로 연결되는가, 자리가 비어서 채운 것인가) · **그리드·카드 응집력**(같은 행·같은 급 항목들이 한 세트로 읽히는가, 하나가 튀거나 밀도가 다른가) · **색 변별력**(이 장르에서 제일 뻔한 선택인가) · **총체적 인상**(공들여 만든 것 같은가, 템플릿에 내용만 부은 것 같은가)
- 발견한 결함은 어느 요소·어느 섹션인지 구체적으로 짚게 한다 — "더 다듬으면 좋겠다" 같은 뭉뚱그린 평가는 반려하고 재요청한다

**말로 풀어서 지시하지 말고 아래 프롬프트를 거의 그대로 `Agent` 툴에 붙여 쓴다** — 매번 다르게 풀어 쓰면 어느 순간 "좋은 점부터 말해줘"가 슬쩍 끼어들거나 판정 축이 빠진다:

```
<html 경로/URL>에 렌더링된 페이지가 있다. 이 페이지에 대한 냉정한 미적 비평만 하라 — 그 외엔 아무것도 하지 마라.

1. 필요하면 브라우저 툴로 페이지를 열고 위부터 아래까지 전체를 스크롤하며 스크린샷을 찍어라(섹션 건너뛰지 말 것).
2. 이 프로젝트에 대한 맥락도, 이 파일에 대한 애착도 없다 — 냉정한 피드백에 아무도 기분 상하지 않는다. 완화하지 말고, 긍정적인 말로 시작하지 말고, 칭찬-비판-칭찬 구조를 쓰지 마라.
3. 순수하게 시각적/미적 품질만 회의적인 시니어 디자이너처럼 판단하라:
   - 여백 우선순위 — 리듬이 실제 중요도를 반영하는가, 균일/임의적인가
   - 밀도 일관성 — 한 밀도에 커밋했는가, 섹션마다 성기고 빽빽한 게 무작위로 바뀌는가
   - 이미지·일러스트 관련성 — 콘텐츠와 실제로 연결되는가, "여기 이미지가 있어야 할 것 같아서" 채운 필러처럼 보이는가
   - 그리드·카드 응집력 — 같은 행/그리드 안 항목들이 한 세트로 느껴지는가, 하나가 형제들과 충돌하는가
   - 색 변별력 — 고심한 팔레트인가, 이런 종류의 페이지에 제일 뻔한 선택인가
   - 총체적 인상 — 사람이 공들여 만든 것 같은가, 템플릿에 내용만 부은 것 같은가
4. 코드 레벨 정합성(대비·spacing·접근성 등)은 완전히 무시하라 — 다른 검사가 이미 확인했다. 지금은 오직 "이게 진짜로 보기 좋은가"만 본다.
5. 구체적으로 — 어느 섹션·어느 요소가 문제인지 정확히 짚어라. "더 다듬으면 좋겠다" 같은 뭉뚱그린 말은 쓰지 마라.
6. 정말 좋은 게 있으면 말해도 되지만, 균형 맞추려고 칭찬을 지어내지 마라.

400단어 이내의 직접적이고 구체적인 목록으로 보고하라 — 에세이가 아니라 결함 목록이다.
```

검토자가 결함을 찾으면 **그건 선택 사항이 아니라 FAIL과 동급이다.** 고치고 다시 이 단계부터 검토받는다 — 코드 게이트로 넘어가지 않는다.

**이 단계는 텍스트 지시만으로 끝내지 않는다 — `gate.py`가 기계적으로 강제한다.** 검토 결과를 `<html 파일명>.feel-review.json`에 `{"html_sha256": "<html 파일의 sha256>", "findings": [...]}` 형태로 저장한다. `gate.py`는 이 파일이 없거나, 해시가 지금 html과 안 맞거나(=html을 고친 뒤 예전 통과 기록을 재사용하는 것), `findings`가 비어 있지 않으면 **코드 게이트(2~3단계)를 아예 돌리지 않고 여기서 멈춘다.** `findings: []`(빈 배열)이어야 2단계로 넘어간다 — 이걸로 "1단계를 건너뛰고 코드부터 손댄다"를 스크립트 레벨에서 막는다.

**이 강제는 `gate.py` 안에만 있지 않다.** `gate.py`를 거치지 않고 `verify.py`·`render_audit.py`를 직접 호출해서 1단계를 우회하는 것도 막혀 있다 — 두 스크립트가 실행 맨 앞에서 같은 `feel-review.json` 검사를 스스로 한 번 더 하고, 통과 못 하면 검사를 아예 시작하지 않고 종료한다(`verify.py`만 `--static-only`로 예외를 둔다 — 토큰·`/* plan */`만 잡는 초기 반복용).

**2. 정적 검증 스크립트 (필수, FAIL 0개까지)**

```
python3 <스킬 경로>/scripts/verify.py <생성한 HTML 경로>
```

FAIL이 하나라도 있으면 그 상태로 완료 보고하지 않는다 — 고치고 재실행한다. WARN은 스크립트가 확신 못 하는 신호이니 4단계에서 직접 눈으로 확인한다. **직접 호출해도 1단계(`feel-review.json`)가 안 끝났으면 이 스크립트 자체가 실행을 거부한다** — 위 안내를 보고 1단계부터 한다.

**3. 렌더링 검증 스크립트 (필수, FAIL 0개까지)**

```
python3 <스킬 경로>/scripts/render_audit.py <생성한 HTML 경로>
```

**이 스크립트도 직접 호출 시 1단계(`feel-review.json`)를 스스로 확인하고, 안 끝났으면 실행을 거부한다** — 예외(`--static-only`) 없음.

2단계(정적 검증)는 소스만 읽으므로 **렌더링해야만 보이는 결함은 원리적으로 못 잡는다.** 이 스크립트가 headless Chrome으로 1440/1100/768/500px에서 실제로 그린 뒤 `getBoundingClientRect`·`getComputedStyle`로 잰다 — 가로 오버플로, 한 행 자식 높이 불균형(짧은 카드가 허공에 뜨는 것), 넓은 카드의 가로 여백 낭비, 헤드라인 고아줄과 폭별 줄 수, **캐스케이드가 덮어버린 실제 텍스트 색의 대비**, 섹션 밴드 대비, 터치 타겟, 잘린 콘텐츠, 액센트 실제 면적.

특히 대비는 2단계(정적 검증)와 겹치는 게 아니다 — 소스에 `color: var(--acc-ink)`라고 옳게 적혀 있어도 `.nav-links a`(특이도 0,2,0)가 `.nav-cta`(0,1,0)를 이기면 파란 버튼에 회색 글씨가 그려진다. **f라운드에서 실제로 그랬고, 소스만 읽어서는 절대 안 보인다.**

서버 기동·측정 주입·정리는 스크립트가 알아서 한다(`file://`는 브라우저가 거부하고 경로의 콜론에서도 깨지므로 임시 HTTP 서버를 쓴다). **좁은 폭**: CLI headless는 레이아웃 뷰포트를 500px 아래로 못 내리므로, 그 아래(390px)는 대상을 **폭 390px짜리 iframe에 가둬서** 잰다 — iframe 안에서는 미디어 쿼리가 iframe 폭을 기준으로 동작한다. g라운드의 nav 오버플로와 h라운드의 `min-width:auto` 오버플로가 둘 다 이 구간에서만 나왔다.

**4. 스크린샷 확인 (필수, 코드 게이트가 못 재는 나머지)**

2~3단계를 다 통과해도 스크린샷 없이 "확인했다"고 보고하지 않는다 — Read로 소스를 읽는 것은 렌더링 확인을 대체하지 못한다. 아래 **다섯 항목**만 남았다. 기계로 잴 수 있게 된 것은 계속 게이트로 내려보낸다:

- **레이아웃이 콘텐츠 우선순위를 반영하는가**: 계획에서 정한 우선순위와 실제 섹션 배치·비중이 일치하는가 — 표준 템플릿(히어로→타임라인→통계 그리드→카드 그리드) 그대로면 콘텐츠 분석 없이 기본값에 수렴한 것이다
- **이름을 가려도 구별되는가**: 선택한 스타일 이름(`material` 등)을 지우고 봐도 기본값(무난한 회색 UI)과 구별되는가. 스크립트가 커밋 신호 0개를 FAIL로 잡지만 그건 "극단값이 코드에 있는가"까지다 — **그 극단이 화면에서 그 스타일로 읽히는지**는 스크린샷으로만 판정된다
- **화면을 채우려고 만든 요소가 있는가**: 2컬럼의 빈 쪽을 메우는 카드, 같은 문구를 다시 쓰는 배지, 셀 수를 맞추려 넣은 항목 — 콘텐츠가 아니라 레이아웃이 요구해서 생긴 블록은 지우고 레이아웃을 바꾼다. 스크립트는 이걸 못 잡는다(글자가 들어 있으면 콘텐츠로 보인다)
- **섹션끼리 다른 화면으로 읽히는가**: 섹션 경계가 제목으로만 구분되고 본문 구조가 같아 보이면 패밀리를 바꾼다 — `verify.py`는 CSS 시그니처만 보므로 클래스가 달라도 육안으로 같아 보이는 경우를 못 잡는다(`references/layout.md` "섹션 레이아웃 패밀리 반복 상한")
- **동종 항목의 상대적 무게가 읽히는가**: 성과 크기가 다른 항목이 같은 크기로 나열돼 있지 않은가 — 대표 1개가 면적·패밀리로 실제로 분리돼 보여야 한다(`references/layout.md` "동급 항목 비중 차등")

그리고 **스크립트가 신호를 띄웠을 때만** 추가로 눈으로 확인할 것 둘 — 통과했으면 여기서 자문자답하지 않는다:

- **콘텐츠 내부 강조가 실제로 있는가**: 리스트/카드/표 반복 항목이 전부 같은 색으로 '착색'만 됐는지, 그중 진짜 중요한 지표 하나는 weight·칩·크기로 구분되는지 확인한다(스크립트가 WARN을 띄우면 반드시 육안으로 재확인 — `references/color.md` "콘텐츠 내부 강조")
- **카드/컴포넌트 조합이 범용 AI 패턴이 아닌가**: 배지 칩+좌측 컬러 보더+인용 박스+스탯 타일처럼 스타일과 무관하게 반복되는 조합을 그대로 쌓지 않았는지 확인한다(`references/ui-patterns.md` 금지/필수). 스크립트가 이 조합을 FAIL로 잡지만 클래스명 관례에 의존하는 휴리스틱이라 관례를 벗어나면 못 잡는다 — 통과했어도 육안으로 한 번 더 본다

(텍스트 대비·구분선 대비·섹션 밴드 델타·액센트 색상환 갈래 수·선언한 톤과 실제 채도·스타일 커밋 신호·타입 스케일·대형 헤드라인 반응형·`<br>`과 `text-wrap:balance` 충돌·2컬럼 분량 균형·그리드 중간 행 구멍·자식 1개 `space-between`·카드 장식 과다 조합·액센트 면 사용·배경/표면 톤차·베이지류 배경 앵커링·플레이스홀더 이름·CTA 반복·폰트 로드·2px 그리드·섹션 레이아웃 패밀리 반복(연속·종수·점유율)·동종 항목 4개 이상의 균일 템플릿은 2단계가, 가로 오버플로(390px 포함)·컬럼 높이 불균형·카드 가로 여백 낭비·고아줄·폭별 헤드라인 줄 수·캐스케이드 후 실제 대비·터치 타겟·잘린 콘텐츠·액센트 실제 면적은 3단계가 기계적으로 확인한다 — 여기서 다시 자문자답하지 않는다)


## 챕터 포인터

작업 종류에 따라 해당 파일만 읽는다. 여러 조건이 겹치면 여러 파일을 함께 읽는다. 큰 두 챕터(styles·motion)는 파일 전체가 아니라 **아래 세부 경로가 가리키는 부분만** 읽는다.

- 시각 위계·여백·대비·정렬 등 배치 원칙을 판단할 때, 게슈탈트 지각 원리가 필요할 때 → `references/principles.md`
- 색·팔레트를 고르거나 시맨틱 색(성공/경고/에러/정보)을 정할 때 → `references/color.md`
- 서체를 고르거나 타입 스케일·자간·행간을 정할 때 → `references/typography.md`
- 페이지/화면 구조를 짜거나 그리드를 정할 때 → `references/layout.md`
- 내비게이션·카드·모달·폼 등 구체적 UI 컴포넌트를 고르거나 만들 때 → `references/ui-patterns.md`
- 접근성을 점검하거나 ARIA·키보드·포커스를 구현할 때 → `references/a11y.md`
- 헤드라인·CTA·라벨 등 화면에 들어갈 문구를 직접 쓰거나 감사할 때 → `references/copy.md`(필러 수식어·플레이스홀더 이름·CTA 반복·범용 섹션 라벨)
- 이미지 시안을 생성·평가하고 레퍼런스로 톤앤매너·레이아웃을 정리할 때 → `references/draft-images.md`(codex exec 커맨드·프롬프트 6블록·평가 5축·시안의 지위 3원칙)
- 디자인 토큰을 신설·정리하거나 흩어진 값을 통합할 때 → `references/design-system.md`
- 스타일 방향을 정하거나("미니멀하게", "브루탈리즘으로") 기존 화면의 스타일을 식별·분석할 때 → `references/styles.md`(29종 인덱스: 태그라인+DNA 8축). **인덱스에서 후보를 1~3개 추린 뒤 그 후보의 카테고리 파일만** 읽는다 → `references/styles/{modern,brutal,effect,art,emotion,contemporary}.md`(사례 URL·계보·관찰 포인트). 2020년대 SaaS·에디토리얼·벤토 관용구가 필요하면 `contemporary.md`(조합 프리셋 3종 — 결정적 동작 포함)
- **모든 작업**(계획 6번에서 `없음`이 아닌 값을 적었다면), 그리고 기존 모션을 감사(슬롭 여부 판정)할 때 → `references/motion.md`. 전체를 읽지 말고 파일 상단 "작업별 진입점" 표에서 해당 절만 고른다:
  - 모션을 뭘 넣을지 모르겠다 / 마케팅 페이지에 모션이 없다 → §2.6 바닥선 → §7 카탈로그
  - 복붙 가능한 완성 코드가 필요 → §7.0 공통 토큰 + §7.1(히어로 entrance)/§7.2(카드→상세)/§7.3(아코디언·탭)/§7.4(스크롤 signature)
  - 개별 요소의 duration·easing 값만 필요 → §3.1–3.4
  - 특정 패턴(fade/slide/scale/collapse/stagger/morph/press/scroll-reveal/parallax) 구현 → §4의 해당 항목 + §3.3
  - 페이지의 signature motion 설계 → §5.3–5.4
  - 기존 모션 슬롭 감사 → §5.1–5.2 + §6.4–6.5
  - 접근성·성능 게이트만 점검 → §6.1–6.3
