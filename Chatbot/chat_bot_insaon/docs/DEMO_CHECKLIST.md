# 인사ON 대시보드 확인 가이드

## 1. 실행

macOS에서는 프로젝트 폴더의 `OPEN_DASHBOARD.html`을 열고 **대시보드 열기**를 한 번
누른다. 런처가 Ollama와 qwen3·bge-m3를 확인해 필요하면 loopback으로 시작하고, local
profile 인사ON 서버가 이미 있으면 재사용한다. 없으면 8000~8009 중 빈 포트에서
백그라운드로 시작한다. offline 서버는 local 모델로 재사용하지 않는다.

새로 복사한 macOS 환경에서 버튼이 처음 한 번 반응하지 않으면 같은 폴더의
`InsaON Launcher.app`을 한 번 연다. macOS에 `insaon://` handler를 등록하는 최초 1회
절차이며, 이후에는 HTML 버튼만 사용한다. `OPEN_DASHBOARD.command`도 같은 등록을
수행하는 예비 진입점이다.

터미널에서는 다음 명령을 사용한다.

```bash
cd <저장소 루트>
.venv/bin/python scripts/preview_dashboard.py --profile offline
```

기본 실행 profile은 `offline`이다. 모델 설치 없이 즉시 뜬다. 실제 모델 재현은
`--profile local`이며 Ollama와 약 3.7GB 모델이 필요하다. 기본
브라우저에서 `http://127.0.0.1:8000/` 또는 선택된 다음 포트가 열린다. 종료는 실행한 터미널에서
`Ctrl+C`다.

`src/insaon/web/templates/review.html`을 직접 열어도 같은 원클릭 실행 화면만 표시된다.
실제 제품 확인 대상은 런처가 연 `http://127.0.0.1:{선택 포트}/` 화면이다.

## 2. 3분 합격 기준

| 순서 | 화면 | 직접 할 일 | 반드시 보여야 하는 것 | 보이면 실패 |
|---:|---|---|---|---|
| 1 | `/` | 첫 화면과 질문 입력창 확인 | 휴직·복직 범위, 중앙 질문 입력, 개인정보 금지, 지원 예시 3개 | 내부 품질·모델·RAG 용어 또는 범위 밖 예시가 먼저 보임 |
| 2 | `/demo/CASE-A` | 누락 조건 chip 선택 | `REVIEW_REQUIRED`, 누락 조건, 같은 세션 후속 입력 | 조건 없이 가능·불가능 결론 생성 |
| 3 | `/demo/CASE-B` | 채팅 답변과 근거 패널 확인 | 사용자 문장, 과거 기준일 근거, claim별 citation, 원문 발췌 | 모델 ID·내부 상태 코드, 기준일과 무관한 citation |
| 4 | `/demo/CASE-C` | 보류 이유 확인 | `INSUFFICIENT_EVIDENCE`, 범위 밖, 기관 규정 미확인 | 지원 범위를 최종 판단처럼 단정 |
| 5 | `/` | `2026년 8월 1일 기준 승진 규정을 찾아주세요` 입력 | `INSUFFICIENT_EVIDENCE`, 인용 0건, 휴직·복직 지원 범위 안내 | 넓은 인사규정 검색이나 승진 판단 제공 |

`ANSWERABLE`이더라도 처분 승인이나 법률적 확정을 뜻하지 않는다. 현재 공식 candidate는
사람 승인 전이므로 CASE-B의 내부 안전 상태는 `REVIEW_REQUIRED`가 맞지만 검토 결과와
근거는 화면에 명확히 제공해야 한다. 위 다섯 화면이
모두 맞아야 데모 계약을 통과한 것으로 본다.

## 3. 화면별 상세 확인

### 기본 화면 `/`

- 중앙 질문 입력이 가장 먼저 보여야 한다.
- 개인정보 금지는 입력창 아래 한 번만 보여야 한다.
- 육아휴직·복직, 질병휴직·복직, 가족돌봄휴직 예시만 보여야 한다.

### CASE-A `/demo/CASE-A`

- 상태가 `추가 검토 필요`여야 한다.
- `leave_type`, `reference_date` 같은 누락 조건이 보여야 한다.
- 가능·불가능 결론이나 인용 근거를 꾸며내면 안 된다.

### CASE-B `/demo/CASE-B`

- 채팅 본문은 결론→근거 요약→관련 근거 링크 순서여야 하며 모델 ID·내부 상태 코드는 숨긴다.
- offline `/demo/CASE-B`는 `예시 규정 자료`로 명확히 표시해야 한다. local profile에서 같은
  2024-01-01 질병휴직 질문을 보냈을 때는 당시 유효한 공식 조문만 연결하고 합성 source는
  0건이어야 한다.
- 근거 패널에는 자료명·조문·효력기간·원문 링크·발췌가 보여야 한다.
- 공무상 질병휴직에만 적용되는 3년+2년 예외를 비공무상 조건에 적용하면 안 된다.
- candidate 승인 전에는 모델이 `ANSWERABLE`을 권고해도 최종 제품 상태가 `REVIEW_REQUIRED`여야 한다.

### CASE-C `/demo/CASE-C`

- 상태가 `근거 부족·답변 보류`여야 한다.
- 지원 범위 밖과 기관 규정 확인 필요를 표시해야 한다.
- 근거가 없는데 조문 링크를 표시하면 안 된다.

## 4. 후속 대화

CASE-A에서 누락 조건 chip을 누르고 자연어 조건을 추가한다.

```text
질병휴직이고 기준일은 2024-01-01입니다.
```

- 페이지 이동 없이 같은 session ID가 유지되어야 한다.
- 확인된 조건과 남은 누락 조건이 갱신되어야 한다.
- 필요한 조건이 아직 남아 있으면 계속 `REVIEW_REQUIRED`여야 한다.

## 5. 화면 품질 확인

1280px 이상에서는 채팅과 오른쪽 근거·유의사항 rail이 구분되어야 한다. 1200px 이하에서는
채팅 입력창이 화면 안에 유지되고 근거는 대화 다음 흐름에 둔다. 760px 이하에서는 근거를
기본 숨기고 `근거와 유의사항 보기`를 눌렀을 때만 표시한다.

- 본문과 상태 설명을 확대 없이 읽을 수 있어야 한다.
- 중앙 질문·대화가 첫 번째 시선 대상이어야 한다.
- 가로 스크롤 없이 질문 입력과 A/B/C 탐색이 가능해야 한다.
- 키보드 `Tab`으로 질문 입력, 보내기, 근거 링크에 접근할 수 있어야 한다.
- 장식보다 상태·누락 조건·기준일·근거가 더 선명해야 한다.
- 390·768·1024·1280·1440·1680px에서 가로 overflow가 없어야 한다.

## 6. 확인하지 않아도 되는 것

- `report/planning-report.html`은 제품 화면이 아니라 16:9 기획 보고서다.
- `OPEN_DASHBOARD.html`은 실행 진입점이고, 실제 챗봇은 런처가 연 로컬 서버 화면이다.
- CASE-A/C는 합성 계약 seed이고 CASE-B local 경로는 비제출 공식 candidate를 사용한다.
  어느 쪽도 법률 정확도나 실제 행정처분 결과로 확대 해석하지 않는다.
