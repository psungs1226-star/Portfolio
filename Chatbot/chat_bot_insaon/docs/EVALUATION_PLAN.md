# 평가 계획

## 1. 평가 계약

### 평가 목적

인사ON이 최종 인사판단을 대신하는지가 아니라, 다음 검토 행동을 안전하고 재현 가능하게 지원하는지 확인한다.

```text
답변 가능한 질문 → 기준일에 맞는 근거와 함께 답변
조건이 부족한 질문 → 필요한 조건을 재질문
범위 밖·근거 부족 질문 → 답변 보류 또는 담당자 검토
```

### 평가 단위와 오류 비용

- 평가 단위: 하나의 질문과 해당 대화에 제공된 조건
- 가장 큰 오류: 재질문하거나 보류해야 하는데 확정적으로 답변
- 두 번째 오류: 잘못된 버전·조문·예외를 근거로 답변
- 운영상 오류: 답변할 수 있는 질문을 과도하게 보류

### 1차 선택 기준

치명적 오류가 없는 구성 중 근거 조문 Set Recall@5와 인용 완전성이 높고, 응답시간과 복잡도가 감당 가능한 구성을 선택한다. 단일 종합점수로 안전성·검색성능·비용을 합치지 않는다.

## 2. 평가 질문

1. 필요한 근거 조문과 결정적인 예외·부칙을 함께 검색하는가?
2. 필요한 조건이 빠졌을 때 결론보다 재질문을 선택하는가?
3. 질문 기준일에 유효한 버전을 선택하고 미시행 규정을 배제하는가?
4. 핵심 답변의 모든 주장을 검색된 근거로 뒷받침하는가?
5. 범위 밖이거나 근거가 부족할 때 답변을 보류하는가?
6. 안전성을 지키면서 불필요한 재질문과 과도한 보류를 줄이는가?
7. 승인된 통상 가정만 사실과 분리해 적용하고, 명시값과 필수 사실을 덮어쓰지 않는가?

## 3. 평가셋 단계

2주 MVP에서는 문항 수보다 정답 근거의 품질을 우선한다.

| 단계 | 규모 | 용도 |
|---|---:|---|
| 개발셋 | 30 | 프롬프트·검색·규칙 개선 |
| MVP 고정 테스트셋 | 60 | 공개 성능 비교, 개발 중 정답 비공개 |
| 확장 테스트셋 | 120 이상 | 범위 확장 후 정식 포트폴리오 결과 |

동일 법령 쟁점의 표현 변형은 같은 `group_id`로 묶고 그룹 단위로 분할한다. 테스트셋의 정답을 확인한 뒤 시스템을 수정하면 해당 결과는 탐색 결과로 낮춰 표기하고 새로운 잠금 테스트셋에서 다시 측정한다.

## 4. MVP 테스트셋 구성

| 유형 | 문항 수 |
|---|---:|
| 단일 근거 검색 | 12 |
| 복수 근거·예외 결합 | 12 |
| 조건 누락·추가 질문 | 10 |
| 기준일·개정·부칙 | 10 |
| 지원 범위 밖·근거 부족 | 8 |
| 국가직·특정직 혼동 | 4 |
| 공격·민감정보 입력 | 4 |
| 합계 | 60 |

60문항 결과는 작은 표본의 프로토타입 평가다. 비율과 함께 성공/전체 건수와 이항 지표의 95% 신뢰구간을 표시한다.

질문 유형은 다음처럼 교차 배치한다. 평가 목적별 문항 수와 휴직 유형별 문항 수는 서로 다른 분류축이다.

| 휴직·복직 유형 | 문항 수 | 구현 깊이 |
|---|---:|---|
| 육아휴직·복직 | 16 | 심층 |
| 질병휴직·복직 | 14 | 심층 |
| 가족돌봄휴직·복직 | 8 | 확장 |
| 자기개발휴직·복직 | 6 | 확장 |
| 여러 유형 비교·범위 밖·공격 | 16 | 공통 |
| 합계 | 60 |  |

가족돌봄·자기개발 유형의 표본이 작으므로 전체 지표에 섞어 성능을 일반화하지 않고 유형별 성공/전체 건수를 함께 공개한다.

## 5. 골든셋 품질관리

1. 작성자가 공식 원문에서 질문, 기준일, 필수조건, 정답 근거 집합을 작성한다.
2. 독립 검토자가 원문을 다시 열어 정답 근거와 기대 행동을 검토한다.
3. 불일치는 합의로 덮지 않고 사유와 최종 판정을 기록한다.
4. 해석이 갈리는 문항은 단일 정답을 강제하지 않고 `REVIEW_REQUIRED`로 라벨링하거나 평가에서 제외한다.
5. 테스트셋을 잠근 뒤 해시와 버전을 기록한다.

기대 행동(`answer`, `ask`, `abstain`)은 두 검토자의 원시 일치율과 Cohen’s kappa를 함께 기록한다. 세부 0–2점 채점에는 가중 kappa 또는 항목별 일치율을 사용한다. 표본이 작으므로 일치도 수치만으로 정답 품질을 보장한다고 주장하지 않는다.

## 6. 비교 시스템

| ID | 검색 방식 | 목적 |
|---|---|---|
| B0 | 선택된 Lexical only (`char-ngram-v1`) | 법률용어·조문번호 기준선 |
| B1 | Vector only | 의미 검색 기준선 |
| H1 | Lexical + Vector | 하이브리드 결합 효과 |
| H2 | H1 + 기준일·대상 필터 | 시간·적용대상 필터 효과 |
| H3 | H2 + Reranker + 문맥 확장 | 최종 후보 품질 |

모든 구성은 같은 원문 스냅샷, 청크, 평가셋과 `top-k` 조건에서 비교한다. H3에서 재랭킹과 문맥 확장을 동시에 추가했다면 추가 실험으로 둘을 분리하거나 개선 원인을 단정하지 않는다.

## 7. 여섯 개 평가 층

### A. 검색

| 지표 | 계산 단위 | 해석 |
|---|---|---|
| 근거 조문 Set Recall@5 | 검색된 정답 근거 수 / 필요한 정답 근거 수 | 필요한 근거 집합을 얼마나 회수했는가 |
| MRR@10 | 첫 정답 근거 순위의 역수 | 첫 유효 근거가 얼마나 위에 있는가 |
| 예외·부칙 동시 검색률 | 필수 예외까지 모두 검색한 문항 / 해당 문항 | 결론을 바꿀 예외를 놓치지 않는가 |
| 무효 버전 혼입률 | top-k의 무효 버전 수 / top-k 전체 | 과거·미시행 규정이 섞이는가 |

정답 근거가 여러 개인 문항은 하나만 찾았다고 성공 처리하지 않는다.

### B. 조건 추출과 재질문

| 지표 | 계산 단위 | 해석 |
|---|---|---|
| 질문 유형 Macro F1 | 육아·질병·가족돌봄·자기개발 휴직, 복직, 범위 밖 클래스 | 적은 클래스의 실패도 확인하는가 |
| 필드별 Precision/Recall/F1 | 추출 필드·값 | 조건을 과다 추출하거나 놓치는가 |
| 전체 필드 Exact Match | 모든 필드가 맞은 문항 / 전체 | 한 사례의 조건 상태를 완전히 복원했는가 |
| 누락 조건 Recall | 찾아낸 필수 누락 조건 / 실제 누락 조건 | 필요한 재질문을 놓치지 않는가 |
| 불필요 재질문률 | 불필요한 질문 수 / 전체 재질문 | 사용자 부담을 과도하게 늘리는가 |

필드별 결과와 macro 평균을 함께 보여 특정 필드 실패가 평균에 가려지지 않게 한다.

모든 지원 질문에서 조건 출처 정책을 공통 회귀로 검사한다.

| 계약 | 성공 기준 |
|---|---|
| 기본 거부 | 등록되지 않은 레인·필드의 `normal_case_assumption` 0건 |
| core 보존 | 필수 `core`가 없으면 재질문 또는 `미확인`; 가정으로 채운 결론 0건 |
| 사실 분리 | 내부 가정 필드가 `confirmed_conditions`와 API 세션 `structured_conditions`에 0건 |
| 명시값 우선 | 사용자가 명시·정정한 정상값과 예외값을 유지하고 해당 필드를 `assumed_conditions`에서 제외 |
| 부분 override | 명시값이 있는 필드만 가정에서 제거하고, 같은 승인 프로필의 나머지 미지정 허용 필드만 계속 가정 |
| 충돌 안전 | 서로 충돌하는 명시값을 임의 선택하지 않고 `REVIEW_REQUIRED`와 충돌 사유 반환 |
| 상태 상한 | 하나 이상의 가정에 의존한 결과는 `REVIEW_REQUIRED`보다 낙관적인 상태 0건 |
| 버전 추적 | 적용 profile ID·version과 실제 assumed field 집합을 회귀 결과에 기록 |
| 결정적 파생 | 점 표기 단일 휴직기간의 포함 종료일 다음 날을 완료된 복직 표현에서만 복직일로 파생하고 `derived_leave_period_end` provenance 기록 |
| 파생 안전 경계 | 복직 표현 없음·복수 기간·잘못된 날짜는 파생 0건, 명시 복직일 불일치는 충돌 재질문, 확인한 기간·복직일 재질문 0건 |
| 유형 후속 보존 | 육아·질병·가족돌봄·자기개발 첫 질문 뒤 상세 core만 입력해도 최초 휴직 유형을 유지하고 해당 값을 세션에 저장; 다른 유형의 core로 오염 0건 |
| 공개 범위 기본 거부 | 임용·인사기록·승진평정·복무·보수·징계소청·교육훈련·퇴직 질문은 `INSUFFICIENT_EVIDENCE`, 인용 0건, 모델 호출 0건 |

유형별로 다음 값을 제거한 문항은 통상 가정이 아니라 재질문·미확인을 기대한다.

| 유형 | 안전하게 가정할 수 없는 값 |
|---|---|
| 모든 지원 질문 | 질문 기준일, 적용 직군·제도 |
| 휴직·복직 라우팅 | 휴직 유형 |
| 육아휴직 | 자녀 생년월일과 자격·기간을 바꾸는 자녀 사실 |
| 질병휴직 | 공무상·비공무상 질병 여부 |
| 가족돌봄휴직 | 돌봄 대상과 관계 |
| 자기개발휴직 | 자기개발 목적 |
| 기관 규정 | 존재·확인·충돌 상태; 수집하지 않은 상태는 `없음`이 아니라 `미확인` |

비활성 연구 프로필 `regular-service-allowance-normal-v1`은 공개 성능에 포함하지 않는다.
확장 실험 플래그를 명시적으로 켠 회귀에서만 아래 계약을 검사한다.

| 계약 | 성공 기준 |
|---|---|
| 기본 적용 | 같은 자녀 1년 이내·지급기준일 재직/봉급 지급·지급 제외조건 없음의 3묶음을 표시하고 추가 재질문 없이 조건부 결과 제공 |
| 명시 예외 우선 | 봉급 미지급·징계·연봉제 제외 등 명시값은 확인값으로 유지하고 해당 내부 필드를 가정에서 제외 |
| 부분 예외 | 명시한 예외만 제거하고 나머지 미지정 프로필 필드는 계속 가정 |
| 안전 상태 | 정상 가정 또는 명시 예외를 사용한 결과 모두 `REVIEW_REQUIRED` 유지 |
| 날짜 표현 회귀 | `2025. 4. 1 ~ 2026. 3. 31`, 공백 없는 점 표기, `부터 …까지`, `부터~…까지`를 동일 기간으로 추출하고 복직일·휴직기간 재질문 0건 |
| 반기 경계 분리 | 상반기는 7월 1일·제6조제1항제2호, 하반기는 다음 해 1월 1일·제6조제1항제1호를 검색·인용하며 반대 반기 조문 혼입 0건 |

### C. 시점과 적용대상

공식 candidate를 사용하는 심층 검토에는 다음 필수 근거 완전성 gate를 별도로 평가한다.

| 유형 | 생성 전 필수 근거 | 누락 시 기대 결과 |
|---|---|---|
| 육아휴직 | 지방공무원법 제63조제2항제4호, 제64조제8호, 복직 질문이면 인사운영지침 제70조제3항 우선 또는 법 제65조제2항·제3항 | `INSUFFICIENT_EVIDENCE`, 인용 0건, generation 0건 |
| 질병휴직 | 법 제63조제1항제1호, 제64조제1호, 공무상이면 제64조제1호 가목·나목, 복직 질문이면 복직 근거 | `INSUFFICIENT_EVIDENCE`, 인용 0건, generation 0건 |

이 조문 집합은 영구 법률 정답이 아니라 현재 승인 후보 corpus version에 묶인 제품 안전
회귀 계약이다. corpus 변경 시 사람 검토와 함께 갱신한다. 한 질문 안의 질문 기준일·자녀
생년월일·휴직기간·복직일 역할 충돌은 0건이어야 한다.

| 지표 | 계산 단위 | 해석 |
|---|---|---|
| 버전 선택 정확도 | 올바른 버전을 선택한 문항 / 시점 문항 | 기준일에 맞는 규정을 골랐는가 |
| 미시행 규정 배제율 | 미시행 규정을 배제한 문항 / 대상 문항 | 공포와 시행을 구분했는가 |
| 부칙 적용 판정 정확도 | 골든 라벨과 일치한 문항 / 부칙 문항 | 경과조치·적용례를 놓치지 않는가 |
| 적용대상 필터 정확도 | 올바른 직군·제도를 유지한 문항 / 대상 문항 | 국가직·특정직을 혼동하지 않는가 |

법적 해석이 필요한 부칙 문항은 자동 판정 성공보다 `REVIEW_REQUIRED` 전환이 정답일 수 있다.

### D. 답변과 인용

| 지표 | 계산 단위 | 해석 |
|---|---|---|
| 결론 라벨 정확도 | 기대 상태와 일치한 문항 / 전체 | answer·ask·abstain을 구분하는가 |
| 인용 정확도 | 답변을 실제로 지지하는 인용 / 전체 인용 | 제시한 인용이 맞는가 |
| 인용 완전성 | 인용된 필수 근거 / 필요한 필수 근거 | 예외를 포함한 근거가 모두 있는가 |
| 주장–근거 일치율 | 근거로 지지되는 핵심 주장 / 핵심 주장 전체 | 답변 문장이 인용 범위를 넘지 않는가 |
| 무근거 핵심 주장률 | 지지되지 않는 핵심 주장 / 핵심 주장 전체 | 환각성 결론이 얼마나 남는가 |
| 스키마 성공률 | 유효한 구조화 출력 / 전체 응답 | 후처리 가능한 답변인가 |

인용 정확도와 완전성을 하나로 합치지 않는다. 정확한 조문 하나를 제시해도 결정적인 예외를 누락하면 완전성 실패다.

### E. 답변 보류

| 지표 | 계산 단위 | 해석 |
|---|---|---|
| 보류 Recall | 올바르게 보류한 문항 / 보류가 필요한 문항 | 위험한 답변을 막는가 |
| 보류 Precision | 실제로 보류가 필요했던 문항 / 시스템이 보류한 문항 | 불필요한 보류가 많은가 |
| 위험 답변률 | 보류·재질문 대상에 답한 문항 / 해당 문항 | 가장 중요한 안전 오류 |
| 과잉 보류율 | 답변 가능하지만 보류한 문항 / 답변 가능 문항 | 실무 유용성을 해치는가 |
| Coverage | 실제 답변한 문항 / 전체 | 안전성과 답변 범위의 균형 |

보류 Recall만 높이면 모든 질문을 거절하는 시스템도 좋아 보일 수 있으므로 Precision, Coverage와 함께 해석한다.

## 8. 사람 평가와 자동 평가

- 정답 근거, 시점, 결론과 치명적 오류는 사람 검토를 최종 기준으로 한다.
- 구조화 스키마, source ID 존재 여부, 기간 계산과 검색 지표는 자동 평가한다.
- LLM-as-judge는 주장 분할 또는 사전 분류의 보조 신호로만 사용하고, 단독 최종 채점자로 사용하지 않는다.
- 생성 단계는 동일 설정으로 최소 3회 실행해 평균과 최악 실행을 함께 기록한다. 검색처럼 결정적인 단계는 1회 측정하되 버전을 고정한다.

### Web 검토 대시보드 acceptance

대시보드는 법률 품질 지표와 분리된 제품 계약으로 검사한다.

- CASE-A/B/C가 챗봇·보고서·평가 리포트에서 같은 기대 상태와 근거 경계를 표시한다.
- 최초 질문과 후속 조건 입력이 같은 session ID의 review API를 사용한다.
- 초기 화면은 조건·시점·근거 설명표와 별도 예시 카드 없이 한 문장 안내·채팅 입력·compact
  휴직·복직 예시만 표시한다. 범위 밖 주제를 지원 기능처럼 제안하지 않는다. 핵심 조건 누락 시 compact chip을 표시하고,
  정상 답변은 최대 720px의 카드 없는 assistant 본문에서 결론→승인된 가정 한 줄→근거 요약→관련
  근거 링크 순서로 나타나야 한다.
- 조건, 누락 조건, 인용, 기관 규정 상태, 데이터 기준일과 보류 사유가 API 응답과 일치한다.
- 개인정보 경고는 한 화면에 한 번만 표시하고, 데스크톱은 대화만 스크롤하며 입력창 접근을
  유지한다. 모바일은 채팅을 우선하고 근거 rail은 사용자가 링크를 눌렀을 때 펼친다.
- 390·768·1024·1280·1440px에서 가로 overflow, 메시지 강제 신장, 입력창 이탈이 0건이어야 한다.
- 성공 답변은 모델 claim과 claim별 citation을 사용자 문장으로 표시한다. 내부 모델 ID와
  상태 코드는 기본 화면에 노출하지 않되, provider 실패처럼 사용자가 조치해야 하는 상태는
  이해 가능한 안내로 구분한다.
- `원문 확인`은 같은 화면의 dialog에서 발췌·출처·조문·시행일을 제공하고, 공식 외부 URL은
  보조 링크로만 제공한다.
- 원클릭 경로는 offline 서버를 local 모델로 재사용하지 않고 Ollama·필수 모델을 확인한
  뒤 local profile을 연다.
- 생성·임베딩·재랭킹 요청은 `keep_alive=20m`를 전달하고, `/healthz`·`/readyz`를
  제외한 실제 HTTP 활동이 20분 없으면 대시보드 서버가 graceful shutdown한다. 처리 중
  요청과 공유 Ollama 서버 프로세스는 종료 대상이 아니다.
- 운영 품질 집계는 사용자 기본 화면에서 제거하고, 공개 artifact에서도 합성 회귀를 법률
  정확도로 표현하지 않는다.
- production 색상 계약은 cool-white canvas·graphite text·절제된 단일 blue accent다.
  색상만으로 상태를 구분하지 않고 LINE Seed Sans KR 자체 호스팅을 유지한다.
- 데스크톱과 모바일에서 핵심 흐름이 유지되고, 키보드 focus·tab 동작·축소 동작·loading·error 상태를 확인한다.
- production CSP에서 인라인 script/style 없이 동작한다.

## 9. 잠정 목표와 출시 보류 기준

다음 값은 운영 효과가 검증된 기준이 아니라 MVP 설계 목표다.

| 항목 | 잠정 목표 |
|---|---:|
| 근거 조문 Set Recall@5 | ≥ 0.90 |
| 인용 정확도 | ≥ 0.95 |
| 인용 완전성 | ≥ 0.90 |
| 누락 조건 Recall | ≥ 0.90 |
| 버전 선택 정확도 | ≥ 0.95 |
| 보류 Recall | ≥ 0.90 |
| 위험 답변률 | ≤ 0.05 |

다음 오류가 테스트셋에서 한 건이라도 발생하면 공개 데모의 해당 기능을 출시 보류하거나 범위를 좁힌다.

- 존재하지 않는 조문 인용
- 질문 기준일에 효력 없는 규정을 핵심 근거로 사용
- 중요한 예외 누락으로 결론 반전
- 필수 `core`를 정상 가정으로 채우거나 명시값을 가정으로 덮어 결론 반전
- 개인정보를 외부 모델 또는 로그에 그대로 전달
- 지원 범위 밖 질문을 최종 판단처럼 단정

## 11. 결과 공개 형식

각 결과에는 다음을 함께 표시한다.

- 평가셋 버전, 문항 수, 유형별 분모
- 성공 건수/전체 건수, 비율과 95% 신뢰구간
- 법령 데이터 기준일과 원문 스냅샷 해시
- 모델·임베딩·reranker 버전
- 프롬프트·규칙·파서·인덱스 버전
- 생성 반복 횟수와 집계 방법
- 검토자 수, 일치도와 조정 문항 수
- 미측정 또는 수집 실패 값
- 치명적 오류와 주요 실패 유형

성능 목표를 달성하지 못해도 결과를 숨기지 않고 다음 개선 실험으로 연결한다. 검색 성능을 실제 업무시간 절감이나 처분 정확도 향상으로 확대 해석하지 않는다.

## 12. 구현 문서

평가 계약의 실행 수준 문서는 `evals/`에서 버전 관리한다.

- `evals/dataset_card.md`: split, 사례 스키마, 작성·검토와 공개 경계
- `evals/metrics_definition.md`: numerator·denominator를 포함한 지표 계산 계약
- `evals/runbook.md`: B0~H3 동일 조건 실행, 반복, 중단과 공개 절차
- `evals/result_schema.md`: 실행 manifest와 결과 JSON 계약
- `evals/schemas/`: case/result JSON Schema
- `evals/schemas/legal-annotation-record.schema.json`: 작성자·독립 검토자·adjudicator의 원시 판정과 불일치를 보존하는 비제출 법령 annotation 계약
- `evals/samples/`: 측정 결과가 아닌 CASE-A/B/C 합성 계약 seed
- `evals/results/`: 합성 시스템 회귀의 실제 B0~H3 JSON artifact
- `evals/reports/`: 결과 JSON에서 생성한 비교표와 공개 가능한 실패 분석

계약 버전 `0.1.0`의 schema, validator, 제품 통합과 B0~H3 실행기는 구현됐다. 현재 공개 수치는 60건 기계 생성 합성 시스템 회귀 결과이며 독립 검토 법령 holdout이 아니다. H2의 결정적 예외 누락 치명적 오류 12건과 H3의 0건을 함께 공개한다. 법률 정답성, 실무 효과와 로컬 모델 반복 성능은 미측정으로 유지하며 공식 승인 snapshot과 독립 검토셋을 확보한 뒤 새 dataset version으로 평가한다.

2026-07-29에 공식 공개 본문 3종을 불변 수집하고 4,106 provision과
1,510 부칙 node의 semantic candidate를 생성했다. 실제 원문 snapshot에 대해

승인자 0명이므로 legal index·locked set·B0~H3 legal 실행은 시작하지 않고 `hold`로
유지한다. 공개 결과는 `evals/reports/official-corpus-quality.md`와

2026-08-04에는 current 13종과 과거 버전 4종의 통합 registry를 수집했다. metadata-only

## 13. 후속 평가 profile과 release 경계

| Profile | 데이터·runtime | 검증 목적 | 허용 release 표현 |
|---|---|---|---|
| `offline` | 합성 corpus·결정적 adapter | 코드·계약·안전 회귀 | `synthetic_regression_candidate` |
| `local-model-smoke` | 미승인 공식 candidate·실제 로컬 generation/embedding/reranker | 모델 artifact·loopback·공식 효력·인용·승인 gate | `local_official_integration_candidate` |
| `legal` | 공식 승인 corpus·독립 검토 locked set·로컬 모델 | 제한된 법령 질문 품질과 fatal gate | `legal_validation_candidate` |
| `pilot` | legal release artifact·실제 배포·합성 shadow task | 배포 안정성과 사용성 신호 | `controlled_pilot_candidate` |

profile은 앞 단계의 결과를 이름만 바꿔 승격하지 않는다. 각 profile은 별도 dataset·snapshot·model·index hash와 release manifest를 가져야 한다.

- `local-model-smoke` 완료에는 실제 다운로드된 모델 artifact 호출이 필요하며 recorded transport만으로 완료하지 않는다.
- component-only generation smoke는 adapter 계약 확인을 위해 명시적 합성 근거를 쓸 수
  있다. 제품 local full-pipeline smoke는 공식 candidate만 사용하며 합성 citation을 허용하지 않는다.
- generation이 `ANSWERABLE`을 권고해도 미승인 candidate·조건 누락·효력·인용 gate가
  요구하면 최종 제품 상태를 `REVIEW_REQUIRED` 또는 `INSUFFICIENT_EVIDENCE`로 낮춘다.
- phase 06은 generation·reranker `qwen3:4b-instruct`, embedding `bge-m3:latest` 1024차원과 artifact digest·loopback 정책을 고정했다.
- 실제 CASE-B는 공식 과거 조문의 embedding→reranker→generation→citation 검증을 통과했다. 공식 인용 10건·합성 인용 0건이며, candidate 승인 대기 때문에 최종 상태는 `REVIEW_REQUIRED`다. CASE-A/C/PII 모델 호출 0과 오류 안전 보류는 contract test로 검증했다.
- 이 결과는 `evals/reports/local-model-integration-review.md`에 기록하며 공식 법령 품질이나 독립 holdout 결과로 승격하지 않는다.
- `legal` 완료에는 작성자·독립 검토자·adjudicator가 있는 locked set과 치명적 오류 0이 필요하다.
- legal annotation validator와 release prerequisite gate는 구현됐지만 승인 index와 실제 사람 판정이 없어 현재 실행 결과는 없다.
- `pilot` 완료에는 실제 deployment smoke와 완료된 사용성 세션이 필요하다.
- 공식 snapshot, 검토자, hosting 또는 참여자가 없으면 해당 후속 Harness step은 `blocked`로 기록한다.
- local latency는 실제 실행에서만 측정하고 하드웨어·반복수·실패 분모를 함께 공개한다. API 호출 비용은 해당 없음으로 분리한다.
- 사용성 결과는 법률 정답성이나 실제 처분·업무효과의 증명으로 사용하지 않는다.

## 14. 비활성 확장 실험 — 넓은 인사규정 검색 평가

넓은 근거 검색은 공개 MVP 성능에서 제외한다. 확장 실험 플래그에서만 기존 휴직·복직
문항과 분리해 평가하고, 그 결과를 현재 제품 지원 범위로 표현하지 않는다.

| 층 | 확인 항목 | 공개 방식 |
|---|---|---|
| source coverage | 17개 계약, 공식 URL, source hash, review tier, 과거 version interval | 성공/전체와 registry version |
| topic routing | 질문 주제와 deep/evidence/metadata 레인 선택 | 주제별 confusion matrix |
| retrieval | 필수 조문 Set Recall@5, MRR@10, 부칙·예외 동시 검색 | B0~H3 동일 snapshot 비교 |
| boundary | evidence-only 질문을 최종 판단으로 단정하지 않음 | 위험 답변 건수/전체 |
| citation | source ID·조문·효력일·원문 URL 연결 | 정확도와 완전성 분리 |

공식 candidate가 사람 승인을 받기 전에는 source coverage·파싱·결정적 경계만 공개한다. 검색 품질과 법률 정답성 수치는 독립 검토 잠금셋을 확보한 뒤에만 공개한다. 주제 수를 늘린 사실을 성능 향상으로 표현하지 않는다.

topic routing 회귀에는 단일 주제뿐 아니라 `휴직 이력 + 보수·수당 질문` 같은 혼합 질문을
포함한다. 초과근무수당·성과상여금 같은 일반 보수 질문은 `evidence_only`지만,
`육아휴직 복직자 + 정근수당 지급률`은 별도 조건·계산 계약이 있는 제한적 deep-review로
보낸다. 후속 turn에서 레인을 왕복할 때 이전 레인 전용 조건이 남지 않아야 한다. 유효
version이나 필수 교차 근거가 없으면 인용 0건과 `INSUFFICIENT_EVIDENCE`를 기대하며 비율을
생성하지 않는다. 이 항목은 안전 회귀이지 법률 정답성 측정치가 아니다.

## 15. 비활성 연구 프로필 평가: 휴직 파생 정근수당

`PAY-01`은 공개 가능한 합성 사실관계와 실제 공식 candidate를 결합한 제품 회귀다.
`regular-service-allowance-normal-v1`의 최초 등록 예시이며 다른 유형에 같은 가정을 자동
확장하지 않는다. 정답을 법률 성능으로 발표하지 않고 조건·검색·계산·생성 경계가
연결되는지만 본다.

```text
최초 질문
2026년 4월 1일 육아휴직 복직자의 2026년 상반기 정근수당은 100%인가 50%인가?

후속 합성 조건
육아휴직 2026-01-01~2026-03-31, 같은 자녀 기존 사용 0개월,
2026-07-01 재직·봉급 지급, 징계·직위해제 없음, 연봉제 별도 미지급 대상 아님

자연어 날짜 변형
2025년 5월 말부터 2026년 4월 1일자 육아휴직한 복직자의
2026년도 상반기 정근수당은 100%야 50%야?
```

| 층 | 회귀 계약 |
|---|---|
| 분류 | `regular_service_allowance_review`, 일반 보수 evidence-only와 구분 |
| 조건 | profile `regular-service-allowance-normal-v1`; 핵심 날짜·기간이 없으면 재질문하고 비율을 만들지 않음. 선행 core가 있으면 자연어 날짜를 자동 추출하고, 사용자가 명시하지 않은 허용 필드에는 같은 자녀 1년 이내·지급기준일 재직/봉급 지급·지급 제외조건 없음의 3묶음을 적용해 조건부 결과 제공 |
| 시점 | 상반기 산정 기준일을 2026-07-01로 변환하고 2026-07-01~08-01 보수규정 버전 선택 |
| 검색 | lexical shortlist와 독립된 전체 vector, temporal filter 전 top-k 유실 0 |
| 필수 근거 | 수당규정 제6조제1항제2호·제2항·제19조제10항, 보수규정 제14조제3호의2 |
| 계산 | 기본 산입 범위의 육아휴직 3개월 + 복직 후 근무 3개월 = 6개월·100% |
| 반대 사례 | 같은 자녀 기본 산입 12개월을 이미 사용했고 확대 요건이 없으면 3개월·50% |
| 안전 | 가정 기반 결과는 `REVIEW_REQUIRED`; 징계·지급일 봉급 미지급·연봉제 제외가 실제 조건으로 입력되면 그 확인값이 가정보다 우선하고 지급대상 경계로 전환; 해당 필드는 가정 목록에서 제거하고 나머지 미지정 필드만 계속 가정; 가정을 확인값이나 세션 사실로 저장하지 않음 |
| 생성 | Qwen이 계산값을 바꾸지 않고 근거 설명, citation allowlist 밖 ID 0, 육아휴직 산입 반전 설명 0; 위반 설명은 결정적 근거 문장으로 대체하고 모델 권고는 별도 기록 |
| 승인 | 공식 candidate 사람 승인 전 최종 상태 `REVIEW_REQUIRED` |

자동 회귀는 100%·50%·지급 제외, 조건 누락, 101위 과거 버전, full-vector cache와
공식 source URL, 한국어 날짜 표현의 불필요 재질문 0건, profile version, 가정과
확인값·세션 사실의 분리, 명시 예외 우선과 나머지 정상 가정 유지를 각각 검사한다. 실제 로컬 모델 반복 3회와 독립 법령 검토는 아직
완료하지 않았으므로 법률 정확도·P95·운영 효과는 미측정으로 남긴다.

## 16. 디자인 A/B 평가

화면 비교는 법률 품질 평가와 분리한다. 대조군은 현재 production dashboard, 후보군은
사람이 A Evidence Ledger·B Case Workbench·C Regulation Map 중 명시적으로 고른 한
방향이다. 선택 전 세 방향은 모두 `AI-provisional-review-candidate`로 유지한다.

2026-08-03 포트폴리오 소유자가 B Case Workbench를 선택했다. production 통합에는
soft rounded geometry, 기존 미색·차콜·포레스트 tone과 자체 호스팅 LINE Seed Sans KR
Regular·Bold를 적용했다. 이 선택과 기술 검수는 rollout 증거이지 사람 사용성 결과가 아니다.

2026-08-04 소유자의 명시적 수정 요청에 따라 production 정보구조를 채팅·근거 2열로
단순화하고, 내부 품질·모델 상태·세션 용어를 기본 화면에서 제거했다. 원문은 화면 안에서
먼저 읽고 외부 법령 사이트는 보조 경로로 연다. 이 변경도 사람 사용성 결과가 아니라
방향성 결정과 기술 검수 기록이다.

같은 날 후속 수정으로 시각 체계를 cool-white·graphite·단일 blue accent로 바꾸고,
assistant를 최대 720px의 카드 없는 본문으로 열었다. 누락 조건은 compact chip, 정상
답변은 결론→가정 한 줄→근거 요약→관련 근거 링크 순서로 고정했다. 이는 ADR-0011의
production 시각 토큰을 대체하고 ADR-0014의 채팅 중심 정보구조를 구체화한 결정이며,
실제 과업 완료율·선호·법령 이해도는 여전히 미측정이다.

- CONTROL과 CANDIDATE는 같은 CASE-A/B/C, 과업 문구와 성공 기준을 사용한다.
- CASE-A는 누락 조건 발견과 후속 입력, CASE-B는 기준일·시행일·원문 발견,
  CASE-C는 보류 이유와 사람 확인 항목 이해를 본다.
- task completion, 첫 행동 명확성, 근거 발견 단계, 오류 회복과 선호를 분리한다.
- 반응형·focus·overflow·어절 줄바꿈 같은 기술 계약은 사람 사용성 결과와 합치지 않는다.
- 참여자가 없으면 시간, 선호, 완료율을 `미측정`으로 남긴다.
- 실제 질문 원문과 직원정보를 수집하지 않고 공개 법령·합성 CASE만 사용한다.

실행 계약은 `evals/design-ab-v0.1.json`, 공개 상태는
`evals/reports/design-ab-evaluation.md`에 둔다. 시각 선호를 법률 정확도, 처분 정확도나
업무시간 절감으로 확대 해석하지 않는다.
