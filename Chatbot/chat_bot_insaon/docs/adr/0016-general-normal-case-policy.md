# ADR-0016: 필수 사실·통상 가정·명시값의 우선순위를 공통 정상가정 정책으로 둔다

- 상태: Accepted
- 날짜: 2026-08-04
- 관련 요구사항: FR-02, FR-03, FR-07, FR-10, FR-13
- 관계: ADR-0001의 사람 검토 경계를 구체화하고, ADR-0013의 정근수당 가정을 최초 프로필로 편입한다

## Context

인사ON은 필요한 조건을 재질문하는 것이 안전하지만 모든 정상 상태를 매번 묻으면 챗봇의
사용성이 크게 떨어진다. 반대로 정근수당 사례에서 사용한 정상값을 다른 휴직·복직 질문에
일괄 적용하면 휴직 유형, 기준일, 자녀·질병·돌봄 사실이나 기관 규정을 실제 확인 없이
만들게 된다. 이 값들은 결론과 적용 근거를 바꾸므로 일반적인 기본값으로 취급할 수 없다.

ADR-0013은 정근수당 한 사례에 통상 가정과 명시 예외의 경계를 먼저 도입했다. 이후 다른
지원 질문이 같은 방식을 재사용하려면 무엇이 필수 사실이고, 어떤 가정이 승인됐으며,
사용자의 후속 입력이 어떤 우선순위를 갖는지 공통 계약이 필요하다.

## Options

1. 모든 미지정 조건을 항상 재질문하고 통상 가정을 금지한다.
2. 지원 유형 전체에 하나의 정상 상태 기본값을 적용한다.
3. 레인별 필수 사실은 가정하지 않고, 문서화·버전화·승인된 프로필의 허용 필드만 통상
   가정하며 사용자 명시값을 최우선으로 둔다.

## Decision

옵션 3을 선택한다.

### 공통 상태와 우선순위

모든 지원 질문의 조건은 다음 세 상태로 관리한다.

- `core`: 해당 review lane의 분류·시점·적용대상·결론에 반드시 필요한 사실
- `normal_case_assumption`: 제품 계약상 승인된 profile이 허용한 미지정 정상값
- `override`: 사용자가 질문이나 후속 turn에서 명시·정정한 정상값 또는 예외값

값의 우선순위는 `override > normal_case_assumption > unknown`이다. `core`가 없으면
profile로 채우지 않고 재질문하거나 `미확인`으로 남긴다. 서로 충돌하는 명시값은 최근값을
임의로 선택하지 않고 충돌을 표시해 `REVIEW_REQUIRED`로 전환한다.

날짜·기간의 명시값에서 결정적 규칙으로 계산한 `core`는 `normal_case_assumption`이 아니다.
파생 provenance와 계산 규칙을 남기고, 입력이 모호하거나 명시값과 충돌하면 파생하지 않는다.

통상 가정은 응답의 `assumed_conditions`에만 기록한다. 질문에서 확인한
`confirmed_conditions`와 API 세션의 `structured_conditions`에는 저장하지 않는다.
적용한 profile ID·version은 API의 `assumption_profile_id`에 함께 기록하되 사용자 화면에는
내부 식별자를 노출하지 않는다.
후속 명시값이 들어오면 해당 필드의 가정을 제거하고 재계산·추가 질문·보류 중 안전한
행동을 선택한다. 가정에 의존한 결과는 `REVIEW_REQUIRED`보다 낙관적으로 승격하지 않는다.

### 가정할 수 없는 core

다음 값은 normal-case profile에 등록할 수 없다. 해당 유형의 판단에 필요하면 반드시
질문하거나 `미확인`으로 남긴다.

- 공통: 휴직 유형, 질문 기준일, 적용 직군·제도
- 육아휴직: 자녀 생년월일과 동일 자녀 여부 등 자격·기간을 바꾸는 자녀 사실
- 질병휴직: 공무상·비공무상 질병 여부
- 가족돌봄휴직: 돌봄 대상과 신청자와의 관계
- 자기개발휴직: 자기개발 목적
- 기관 규정: 존재·확인 여부와 상위 규정 충돌 상태

기관 규정을 수집하지 않은 상태는 `없음`이 아니라 `미확인`이다. evidence-only 레인도
질문 기준일이나 적용대상이 불명확하면 정상 상태를 만들지 않고 적용 경계를 질문한다.

### profile registry 승인 계약

registry는 기본 거부형이다. 등록되지 않은 레인·필드에는 통상 가정을 적용하지 않는다.
새 profile은 최소한 다음 내용을 PRD·평가계획·추적표와 관련 ADR에 함께 기록하고 회귀
테스트를 통과해야 한다.

1. profile ID와 version, 적용 review lane
2. 적용 전에 확인돼야 하는 `core`
3. 허용 필드의 정확한 내부 값과 사용자 표시 문구
4. 명시값 override, 충돌과 부분 override 처리
5. 최대 허용 상태와 근거·평가·철회 조건

profile 등록 승인은 제품 조건 계약의 승인이지 법률적 정답 승인이나 공식 corpus 사람
승인을 대신하지 않는다.

### 최초 등록 profile

ADR-0013의 정근수당 정상 시나리오를 `regular-service-allowance-normal-v1`으로
등록한다. 적용 lane은 `regular_service_allowance_review`이며 선행 core는 산정 반기,
질문 기준일, 복직일, 이번 휴직기간과 질문에서 분류된 육아휴직·정근수당 유형이다.

| 사용자 표시 묶음 | 허용 내부 가정 |
|---|---|
| 같은 자녀의 현재·이전 육아휴직 합산이 기본 산입 한도 1년 이내 | `prior_same_child_leave_months=0` |
| 지급기준일 현재 재직하고 봉급 지급 | `salary_on_payment_date=true` |
| 지급 제외조건 없음 | `disciplinary_action_in_period=false`, `other_nonservice_periods=[]`, `annual_salary_exclusion_applies=false` |

PAY-01 상반기 예시의 지급기준일은 7월 1일이다. 사용자가 같은 자녀 기존 사용기간,
지급일 봉급 미지급, 징계·직위해제 등 제외기간이나 연봉제 제외를 명시하면 해당 내부
가정만 제거하고 명시값을 유지한다. 나머지 미지정 허용 필드는 같은 version의 profile을
계속 적용한다.

이 profile은 다른 휴직·복직 유형의 정상값을 추정하는 근거가 아니다. 후속 profile이
별도로 승인되기 전까지 다른 지원 질문에는 `normal_case_assumption`을 적용하지 않는다.
공통 UI는 가정값을 `가정한 조건`으로 표시하고, 확인값처럼 표현하지 않는다. 지급기준일과
휴직기간 라벨은 특정 상반기·육아휴직 사례를 전역 기본값으로 사용하지 않는다.

## Consequences

- 모든 유형에서 필수 사실과 편의상 가정을 같은 단어로 취급하지 않는다.
- 승인된 좁은 사례에서는 반복 질문을 줄이면서도 가정·확인·예외의 경계를 사용자에게
  보여줄 수 있다.
- profile마다 core 누락, 미등록 필드, 세션 오염, 명시값 override, 충돌과 상태 상한을
  회귀 테스트해야 하므로 등록 비용이 생긴다.
- 현재 구현·회귀와 API version 추적이 있는 profile은 정근수당 하나다. 새 profile은 같은
  유형별 core/override matrix를 별도 검토·평가한 뒤 등록해야 한다.
- `prior_same_child_leave_months=0` 내부값과 사용자용 1년 이내 요약이 계산 의미를 다르게
  전달하지 않는지 독립 사용성·법령 검토에서 확인해야 한다.

## Revisit

- 새 review lane에 정상 상태 profile을 추가하려 할 때
- 필수 질문이 과도하다는 실제 사용성 증거가 확보될 때
- 통상 가정 때문에 결론이 반전되거나 명시값이 덮이는 회귀가 발견될 때
- profile 내부값과 사용자 표시 문구가 같은 의미를 전달하지 못할 때
- 기관 규정을 승인·버전화해 별도 데이터 경계를 설계할 때

## 개정 2026-08-11: `parental-leave-normal-v1` 등록과 상태 상한의 코드 강제

### 왜 고치는가

이 ADR의 "가정할 수 없는 core"는 육아휴직 항목에 *"자녀 생년월일과 동일 자녀 여부 등
자격·기간을 바꾸는 자녀 사실"*을 넣었다. 이 문장대로면 `previous_leave_periods`는 가정
대상이 아니다. 그런데 같은 사실을 정근수당 lane은 이미
`prior_same_child_leave_months = 0`으로 가정하고 있었다.

같은 사실을 한쪽에서는 통상값으로 두고 다른 쪽에서는 매번 필수로 요구했다. 사용자에게는
"육아휴직 쓸 수 있나요"에 두 가지를 되묻는 화면으로 나타났고, 그중 하나는 이 제품이
다른 화면에서 스스로 기본값을 정해 쓰던 값이었다. 정책의 일관성 문제이지 안전 문제가
아니었다.

### 무엇을 바꾸는가

**profile 등록.** `parental-leave-normal-v1`을 육아휴직 심층 검토 lane에 등록한다.

| 항목 | 내용 |
|---|---|
| profile ID | `parental-leave-normal-v1` |
| 적용 lane | `deep_review` · `LeaveType.PARENTAL` |
| 적용 전 확인돼야 하는 `core` | `leave_type`, `reference_date`, `child_birth_date` |
| 허용 필드 | `previous_leave_periods = ()` |
| 사용자 표시 | "같은 자녀의 이전 육아휴직 기간" |
| 최대 허용 상태 | `REVIEW_REQUIRED` |

**core 목록 개정.** 육아휴직 항목을 *"자녀 생년월일"*로 좁힌다. 자녀 생년월일은 기간
상한을 직접 정하고 가정할 수 있는 "정상적인 생년월일"이라는 것이 없으므로 계속 `core`다.
같은 자녀의 이전 육아휴직 기간은 위 profile로 옮긴다.

**질병·가족돌봄·자기개발은 그대로 `core`다.** 공무상·비공무상 구분, 돌봄 대상과의 관계,
자기개발 목적은 "정상 상태"가 아니라 어느 조문을 적용할지 자체를 가르는 분류값이다.
기본값을 두면 근거 조문이 통째로 바뀐다. 이 셋에는 profile을 등록하지 않는다.

### 함께 고친 결함

이 ADR은 처음부터 *"가정에 의존한 결과는 `REVIEW_REQUIRED`보다 낙관적으로 승격하지
않는다"*고 적고 있었다. **정근수당 lane에는 그 상한이 코드에 있었고 휴직 lane에는
없었다.** 휴직 심층 검토의 반환부는 `assumed_conditions`를 싣지도 않았다.

그대로 profile만 등록했다면 아무도 확인하지 않은 사실 위에서 `ANSWERABLE`("가능합니다")이
나갔을 것이다. 실제로는 이미 한도를 다 쓴 사람일 수 있다. 화면에는 가정했다는 표시조차
없었을 것이다. 상한과 공개를 함께 넣었다.

문서에 적힌 안전 규칙이 한 lane에만 구현돼 있었다는 사실 자체가 이 ADR의 교훈이다.
profile 등록 계약(5항 "최대 허용 상태")은 문서가 아니라 회귀 테스트로 확인한다.

### 회귀

`tests/integration/test_assumption_status_cap.py`

- 가정이 적용된 답은 `ANSWERABLE`에 도달하지 않는다
- 조건을 전부 답하면 여전히 `ANSWERABLE`에 도달한다(상한이 모든 결론을 막지 않는다)
- 명시값이 가정을 대체한다(`override > normal_case_assumption`)
- 가정값은 세션 `structured_conditions`에 저장되지 않는다

`tests/integration/test_normal_assumption_boundary.py`는 두 profile의 기본값이 서로의
lane으로 새지 않는지 확인한다.

## 개정 2026-08-11(2): 복직일 파생을 가정으로 등록하고, 표기 게이트를 걷어낸다

화면에서 이렇게 끝났다.

```
나> 2025. 4. 1 ~ 2026. 3. 31 육아휴직자의 2026년 상반기 정근수당은?
봇> 지급률을 확인하려면 아래 1가지만 더 알려주세요.  [복직일]
```

`leave_periods`는 확정으로 잡혀 있었다. 휴직이 2026. 3. 31에 끝난다는 것을 방금 입력받고도
복직일을 되물었다. 파생이 `복직자|복직한|복직했|…` 정규식에 걸려 있어서 같은 사실을
"복직자"라고 쓰면 계산하고 "육아휴직자"라고 쓰면 물었다. **계산되는 값을 어휘로 갈랐다.**

### 결정

휴직 종료일이 확정이고 그 lane이 `reinstatement_date`를 요구하면 복직일을
`regular-service-allowance-normal-v1`의 **파생 통상값**으로 채운다.

확정 사실로 두지 않는다. 휴직이 끝났다고 반드시 복직한 것은 아니다 — 연장했거나 다른
휴직으로 이어졌거나 퇴직했을 수 있다. 가정이므로 화면에 표시되고, 상태 상한이 걸리고,
명시값이 들어오면 물러나고, 세션에 저장되지 않는다.

종료일이 없으면(진행 중인 휴직) 계산할 것이 없으므로 그대로 묻는다. `reinstatement_date`를
요구하지 않는 lane(휴직 심층 검토)에는 붙이지 않는다 — 쓰이지도 않는 "가정" 줄이 화면에
뜬다.

### 같은 유형을 전 lane에서 걷어냈다

복직일 하나만의 문제가 아니었다. 네 lane을 훑으니 **11건 중 6건**이 이미 문장에 있는
사실을 되묻고 있었다. 원인은 전부 같다. 추출기가 `자녀 생년월일은`·`돌봄 대상은`·`목적은`
같은 **라벨 표기**를 요구하는데 사람은 그렇게 쓰지 않는다.

| 필드 | 되묻던 문장 |
|---|---|
| `child_birth_date` | "2025년 3월 2일**생** 자녀", "2025. 3. 2. **태어났는데**" |
| `medical_leave_basis` | "**업무상 재해**로 인한" |
| `care_recipient_relation` | "**부모 간병**으로", "**어머니를 돌보려고**" |
| `application_purpose` | "**대학원 진학하려고**" |

표기만 넓혔고 의미는 추측하지 않는다. 문장에 값이 없으면 여전히 묻는다. 관계어가 둘 이상
나오면(예: "부모와 배우자") 어느 쪽이 대상인지 정할 수 없으므로 읽지 않고 되묻는다.

**부분 문자열이 두 번 물었다.** `비공무상`은 `공무상`을 품어 순서를 뒤집으면 정반대로
판정되고, `조부모`는 `부모`를, `손자녀`는 `자녀`를 품어 "조부모 간병"이 모호로 잡혔다.
더 긴 일치에 삼켜진 짧은 일치는 버린다.

### 상시 감시
