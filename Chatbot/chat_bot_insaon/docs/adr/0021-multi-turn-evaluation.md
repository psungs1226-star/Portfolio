# ADR-0021: 평가를 대화 단위로 실행한다

## Context

인사ON은 챗봇이다. 핵심 시나리오는 한 번의 질문이 아니라 세 걸음이다.

```
사용자: 질병휴직을 검토해 주세요.
인사ON: 질문 기준일과 공무상·비공무상 구분이 필요합니다.        ← REVIEW_REQUIRED
사용자: 질문 기준일은 2026-03-02입니다. 비공무상 사유입니다.
인사ON: (근거 조문과 함께) …                                    ← ANSWERABLE
```

이 흐름은 제품에 구현돼 있었다. `POST /reviews`가 세션을 열고
`POST /reviews/{id}/messages`가 이어받으며, 세션은 확정된 구조화 조건을 턴 사이에
들고 간다. 웹 UI도 `data-session-id`로 두 번째 질문부터 후속 엔드포인트를 쓴다.

**평가는 그 흐름을 한 번도 실행하지 않았다.** `runner.py`는 케이스마다
`service.handle()`을 한 번 호출했고, `EvaluationCase.turns` 필드는 선언만 돼 있을 뿐
읽히지 않았으며, 잠금셋 58건은 전부 `turns: []`이었다. `/messages`를 건드리는 테스트는
저장소 전체에 두 개였다.

그래서 공개된 모든 수치 — 상태 정확도 1.000, 인용 완전성 1.000, 실모델 0.983 — 는
**첫 턴의 성능**이었다. 특히 나쁜 것은 `missing_condition` 슬라이스다. 이 8건이 위
시나리오의 1단계인데, 평가는 "되물었다"까지만 보고 정답 처리했다. 사용자가 답한 뒤
실제로 결론에 도달하는지는 측정 대상이 아니었다.

세션 병합 규칙(주제가 바뀌면 기준일만 남기고 버린다)은 `api/reviews.py`의 private
static method였다. 평가 코드가 닿을 수 없는 자리이고, 닿으려면 규칙을 베껴 써야 했다.
베낀 규칙을 재면 제품이 아니라 사본을 재게 된다.

## Options

1. 그대로 둔다 — 다회차는 통합 테스트로 확인하고 지표는 단발로 유지한다
2. 러너가 세션 병합 규칙을 자체 구현해 다회차를 흉내낸다
3. 대화 상태를 application 계층으로 올리고 API와 러너가 같은 객체를 쓴다

## Decision

**3을 택한다.**

`application/session.py`에 `ReviewConversation`과 `merge_conditions`를 두고,
`ReviewApiService`와 `evaluation/runner.py`가 둘 다 이것을 통해 턴을 진행한다.
러너는 `case.question_text`에 이어 `case.turns`를 같은 세션에 순서대로 먹이고,
**마지막 턴의 답으로 채점한다.** 턴이 없는 케이스는 호출이 한 번이므로 기존 결과와
같다.

`multi_turn` 슬라이스 12건을 잠금셋에 넣고 세 갈래로 나눠 잰다. 각 갈래는
`critical_flags`로 선언되며 지표는 그 flag를 분모로 쓴다.

| flag | 지표 | 무엇을 재는가 |
|---|---|---|
| `prior_turn_conditions_must_carry_over` | `conversation.condition_carryover` | 되물은 필드를 사용자가 답한 뒤 세션이 들고 있는가 |
| `prior_turn_conditions_must_not_leak` | `conversation.topic_switch_isolation` | 유형이 바뀌면 앞 유형 조문이 근거에서 빠지는가 |
| `elliptical_followup_must_keep_task` | `conversation.elliptical_followup` | "질병휴직은요?" 같은 축약 발화에서 과업이 유지되는가 |

`conversation.condition_carryover`는 골든셋에 새 정답 필드를 넣지 않는다. 앞 턴 답변의
`missing_conditions`와 대화가 최종적으로 들고 있는 조건을 비교해 계산하므로, 분자·분모가
모두 대화 자체에서 나온다.

주제 전환 누수는 `FATAL_STALE_TURN_EVIDENCE`로도 센다. 바뀐 주제의 질문에 앞 주제의
조문을 근거로 다는 것은 유효하지 않은 버전을 인용하는 것과 같은 등급의 실패다.

후속 턴 문장은 `ConditionExtractor`가 실제로 파싱하는 표기만 쓴다. 파싱되지 않는 문장을
쓰면 재는 것이 제품이 아니라 데이터 생성기의 작문이 된다.

## Consequences

공개 수치가 내려갔다. 70건 기준 H3·H4에서:

| | 0.3.0 (58건, 전부 1턴) | 0.4.0 (70건, 12건 다회차) |
|---|---:|---:|
| 상태 정확도 | 1.000 | **0.943** (66/70) |
| 인용 완전성 | 1.000 | **0.931** (54/58) |

떨어진 4건은 전부 생략형 후속이다. `conversation.elliptical_followup`은 B0부터 H4까지
**0/4**다. 검색 구성과 무관하며, 검색으로 고쳐지지 않는다. 축약 발화가 앞 턴의 과업
(`evidence_lookup`)을 잃고 심층 검토로 재분류되면서 조건을 처음부터 다시 묻는다.

이 실패는 **안전한 방향으로 실패한다.** 틀린 답을 만드는 것이 아니라 더 묻는다. 그래서
게이트를 느슨하게 푸는 방식으로 "고치지" 않는다. 필수 조건 없이 결론을 만들지 않는다는
규칙이 이 UX 결함보다 우선한다. 측정해서 한계로 공개한다.

Set Recall@5의 분모에서 다회차 12건을 뺐다. 이 지표는 질문 한 줄을 그대로 색인에 넣는
단일 질의 probe인데, 다회차의 마지막 턴("질문 기준일은 …입니다")만으로는 무엇을 찾아야
하는지 알 수 없고 실제 제품은 이월된 조건과 분류 결과를 함께 넣어 검색한다. probe로
흉내내면 제품이 아니라 흉내를 재게 되므로, 다회차의 검색 성패는 답변이 실제로 인용한
조문(`citation.completeness`)으로 판단한다.

`distinct_case_count`의 서명에 `turns`를 넣었다. 넣지 않으면 같은 문장으로 시작하는
1턴 케이스와 다회차 케이스가 하나로 합쳐져, 이 카운터가 막으려던 padding 결함이 다시
생긴다.

부수적으로 다회차 경로에만 있던 결함 하나를 찾아 고쳤다. `ReviewQuestion`의 후속 기준일
패턴이 `\b`를 쓰고 있었다. 한글 음절은 파이썬 정규식에서 `\w`라서 `2026-03-02입니다`처럼
조사가 붙으면 뒤쪽 경계가 성립하지 않는다. 후속 턴은 날짜만 던지고 조사를 붙이는 형태가
가장 흔하므로 이 경로에서 특히 잘 깨졌고, 깨지면 대화가 앞 턴의 과업에서 떨어져 나가
조건을 처음부터 다시 물었다. 단발 질문 평가로는 관측될 수 없는 자리다.

## Revisit

- 다회차 지표의 분모는 구성당 12건, 하위 지표는 각 4건이다. 신뢰구간을 논할 규모가
  아니라 동작 유무를 보는 회귀 확인이다. 3턴 이상, 사용자가 앞 턴 사실을 정정하는 경우,
  한 턴에서 조건 일부만 답하는 경우는 아직 없다.
- 생략형 후속을 안전하게 이어받는 방법 — 과업을 이월하되 필수 조건 게이트는 유지하는
  분류 규칙 — 은 별도 결정으로 남긴다.
