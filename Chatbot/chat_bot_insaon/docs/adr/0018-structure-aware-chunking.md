# ADR-0018: 문자 수가 아니라 조문 구조 단위로 분할한다

## Context

`ProvisionParser`는 처음부터 문자 수 분할 없이 법령 → 조 → 항 → 호 → 목 계층으로만
문서를 나눈다. 그런데 이 선택을 대안과 비교한 기록이 없었다. ADR-0004는 lexical 엔진
선택이지 청킹 전략이 아니다.

RAG 구현에서 가장 먼저 손이 가는 것은 고정 길이 분할과 재귀 분할이다. 구조 단위 분할은
파서를 직접 써야 해서 비용이 크다. 비용을 더 치른 결정이면 근거가 있어야 한다.

인사ON에는 청킹이 검색 점수만의 문제가 아니라는 사정이 하나 더 있다. 제품 계약이
"질문 기준일에 유효한 `article_path`를 인용한다"이므로, 조문 경계를 넘는 청크는 순위와
무관하게 계약을 지킬 수 없다.

## Options

1. `fixed-512` — 원문을 512자로 자르고 겹침 없음
2. `recursive-512-64` — 문단 → 문장 재귀 분할, 512자 목표·64자 겹침
3. `structure-v1` — 조·항·호·목 구조 단위, 계층과 관계 ID 보존 (현행)

## Decision

3번을 유지한다. `insaon-synthetic-distractor-corpus`(101개 조문)와 12건 질의를
같은 `char-ngram-v1` 검색기, 같은 `top_k=5`로 비교했다. 실행 manifest는
`artifacts/spikes/chunking/manifest.json`, 해석은 `evals/reports/chunking-comparison.md`에
보존한다.

| 후보 | Set Recall@5 | MRR@10 | 인용 가능 청크 | top-5 corpus 비율 |
|---|---:|---:|---:|---:|
| `structure-v1` | 0.958 | 0.944 | 1.000 | 0.047 |
| `fixed-512` | 0.979 | 0.644 | 0.000 | 0.296 |
| `recursive-512-64` | 1.000 | 0.554 | 0.000 | 0.280 |

**Set Recall@5에서는 현행 방식이 세 후보 중 꼴찌다.** 그럼에도 3번을 선택하는 근거는 두
가지다.

첫째, 청크 크기가 다르면 Recall@k는 비교 지표가 아니다. `recursive-512-64`는 현행보다
6.0배 많은 원문을 넘겨주고 recall을 0.042 얻었다. 정답을 더 잘 찾은 것이 아니라 한 청크가
더 많은 정답을 우연히 포함한 것이다. 순위 품질을 보는 MRR에서는 0.944 → 0.554로 역전된다.

둘째, 문자 수 분할 두 후보는 **모든** 청크가 조문 2개 이상을 걸쳐 단 한 건도 `article_path`
하나로 인용할 수 없다. 12건 질의 전부가 정답을 인용 불가 청크로만 도달했다. 검색 점수와
무관하게 제품 계약을 만족시키지 못한다.

`relation_ids` 추적이 끊기는 것도 같은 원인이다. H3의 문맥 확장은 조문에서 출발해 관계를
따라가는데, 청크가 조문이 아니면 출발점이 없다.

선택 기준은 **인용 가능성 → MRR@10 → Set Recall@5** 순으로 본다. 단일 가중 종합점수는
사용하지 않는다.

## Consequences

- 원문 구조가 명시된 자료만 수집 대상이 된다. 구조가 깨진 PDF·스캔 자료는 이 파서로
  처리할 수 없고, 처리하려면 구조 복원을 먼저 해야 한다. **이것을 포기한 것으로 명시한다.**
- 파서 구현·유지 비용을 계속 진다. `_article`/`_paragraph`/`_item`/`_subitem` 경로가
  원천 자료 형식이 바뀔 때마다 영향을 받는다.
- 청크가 짧아 다중 근거 질의에서 top-5 자리를 여러 개 쓴다. `multi_evidence` slice에서
  현행이 0.750으로 유일하게 진 이유다. 이 약점은 청크를 키워서가 아니라 H3 문맥 확장으로
  푼다.
- 인용·시점 검증과 관계 추적이 조문 ID 위에서 성립한다. ADR-0002의 기준일 필터가 조문
  단위 `valid_time`을 전제하므로 이 결정과 묶여 있다.
- `fixed-512`와 `recursive-512-64`는 비교 실험용 구현으로 `src/insaon/evaluation/chunking.py`
  에만 둔다. 제품 런타임이 import하지 않는다.

## Revisit

구조가 명시되지 않은 원천 자료를 다뤄야 하거나, 조문 길이 분포가 크게 달라져 조문 하나가
단독으로 너무 길어지거나(조 안에서 재분할이 필요해지거나), 임베딩 검색에서 청크 길이 효과를
측정해 결론이 달라질 때 재실행한다.
