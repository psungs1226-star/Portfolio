# AX 해커톤 예선 제출물 — 세법 개정 영향 선제탐지 플러그인

이 저장소는 AX 해커톤 예선 제출물이다. 핵심 산출물은 Codex 플러그인 하나(`src/`)와,
그 플러그인이 실제로 동작해 만든 결과물(HTML)이다.

## 한 줄 요약

**세법(부가세) 개정이 들어오면, 그 개정으로 해석이 달라질 수 있는 기존 집행기준·예규·판정을 먼저 찾아
전문가가 검토하고 고객에게 선제적으로 안내할 수 있도록 "검토 리스트"로 정직하게 라벨링하는 내부용 Tax Agent 보강 스킬.**

- AI는 결론(면세→과세 등 뒤집힘)을 **단정하지 않는다.** 세무 전문가가 검토할 수 있도록 질문·근거·반대논거를 구조화해 넘긴다.
- 상태는 항상 명시적으로 라벨링한다: `confirmed` / `REVIEW_WORTHY` / `hold_확인필요` / `exclude`.

## 번들된 스킬 2개

### 1) `tax-enforcement-standard-impact` (주력 스킬)

부가세 개정 1건을 입력받아, **공식 집행기준을 1순위 근거로** 두고
"이 개정으로 검토가 필요해진 집행기준·예규 리스트"를 정직한 상태 라벨과 함께 산출한다.
해석례(세법해석 정비사례)는 골든셋/보강 근거로만 쓰고, 최종 판단 근거로 격상하지 않는다.

### 2) `company-problem-evidence` (보조 스킬)

제출을 한 회사·공개근거에 집중시키고, **사실 / 가정 / 부족한 정보**를 분리해
과장 없는 제출 답변을 준비하도록 돕는다.

## 파이프라인 설명 — `tax-enforcement-standard-impact`

이것은 **하나의 스킬**이다. 아래 번호 단계는 사용자에게 보이는 별도 스킬이 아니라,
스킬이 내부적으로 따르는 파이프라인 단계다. 사용자 관점의 기능은 하나:
"개정이 흔들 만한 집행기준을 찾아 내부 검토 리스트를 낸다."

### 룰형 스윕 (Phase 0 ~ 6) — 검증 완료된 본체

| 단계 | 이름 | 하는 일 |
|---|---|---|
| **Phase 0** | 이슈 선정 | 직관이 아니라 **골든셋 확보 가능성**으로 첫 이슈를 고른다. 해석 정비사례를 부가세로 필터→쟁점 태깅→점수화(`usable·law_linked·non_trivial·negative` 가점, `trivial` 감점). |
| **Phase 1** | 법 개정 정규화 | 개정문을 구조화 객체로(대상·요건·효과·시점·예외 분리, 시행일·적용례 포함). LLM 추론 필드는 "추론"으로 표시. |
| **Phase 2** | 집행기준 우선 정규화 | 집행기준을 **1차 문서집합**으로 파싱(기준번호·관련조문·본칙·예외·예시·개정일). 해석례는 검증/희소 보강용으로만 수집. |
| **Phase 3** | 매칭 | 점수만 믿지 않는다. `Hard Filter → Direct Link → Logic Match → Keyword Match → Semantic Match → Evidence Check → Score` 순서. 대상·요건 동시 일치 또는 직접 조문링크 없으면 고신뢰 금지. |
| **Phase 4** | 영향 분류 | 후보를 영향 유형(조문·요건·대상·효과·예외·시점·저관련·보류)으로 분류하고 신뢰도(고/중/저/보류) 부여. |
| **Phase 5** | 검토 리스트 산출 | 내부 검토표 생성. "영향 가능 집행기준 / 보강 해석례 / 후보 없는 신규 검토주제 / 보류·제외"를 **섞지 않고** 분리. 전문가용 검토 질문 포함. |
| **Phase 6** | 검증 | 해석 정비사례를 초기 골든셋으로 recall·precision·근거율·사유품질 측정. 개정된 해석은 있는데 대응 집행기준이 없으면 "보강 해석례/신규 주제"로 분류(집행기준 변경으로 오분류 금지). |

이 룰형 스윕은 **로직 게이트 + 퍼널 + 블라인드 백테스트**로 검증했다(아래 "검증 상태" 참조).

### Phase 7 — 스코프 확장 + 판단층 (설계·파일럿, 통계검증 전)

단일 개정 1건으로는 워크플로를 통계적으로 검증할 수 없으므로, 같은 룰로 여러 개정 이벤트를 돌려
recall/precision을 집계하고 실패를 룰 개선으로 되먹인다. 여기에 두 층을 더한다.

**① 판정형(Q&A) 판단층 — "텍스트는 안 바뀌어도 결론이 뒤집히는" 과거 판정 포착**

룰형 스윕은 룰형 기준(26-x-1)의 명시적 문구 변경만 잡는다. 판정형·예규(26-40-2 등)는
**개정문 문구가 안 바뀌어도 결론이 뒤집힐 수 있다.** 이를 잡는 병렬 층이다.

- **reach(후보 찾기)와 judgment(판단)를 분리.** reach는 LLM 가설생성+시맨틱 검색이고, 결과맵은 검증결과 캐시일 뿐 손으로 만든 지식그래프가 아니다. 가치는 judgment에 있으므로, 취약한 그래프를 손으로 넓히는 대신 판단 깊이에 투자한다.
- **핵심 산출물은 verdict가 아니라 "깊은 질문 스캐폴드".** 각 후보에 대해 개정의 신설 요건을 과거 예규의 사실관계에 대입해 (1) 결론 delta, (2) 요건 원문 인용(before/after), (3) 반대논거, (4) 보정된 신뢰도를 낸다. **AI는 flip을 단정하지 않고** 전문가용 질문으로 스캐폴드만 세운다.
- **자명성 감점:** 0홉(같은 조문번호·키워드 겹침)은 저가치, ≥1홉(유추·논리연쇄·하위조문 파급·외부참조 정의변경)은 고가치. 홉 수로 스캐폴드 가치를 랭크.
- **적대적 검증 필수:** 신뢰할 수 없는 깊이는 없는 것만 못하다. 독립 관점(distinct lens) 스켑틱들이 flip을 **반증**하려 시도 → 다수가 반증하면 flip을 kill. 한 축을 좁고 완전하게(broad-and-shallow 금지).
- **verdict:** `confirmed`(적대검증을 통과한 flip) / `REVIEW_WORTHY`(본안상 뒤집히진 않지만 같은 조문군·생존 불안정 신호 → 검토 큐 유지, 단정 금지) / `hold_확인필요` / `exclude`. **적대검증이 flip을 kill하면 그것은 이 층의 실패가 아니라 성공**(REVIEW_WORTHY와 진짜 flip을 구분한 것). 대표 산출물: `07-scope-expansion/JUDGMENT_SCAFFOLD_AXIS1.json`(기술보증기금 제3호 신설 → 신용보증기금 발명평가 예규: 3-lens 적대패널 → REVIEW_WORTHY, flip 아님).
- **모트 우선순위(Tier):** Tier 1 = 과거 판정의 **분류가 뒤집힘**(면세↔과세) = 검토 큐 최상단. Tier 2 = 분류는 유지되나 **효과(세율·과표·계산방법)가 변동**. Tier 3 = 분류·효과 모두 불변(기존 실무 성문화) = 저순위/드롭.
- 데이터 창은 시행일 기준 **과거로 ~10년**(개정은 미래 텍스트가 아니라 이미 확정된 판정을 흔든다). 날짜 근접이 아니라 개정된 법리(대상·요건·효과)로 매칭. 생산일자 기준 필터.

**② 신호 레이어(사용자 승인 스코프 확장) — 트리거 타이밍 축**

개정 외에 두 판단자료를 **불안정 신호/권위 확인용으로만** 인정(새 스윕 코퍼스나 최종 권위로 승격 금지):

- **L1 개정(선행)** — 가장 이르고 예측적. 기존 개정 스윕. 정비 후 삭제 판정은 색인에서 빠지므로 개정 시점이 유일한 포착 기회.
- **L2 심판례(동행)** — 과세 후 ~1년 내 접수, 법원보다 수년 빠르고, 납세자가 예규를 다투는 곳에 밀집. **REVIEW_WORTHY 신호로만**(권위 낮음, 번복 가능). "대법원은 수년 걸린다"는 지연 문제를 분쟁 파이프라인의 앞 단으로 해결.
- **L3 판례(후행 권위)** — 과거 예규가 이미 확정/번복됐는지 확인하는 소급 검증자. 이 역할에선 지연이 무관.

### Phase 8 — 패키징

런타임 데이터 단계가 아니라 **빌드/릴리스 단계**다. canonical 파이프라인 아티팩트(Phase 5·7 산출물)를

- `steps/05-html-finalize/build_brief.py` — canonical → `brief_data.json` → HTML (end-to-end, 계약 검증 포함).
- `steps/05-html-finalize/render_brief.py` — `brief_data.json` → HTML 결정론적 렌더.

## 검증 — 두 층으로 명시 (중요)

검증은 성격이 다른 두 가지가 있고, 스킬은 **둘 다** 요구한다. 하나가 다른 하나를 대체하지 않는다.

### (A) 런타임 검증 게이트 — 새 개정이 들어올 때마다 (필수)

Phase 6(아래 B)는 골든셋으로 **워크플로 자체**를 검증하는 오프라인·주기 절차라,
**정답 라벨이 아직 없는 새 개정**의 산출물을 그 자체로 검증하지는 못한다. 그래서 실제 운영에서
새 법령 개정이 들어오면, 검토 리스트를 내보내기 **전에** 아래 게이트를 반드시 통과해야 한다(어떤 항목도 예외 없음).
검증은 정답셋이 없으므로 **내재적 자체검사 + 적대적 반증 + 정직한 라벨링**으로 한다.
(스킬 본문 `SKILL.md`의 "Runtime Verification Gate" 참조.)

1. **근거 게이트(하드):** "영향 가능 집행기준"의 모든 후보는 구체 근거 ≥1개(변경조문/기준번호/관련조문/본칙요지)를 갖는다. 근거 없으면 `hold`/`exclude`로 강등, 영향가능에 등재 불가.
2. **홉 라벨링:** 각 후보를 0홉(직접 링크)·≥1홉(추론)으로 태깅. ≥1홉은 3번을 통과하지 않으면 `confirmed` 금지.
3. **적대적 검증(모든 flip 주장·≥1홉 후보 필수):** 독립 관점 스켑틱들이 영향을 **반증** 시도 → 다수 반증 시 `REVIEW_WORTHY`/`exclude`로 강등. 적대검증이 flip을 kill하면 그것은 게이트의 **성공**(진짜 flip과 REVIEW_WORTHY를 구분).
4. **네거티브 컨트롤(런타임 정밀도):** 같은 실행에 "유사하지만 무관한" 기준을 디코이로 섞는다. 디코이가 고신뢰로 뜨면 이번 개정에서 정밀도가 무너지는 것 → 하드필터 강화 후 강등하고 내보낸다.
5. **블라인드스팟 자기보고(은폐 금지):** 알려진 놓침 유형(동의어 gap: 개정 어휘 ≠ 사례/기준 어휘, 광역 전문개정)을 백테스트로 고정해 뒀다. 들어온 개정이 광역 전문개정이거나 어휘가 어긋나면 "놓쳤을 가능성" 노트를 반드시 출력. 커버리지를 완전한 것처럼 제시하지 않는다.
6. **정직한 verdict + 재현성:** 최종 라벨은 `{confirmed, REVIEW_WORTHY, hold_확인필요, exclude}`만. 반드시 바뀐다고 단정 금지. 결정론적 재실행 시 동일 리스트.

**게이트 end-to-end 데모(실행 가능):** `pipeline/06-validation/runtime_gate_demo.py`.
데모 canonical(제40조①13 민간재간접벤처투자조합 면세 신설) 1건을 6단계 게이트에 통과시키면,
소박한 사전판정 `confirmed`(엔티티 히트)가 **홉 라벨링→적대검증 다수 반증**으로 `REVIEW_WORTHY`로 강등되고,
동의어 gap('재간접' 직접검색 해석례 0건)을 블라인드스팟으로 자기보고한다. 결과는 `RUNTIME_GATE_DEMO.json`으로 저장(결정론).

```bash
python3 src/skills/tax-enforcement-standard-impact/pipeline/06-validation/runtime_gate_demo.py
```

### (B) 오프라인 골든셋 검증 — 워크플로 품질 측정 (주기)

- **룰형 스윕(Phase 0~6): 검증 완료.** 로직 게이트 + 퍼널 + 블라인드 백테스트로 측정.
  블라인드 백테스트(11개 code-10 flip 대상)에서 HIT@10 = 2/7(정밀 개정은 rank 2·4에서 적중, 광역 전문개정·동의어 gap은 놓침), 축 도달성 ~9/11. 개선 레버: 동의어 사전, 항·호 단위 개정 해상도, 다중 키워드 질의.
- **판단층·신호 레이어(Phase 7): 설계·파일럿(n=1) 단계, 통계검증 전.** 대표 축 1건에 대해 스캐폴드+3-lens 적대검증을 돌려 REVIEW_WORTHY로 수렴함을 보였다. 통계적 정밀도는 아직 측정 전임을 명시한다.
- **루프 폐쇄:** 새 개정이 나중에 세법해석 정비 기록·심판례·판례를 받으면 골든셋에 추가해 Phase 6을 재측정. 런타임 게이트(A)는 매 실행, 오프라인 검증(B)은 라벨이 도착할 때 — 둘 다 필수.
- 산출물 재현성: `build_brief.py` 2회 실행 시 HTML 해시 동일(결정론). HTML 무결성(doctype/누출/script·iframe) 통과.

## 내용 검증 시도 상태 (정직성)

코드·구조 검증과 별개로, **인용 예규의 실재/요지 일치 같은 실제 내용 검증**을 데모 1건(제40조①13, 인용 예규 `서면-2015-법령해석부가-0932`)에 시도했다.

- NTS 국세법령정보시스템 해석례 검색 액션(`ASIPDI002PR01`)에 **실제 조회 시도** → 세션 연결·HTTP 200까지 도달(엔드포인트 reachable).
- 그러나 정확한 검색 paramData 스키마 미확정으로 문서번호 반환 확인 실패 → **문서 실재/요지 일치는 이번 패스에서 미확정(inconclusive)**. 이는 스캐폴드가 자기선언한 한계(`honest_limits`: "예규 전문·근거조문 문자열 인용 pending", detail full-text 액션 unconfirmed)와 일치한다.
- 즉 현재 소스 대조가 **실측된 부분**은 개정 전/후 diff(`ASISTA002MR03`)와 예규 **요지**(`ASIPDI002PR01` GIST)까지이고, **예규 전문 대조·법적 정오 판단은 여전히 세무 전문가 몫으로 남는다**(설계상 AI는 flip을 단정하지 않음).

## 정직성 규칙 (Output Rules)

- 근거가 집행기준인지 해석례인지 항상 명시.
- **집행기준이 반드시 바뀐다고 단정하지 않는다.** "검토 후보", "영향 가능", "전문가 검토 보류" 같은 표현 사용.
- 최종 납세자 자문은 제공하지 않는다.
- MVP 스코프(내부지침·기재부 해석·기본통칙·판례) 밖으로 사용자가 명시적으로 넓히기 전까지 확장하지 않는다.
