# Tax Agent 보강 스킬 파이프라인 워크트리

## 0. 설계 기준

이 문서는 실제 구현 전에 검토하고 페이즈별로 진행하기 위한 실행계획이다.

핵심 원칙은 아래와 같다.

- 실행 흐름은 **법령 변경을 먼저 정규화**한다.
- 데이터 준비는 **집행기준을 우선 정규화**하고, 판단 사례가 부족할 때만 **해석례를 보조/검증 데이터**로 사용한다.
- 매칭 기준은 단순 키워드가 아니라 **대상, 요건, 효과, 시점, 예외**다.
- MVP는 **부가가치세**로 제한한다.
- 1차 사용자 대상은 **회계법인 임직원**이다.
- 1차 산출물은 세무 결론이 아니라 **내부용 변경 예상 검토리스트**다.
- Tax Agent 가드레일과 영업·홍보 소재는 1차 구현 대상이 아니라, 내부 검토리스트가 나온 뒤의 선택 활용안으로 둔다.

## 2. Phase 0. 정답셋 기반 첫 쟁점 선정

### 목적

첫 쟁점을 사전 선호로 고르지 않고, 세법해석정비 데이터에서 정답셋을 가장 많이 만들 수 있는 쟁점으로 선택한다.

### Phase 0 입력

- 세법해석정비 데이터
- 정비 전 해석례
- 정비 후 해석례
- 관련 법령 조문
- 정비 사유

### Phase 0 출력

```json
{
  "selected_issue": "매입세액공제",
  "reason": "세법해석정비 사례 수와 전후 비교 가능 사례가 가장 많음",
  "issue_stats": {
    "candidate_count": 42,
    "usable_goldenset_count": 18,
    "excluded_count": 7
  },
  "selected_cases": ["VAT-REVISION-001", "VAT-REVISION-002"],
  "excluded_reasons": ["단순 문구정비", "관련 조문 불명확"]
}
```

### Step 1. 세법해석정비 데이터 수집

#### 수집 필드

- 정비 사례 ID
- 세목
- 정비 전 문서번호
- 정비 후 문서번호
- 정비 전 해석 요지
- 정비 후 해석 요지
- 관련 법령
- 정비 사유
- 정비일 또는 공개일

#### 실패 예측

- 정비 전/후 문서가 모두 없는 사례가 있을 수 있다.
- 정비 사유가 추상적일 수 있다.
- 법령 개정 때문인지 단순 문구정비인지 구분이 어려울 수 있다.

#### 검수 로직

- 정비 전 문서와 정비 후 문서가 모두 있는 사례를 우선한다.
- 관련 법령 조문이 없는 사례는 낮은 품질로 둔다.
- 단순 오탈자, 문구정비, 서식정리는 정답셋 후보에서 제외한다.

### Step 2. 부가가치세 건 필터링

#### 필터 기준

- 세목 필드가 부가가치세인 사례
- 관련 법령이 부가가치세법, 시행령, 시행규칙인 사례
- 정비 요지에 부가가치세 핵심 쟁점이 포함된 사례

#### 제외 기준

- 법인세, 소득세, 상증세, 지방세 사례
- 조세특례제한법 단독 사례 중 부가가치세 쟁점과 직접 연결되지 않는 사례
- 법령 개정과 연결되지 않는 단순 질의응답 정비

### Step 3. 쟁점 태그 분류

#### 1차 후보 태그

- 간이과세자
- 세금계산서
- 매입세액공제
- 면세/과세 구분
- 공급시기
- 영세율
- 가산세
- 대손세액공제
- 공통매입세액 안분

#### 분류 방식

- 관련 조문 기반 태그
- 정비 전/후 요지 키워드 기반 태그
- 해석례 제목 기반 태그
- 필요 시 LLM 후보 태그 후 룰 기반 검수

#### 검수 로직

- 하나의 사례에 여러 태그가 붙을 수 있다.
- 주 쟁점 1개와 보조 쟁점 N개를 분리한다.
- 주 쟁점이 없으면 정답셋 후보에서 보류한다.

### Step 4. 쟁점별 정비 사례 수 집계

#### 집계 지표

| 지표 | 의미 |
|---|---|
| total_count | 해당 쟁점의 전체 정비 사례 수 |
| usable_count | 정비 전/후 비교가 가능한 사례 수 |
| law_linked_count | 관련 법령 조문이 명확한 사례 수 |
| non_trivial_count | 단순 문구정비가 아닌 사례 수 |
| negative_candidate_count | 반례로 쓸 수 있는 유사 비영향 사례 수 |

#### 선택 기준

단순 총건수보다 `usable_count`, `law_linked_count`, `non_trivial_count`를 우선한다.

```text
issue_score =
  usable_count * 4
  + law_linked_count * 3
  + non_trivial_count * 2
  + negative_candidate_count
  - trivial_count * 2
```

### Step 5. 정답셋 품질 점수 산정

#### 정답셋으로 좋은 사례

- 정비 전 해석례가 존재한다.
- 정비 후 해석례가 존재한다.
- 법령 개정 또는 조문 변경과 연결된다.
- 기존 해석의 대상, 요건, 효과, 예외, 시점 중 무엇이 바뀌었는지 설명 가능하다.
- 유사하지만 영향 없는 반례를 만들 수 있다.

#### 정답셋으로 나쁜 사례

- 단순 오탈자 정비
- 표현만 순화한 사례
- 관련 조문이 불명확한 사례
- 정비 사유가 공개되지 않은 사례
- 사실관계가 너무 특수해 일반화가 어려운 사례

### Step 6. 첫 MVP 쟁점 확정

#### 확정 기준

- issue_score가 가장 높다.
- usable_count가 최소 5건 이상이다.
- 법령 조문 연결이 가능한 사례가 충분하다.
- 반례 문서를 최소 3건 이상 만들 수 있다.

#### 확정 후 조치

- Phase 1의 법령 수집 범위를 해당 쟁점 관련 조문으로 제한한다.
- Phase 2의 집행기준 수집 범위를 해당 쟁점으로 제한하고, 해석례는 정답셋·보조 판단용으로만 사용한다.
- Phase 6의 정답셋은 해당 쟁점의 정비 사례에서 만든다.

## 3. Phase 1. 법령 변경 정규화

### 목적

법령 개정 자료를 그대로 검색에 넣지 않고, Tax Agent가 비교 가능한 구조로 바꾼다.

### Phase 1 입력

- 부가가치세법 개정 조문
- 부가가치세법 시행령 개정 조문
- 신구조문대비표
- 개정 이유
- 시행일
- 적용례
- 경과조치

### Phase 1 출력

```json
{
  "change_id": "VAT-LAW-CHANGE-001",
  "tax_type": "VAT",
  "law_level": "법|시행령|시행규칙",
  "law_name": "부가가치세법",
  "article_path": "제XX조 제X항 제X호",
  "change_type": "요건변경",
  "before_text": "...",
  "after_text": "...",
  "effective_date": "YYYY-MM-DD",
  "application_rule": "...",
  "transition_rule": "...",
  "legal_logic": {
    "target": ["간이과세자"],
    "condition": ["직전 연도 공급대가 기준"],
    "action": ["세금계산서 발급"],
    "effect": ["발급 의무 변경"],
    "exception": ["특정 업종 제외"],
    "time_scope": ["시행일 이후 공급분"]
  },
  "keywords": ["간이과세자", "공급대가", "세금계산서"],
  "review_flags": ["시행일 확인 필요"]
}
```

### Step 1. 수집 범위 확정

#### 수집 법령

MVP에서 반드시 수집할 법령은 아래로 제한한다.

| 구분 | 수집 범위 | 목적 |
|---|---|---|
| 부가가치세법 | 개정 대상 조문과 관련 조문 | 변경 기준점 |
| 부가가치세법 시행령 | 개정 조문과 직접 연결된 조문 | 구체 요건 확인 |
| 부가가치세법 시행규칙 | 서식·절차 변경이 있는 경우만 | 절차 영향 확인 |
| 조세특례제한법 | 영세율·면세 등 직접 관련 시만 | 예외 쟁점 확인 |

#### 수집하지 않는 범위

- 법인세법 전체
- 소득세법 전체
- 모든 조세특례제한법 조문
- 판례 전체
- 과거 모든 개정 이력

#### 수집 단위

- 전체 법령 전문이 아니라 **개정 조문 중심**으로 수집한다.
- 직접 연결된 시행령/시행규칙 조문은 함께 수집한다.
- 적용례와 경과조치는 별도 블록으로 수집한다.

### Step 2. 원천 데이터 수집

#### 데이터 소스

API는 사용자가 제공한다는 전제로 아래 입력 형식을 받는다.

- 법령 본문 API
- 신구조문대비표 API
- 개정 이유 API 또는 공포문 텍스트
- 시행일/부칙 API

#### 수집 필드

| 필드 | 설명 |
|---|---|
| source_id | 원천 데이터 식별자 |
| source_type | 법령, 신구조문대비표, 부칙, 개정이유 |
| law_name | 법령명 |
| article_no | 조문번호 |
| paragraph_no | 항 번호 |
| item_no | 호/목 번호 |
| old_text | 개정 전 문구 |
| new_text | 개정 후 문구 |
| promulgation_date | 공포일 |
| effective_date | 시행일 |
| appendix_text | 부칙/적용례/경과조치 |
| source_url | 출처 URL |

#### 저장 조치

- 원문은 `raw_law_sources`에 저장한다.
- 파싱 결과는 `law_change_units`에 저장한다.
- 원문과 파싱 결과를 `source_id`로 연결한다.

### Step 3. 조문 구조 파싱

#### 추출 대상

- 법령명
- 조문번호
- 조 제목
- 항
- 호
- 목
- 단서
- 괄호 문구
- 부칙
- 적용례
- 경과조치

#### 파싱 방법

- 조문번호는 정규식으로 1차 추출한다.
- 신구조문대비표는 표 컬럼 기준으로 개정 전/후를 분리한다.
- 항/호/목은 계층 구조를 유지한다.
- 단서 문구는 `proviso` 필드로 분리한다.
- 괄호 문구는 삭제하지 않고 별도 보조 필드에 저장한다.

#### 실패 처리

- 조문번호가 없으면 `parse_status = "needs_manual_review"`로 둔다.
- 개정 전/후 문구가 모두 없으면 매칭 대상에서 제외한다.
- 표 구조가 깨진 경우 원문 블록 단위로 임시 저장한다.

### Step 4. 변경 전후 비교

#### 비교 기준

- 삭제된 문구
- 추가된 문구
- 숫자/금액 기준 변경
- 대상 범위 변경
- 의무/선택 표현 변경
- 예외 신설 또는 삭제
- 시행일 변경

#### 추출 예시

```json
{
  "removed_terms": ["직전 연도 공급대가 4,800만원"],
  "added_terms": ["직전 연도 공급대가 8,000만원"],
  "changed_numbers": [
    {
      "from": "4,800만원",
      "to": "8,000만원",
      "meaning": "간이과세 기준금액"
    }
  ],
  "modal_change": {
    "from": "할 수 있다",
    "to": "하여야 한다"
  }
}
```

### Step 5. 법적 논리 단위 추출

#### 논리 단위

법령 변경은 아래 6개 논리 단위로 정규화한다.

| 논리 단위 | 설명 |
|---|---|
| 대상 | 누구에게 적용되는가 |
| 요건 | 어떤 조건을 충족해야 하는가 |
| 행위 | 무엇을 해야 하거나 하지 않아도 되는가 |
| 효과 | 세무상 결론이나 의무가 어떻게 바뀌는가 |
| 예외 | 적용 제외 또는 특례가 있는가 |
| 시점 | 언제부터, 어떤 거래분부터 적용되는가 |

#### 추출 방법

- 1차: 룰 기반 키워드 추출
- 2차: LLM으로 대상/요건/효과 후보 추출
- 3차: 조문 구조와 맞지 않는 후보 제거
- 4차: 사람이 검토해야 할 항목에 flag 부여

### Step 6. 변경 유형 분류

#### 변경 유형

- 대상 변경
- 요건 변경
- 금액 기준 변경
- 절차 변경
- 의무 변경
- 예외 변경
- 서식 변경
- 단순 문구 정비

#### 분류 기준

- 숫자/금액이 바뀌면 `금액 기준 변경`
- `하여야 한다`, `할 수 있다`가 바뀌면 `의무 변경`
- `제외한다`, `포함한다`가 바뀌면 `대상/예외 변경`
- 신고, 제출, 발급, 보관이 나오면 `절차 변경`
- 법령 용어만 정리되면 `단순 문구 정비`

### Step 7. 정규화 결과 검수

#### 검수 체크리스트

- 조문번호가 정확한가
- 시행일이 들어갔는가
- 적용례/경과조치가 분리됐는가
- 변경 전/후 문구가 모두 있는가
- 대상/요건/효과/시점이 비어 있지 않은가
- 단순 문구 정비를 과대평가하지 않았는가

#### 통과 기준

- 필수 필드 누락 없음
- 변경 유형 1개 이상 부여
- 핵심 논리 단위 3개 이상 추출
- 사람이 확인해야 할 사항이 flag로 표시됨

## 4. Phase 2. 기준문서 사전 정규화

### 목적

집행기준을 우선 구조화해 법령 변경과 빠르게 매칭할 수 있게 한다. 해석례는 집행기준만으로 판단 사례가 부족하거나 검증 정답셋이 필요할 때 보조로 사용한다.

### Phase 2 입력

- 부가가치세 집행기준
- 세법해석정비 전후 해석례
- 집행기준 판단에 필요한 관련 법령 조문

### Phase 2 출력

```json
{
  "doc_id": "VAT-ENFORCEMENT-STANDARD-001",
  "doc_type": "집행기준",
  "tax_type": "VAT",
  "title": "...",
  "document_no": "...",
  "published_date": "YYYY-MM-DD",
  "article_refs": ["부가가치세법 제XX조"],
  "issue_tags": ["매입세액공제"],
  "taxpayer_tags": ["개인사업자"],
  "transaction_tags": ["전자상거래"],
  "logic_units": {
    "target": ["개인사업자"],
    "condition": ["세금계산서 수취"],
    "action": ["매입세액 공제 신청"],
    "effect": ["공제 가능 여부"],
    "exception": [],
    "time_scope": []
  },
  "text_blocks": {
    "question": "...",
    "answer": "...",
    "facts": "...",
    "reasoning": "..."
  },
  "embedding_text": "..."
}
```

### Step 1. 문서군 범위 확정

#### MVP 문서군

| 문서군 | 수집량 | 목적 |
|---|---:|---|
| 부가가치세 집행기준 | Phase 0 확정 쟁점 관련 기준 전체 | 1차 영향 후보 탐색 |
| 세법해석정비 전후 해석례 | Phase 0 정답셋 후보 | 검증 및 보조 판단 |
| 기타 해석례 | 판단 사례가 부족할 때만 제한 수집 | 보조 사례 |

#### 제외 문서군

| 문서군 | 제외 이유 |
|---|---|
| 내부 실무지침 | API 확보가 어렵고 이번 MVP의 메인이 아님 |
| 기획재정부 해석 | API 확보와 범위 통제가 어렵기 때문에 1차 제외 |
| 기본통칙 | 집행기준 중심 MVP 이후 보강 대상으로 둠 |
| 판례 | 기존 Tax Agent 자산 활용 가정, 1차 제외 |

#### 우선 수집 쟁점

- Phase 0에서 확정된 첫 MVP 쟁점 1개
- 해당 쟁점의 보조 쟁점
- 해당 쟁점의 반례 생성을 위해 필요한 유사 쟁점

### Step 2. 집행기준 수집

#### 수집 필드

- 기준번호
- 제목
- 관련 조문
- 본문
- 예시
- 주의사항
- 개정일

#### 수집 방식

- Phase 0에서 확정된 쟁점과 직접 관련된 부가가치세 집행기준을 우선 수집한다.
- 집행기준 번호와 관련 조문을 기준으로 수집 범위를 고정한다.
- 하나의 기준 안에 여러 쟁점이 있으면 문단 단위로 나눈다.

#### 분리 조치

- 원칙, 예외, 예시, 주의사항을 분리한다.
- 관련 조문은 별도 배열로 저장한다.
- 예시는 검색에는 포함하되 근거 신뢰도는 본문보다 낮게 둔다.

### Step 3. 집행기준 구조 파싱

#### 파싱 단위

- 기준번호
- 소제목
- 관련 조문
- 원칙 문단
- 예외 문단
- 예시 문단
- 주의사항

#### 실패 처리

- 기준번호가 없으면 보류한다.
- 관련 조문이 없으면 의미 검색 보조군으로만 둔다.
- 예시만 있고 원칙 문단이 없으면 낮은 신뢰도로 둔다.

### Step 4. 해석례 보조 수집

#### 수집 필드

- 문서번호
- 생산일자
- 제목
- 질의
- 회신
- 사실관계
- 관련 법령
- 세목
- 출처 URL

#### 수집 방식

- 세법해석정비 전후 해석례를 우선 수집한다.
- 집행기준만으로 판단 사례가 부족할 때만 같은 쟁점의 해석례를 제한적으로 추가한다.
- 해석례는 집행기준 영향 후보를 보조하거나 검증하는 용도이며, 1차 산출물의 중심 문서군이 아니다.
- 문서번호가 같은 중복 문서는 최신 수집본만 남긴다.

#### 분리 조치

- `question`, `answer`, `facts`, `related_laws`로 분리한다.
- 회신 문구와 사실관계가 섞이면 회신 우선으로 요약한다.
- 관련 법령이 없는 문서는 `article_refs = []`로 두고 낮은 신뢰도로 처리한다.

### Step 5. 문서 구조 파싱

#### 공통 파싱 단위

- 제목
- 본문
- 관련 조문
- 쟁점
- 대상
- 요건
- 효과
- 예외
- 시점

#### chunk 기준

| 문서 유형 | chunk 기준 |
|---|---|
| 집행기준 | 기준번호 또는 문단 |
| 세법해석정비 해석례 | 정비 전/후 회신 비교 단위 |
| 기타 해석례 | 질의 1개 + 회신 1개 |

### Step 6. 태그·메타데이터 부여

#### 필수 태그

- 세목 태그: VAT
- 문서유형 태그: 집행기준, 세법해석정비 해석례, 기타 해석례
- 납세자 태그: 간이과세자, 개인사업자, 영세사업자 등
- 쟁점 태그: 세금계산서, 매입세액공제 등
- 거래 태그: 전자상거래, 부동산임대, 수출입 등
- 조문 태그: 부가가치세법 제XX조

#### 태그 부여 방법

- 조문번호와 문서번호는 룰 기반으로 추출한다.
- 쟁점 태그는 키워드 사전으로 1차 부여한다.
- 대상/요건/효과는 LLM으로 후보를 만들고 룰로 검수한다.
- 태그 신뢰도는 `manual`, `rule`, `llm`, `unknown`으로 구분한다.

### Step 7. 검색 인덱스 생성

#### 인덱스 종류

- 조문번호 인덱스
- 문서번호 인덱스
- 제목/키워드 인덱스
- 쟁점 태그 인덱스
- 납세자/거래 태그 인덱스
- 벡터 인덱스

#### embedding_text 구성

```text
문서유형 + 제목 + 관련 조문 + 질의 요약 + 회신 요약 + 대상 + 요건 + 효과 + 예외
```

### Step 8. 기준문서 품질 검수

#### 검수 체크리스트

- 문서번호 또는 기준번호가 있는가
- 관련 조문이 추출됐는가
- 질의와 회신이 분리됐는가
- 납세자/쟁점/거래 태그가 붙었는가
- 원문 출처가 연결됐는가
- 해석례가 집행기준보다 우선 문서처럼 처리되지 않았는가

#### 통과 기준

- 필수 메타데이터 80% 이상 채움
- 조문 직접 매칭 가능한 문서 비율 확인
- 태그 없는 문서는 별도 보류 목록으로 이동

## 5. Phase 3. 법령 변경과 기준문서 매칭

### 목적

정규화된 법령 변경과 사전 정규화된 기준문서를 연결해 영향 후보를 만든다.

### Step 1. 조문 직접 매칭

#### 방법

- `law_change_units.article_path`와 `tax_documents.article_refs`를 비교한다.
- 같은 조문이면 가장 높은 우선순위를 준다.
- 시행령 조문이 바뀐 경우 위임 법률 조문도 함께 확장 검색한다.

#### 산출물

- 직접 관련 문서 후보
- 연결 조문
- 조문 일치 점수

### Step 2. 핵심 키워드 매칭

#### 방법

- 법령 변경의 `keywords`와 문서 제목/질의/회신/태그를 비교한다.
- 동의어 사전을 적용한다.
- 예: 간이과세자, 간이사업자, 소규모 개인사업자

#### 주의사항

- 키워드만 같고 요건이 다르면 낮은 점수로 둔다.
- “세금계산서”처럼 범용 키워드는 단독으로 높은 점수를 주지 않는다.

### Step 3. 대상·요건·효과 매칭

#### 방법

법령의 논리 단위와 기준문서의 논리 단위를 비교한다.

| 비교 항목 | 예시 |
|---|---|
| 대상 | 간이과세자 vs 개인사업자 |
| 요건 | 공급대가 기준 vs 매출 기준 |
| 행위 | 세금계산서 발급 |
| 효과 | 발급 의무, 공제 가능 여부 |
| 예외 | 특정 업종 제외 |
| 시점 | 시행일 이후 공급분 |

#### 점수 기준

- 대상과 요건이 모두 같으면 강한 후보
- 대상만 같으면 중간 후보
- 키워드만 같으면 낮은 후보
- 효과가 반대면 전문가 검토 후보

### Step 4. 의미 검색 매칭

#### 방법

- 법령 변경 요약을 검색 쿼리로 만든다.
- 벡터 인덱스에서 의미적으로 가까운 문서를 찾는다.
- 조문번호가 없지만 쟁점이 같은 문서를 보완적으로 찾는다.

#### 사용 위치

- 직접 조문 매칭이 부족할 때
- 해석례에 관련 조문이 누락됐을 때
- 집행기준에 관련 조문이 누락됐을 때

### Step 5. 시간 조건 필터링

#### 기준

- 개정 전 생산된 해석례는 영향 가능성이 높다.
- 개정 후 생산된 해석례는 보정 근거가 될 수 있다.
- 시행일 이후 거래분만 적용되는 경우 거래시점 flag를 붙인다.

#### 처리

- `published_date < effective_date`이면 기존 해석 영향 후보로 분류한다.
- `published_date >= effective_date`이면 개정 반영 가능 문서로 분류한다.
- 생산일자 없음은 `date_unknown`으로 두고 낮은 신뢰도로 처리한다.

### Step 6. 후보 점수화

#### 기본 점수

```text
조문 직접 일치: 35점
대상 일치: 15점
요건 일치: 15점
효과 일치 또는 충돌: 15점
핵심 키워드 일치: 10점
의미 검색 상위권: 10점
시간 조건 관련성: 10점
```

#### 신뢰도 구간

- 80점 이상: 높음
- 55점 이상: 중간
- 35점 이상: 낮음
- 35점 미만: 제외 또는 보류

### Step 7. 중복 후보 병합

#### 병합 기준

- 같은 문서번호
- 같은 기준번호
- 같은 조문과 제목
- 같은 집행기준 번호와 개정일

#### 병합 후 유지할 정보

- 가장 높은 점수
- 모든 매칭 근거
- 모든 영향 유형
- 출처 문서 링크

## 6. Phase 4. 영향 가능성 분류

### 목적

후보 문서가 어떤 방식으로 영향을 받을 수 있는지 설명 가능한 형태로 분류한다.

### Step 1. 영향 유형 분류

| 영향 유형 | 조건 |
|---|---|
| 직접 영향 | 변경 조문을 직접 인용 |
| 요건 영향 | 판단 요건이 변경됨 |
| 대상 영향 | 적용 대상이 변경됨 |
| 절차 영향 | 신고, 제출, 발급, 보관 절차 변경 |
| 금액 기준 영향 | 기준금액 또는 한도 변경 |
| 예외 영향 | 적용 제외 또는 특례 변경 |
| 해석 충돌 가능성 | 기존 회신 전제가 개정 후와 다를 수 있음 |
| 낮은 관련성 | 키워드는 같지만 요건이 다름 |

### Step 2. 신뢰도 산정

#### 신뢰도 산정 요소

- 조문 직접 일치 여부
- 관련 조문 존재 여부
- 논리 단위 일치 개수
- 원문 근거 문장 존재 여부
- 생산일자와 시행일 관계
- LLM 추정 의존도

#### 낮은 신뢰도 처리

- 근거 조문이 없으면 낮음으로 내린다.
- 키워드만 일치하면 낮음으로 둔다.
- LLM 설명만 있고 원문 근거가 없으면 제외한다.

### Step 3. 근거 문장 연결

#### 연결할 근거

- 변경 조문 문장
- 신구조문대비표 변경 문구
- 해석례 회신 문장
- 집행기준 본문 문장
- 해석례 회신 근거는 보조 근거로만 사용

#### 원칙

- 최종 리포트에는 원문 전체가 아니라 필요한 근거 요약만 표시한다.
- 출처 식별자는 반드시 남긴다.
- 원문 근거가 없으면 “추정”으로 표시한다.

### Step 4. 낮은 관련성 제거

#### 제거 기준

- 세목이 VAT가 아님
- 납세자 유형이 전혀 다름
- 거래 유형이 전혀 다름
- 조문번호와 쟁점이 모두 다름
- 단순 단어 유사성만 있음

#### 보류 기준

- 조문은 다르지만 효과가 유사함
- 생산일자가 없어 시간 조건을 판단하기 어려움
- 집행기준 원칙 문단이 없고 예시만 있어 추가 검토가 필요함

### Step 5. 전문가 검토 사유 생성

#### 생성 항목

- 왜 검토해야 하는가
- 어떤 조문이 바뀌었는가
- 기존 문서의 어떤 전제가 흔들릴 수 있는가
- 어떤 고객군이 영향을 받을 수 있는가
- 무엇을 추가 확인해야 하는가

#### 금지 항목

- 최종 세무 결론 단정
- 유리/불리 판단 단정
- 신고 방법 단정
- 출처 없는 절세 제안

## 7. Phase 5. 결과물 생성

### 목적

영향 후보를 내부 검토자가 바로 볼 수 있는 변경 예상 목록으로 바꾼다.

### Step 1. 내부 검토 리스트 생성

#### 포함 항목

- 우선순위
- 영향 유형
- 신뢰도
- 변경 조문
- 관련 집행기준 및 보조 해석례
- 영향 가능성 사유
- 확인 필요사항
- 담당자 검토 상태

#### 출력 예시

```text
우선순위 1
- 영향 유형: 요건 영향
- 변경 조문: 부가가치세법 제XX조
- 관련 문서: 국세청 해석례 XXX
- 사유: 기존 회신이 개정 전 기준금액을 전제로 함
- 고객군: 간이과세 개인사업자
- 확인 필요: 시행일 이후 공급분 적용 여부
```

### Step 2. 문서 변경 예상 목록 생성

#### 목록 구분

- 변경 예상 집행기준
- 보조 검토 해석례
- 변경 가능성은 있으나 근거가 부족한 보류 문서

#### 출력 항목

- 문서번호 또는 기준번호
- 기존 문서의 전제
- 법령 개정으로 흔들리는 논리 단위
- 영향 강도
- 검토 질문
- 보류 사유

### Step 3. 신규 검토 논리주제 목록 생성

#### 생성 조건

- 관련 집행기준은 없지만 법령 개정으로 새 대상, 요건, 예외, 시점 문제가 생김
- 집행기준은 있으나 해석례 등 보조 판단 사례가 부족함
- 적용례나 경과조치 때문에 실무 판단 쟁점이 생김

#### 출력 항목

- 논리주제명
- 관련 개정 조문
- 신규 검토가 필요한 이유
- 관련 문서 존재 여부
- 전문가 검토 질문
- 사후 해석례 발생 시 검증 대상 여부

### Step 4. 선택 활용안 분리

#### 선택 활용안

- Tax Agent 응답 가드레일 예시
- 고객군별 영향 요약
- 영업·홍보 소재 초안
- 고객 안내문 초안

#### 주의사항

- 위 항목은 1차 산출물이 아니다.
- 내부 검토리스트가 전문가 검토를 통과한 뒤에만 활용한다.
- 외부 배포 전 전문가 검토 필요
- 법령 해석을 단정하지 않음
- 개별 고객 사실관계 확인 필요

### Step 5. 최종 리포트 검수

#### 검수 체크리스트

- 근거 없는 항목이 없는가
- 조문과 문서번호가 표시됐는가
- 신뢰도와 검토 필요성이 분리됐는가
- 변경 예상 문서와 신규 검토 논리주제가 분리됐는가
- 선택 활용안이 기본 산출물처럼 섞이지 않았는가

## 8. Phase 6. 검증 루프

### 목적

데모가 그럴듯한 문서 생성이 아니라 실제로 영향 후보를 찾는지 확인한다.

### Step 1. 과거 개정 사례 선정

#### 선정 기준

- 부가가치세 개정 사례
- 영세사업자 또는 개인사업자와 관련 있음
- 개정 전후 문구가 명확함
- 관련 해석례/집행기준이 존재함
- 반례 문서도 만들 수 있음

#### 권장 개수

- 대회 MVP: 1개 필수
- 설득력 있는 데모: 2~3개

### Step 2. 정답셋 구축

#### 정답셋 구성

- 실제 영향받은 문서
- 영향받지 않은 유사 문서
- 전문가 검토가 필요한 애매한 문서
- 정답 판단 사유

#### 저장 필드

```json
{
  "case_id": "VAT-VALID-001",
  "change_id": "VAT-LAW-CHANGE-001",
  "positive_docs": ["VAT-INTERP-001"],
  "negative_docs": ["VAT-INTERP-009"],
  "ambiguous_docs": ["VAT-GUIDE-003"],
  "expected_impact_types": ["요건 영향"],
  "reason": "기존 해석례가 개정 전 기준금액을 전제로 함"
}
```

### Step 3. 자동 실행

#### 실행 내용

- Phase 1 정규화 결과를 입력한다.
- Phase 2 인덱스를 대상으로 검색한다.
- Phase 3~5를 한 번에 실행한다.
- 영향 후보 리스트를 저장한다.

### Step 4. 정답셋 비교

#### 평가 지표

| 지표 | 기준 |
|---|---|
| Recall | 실제 영향 문서를 후보로 올렸는가 |
| Precision | 관련 없는 문서를 과도하게 올리지 않았는가 |
| Evidence Rate | 후보마다 근거가 있는가 |
| Safety Rate | 세무 결론을 단정하지 않았는가 |
| Review Usefulness | 전문가가 우선순위를 판단할 수 있는가 |

### Step 5. 실패 원인 분류

#### 누락 원인

- 조문번호 파싱 실패
- 관련 조문 누락
- 동의어 사전 부족
- 요건/효과 추출 실패
- chunk 크기 부적절

#### 오탐 원인

- 키워드만 같음
- 납세자 유형 불일치
- 거래 유형 불일치
- 시행일 조건 불일치
- LLM 추정 과다

### Step 6. 룰·태그·검색 쿼리 개선

#### 개선 대상

- 동의어 사전
- 쟁점 태그 사전
- 조문 연결 테이블
- 점수 가중치
- 낮은 관련성 제거 기준
- LLM 프롬프트

### Step 7. 재실행 및 기록

#### 기록 항목

- 실행일
- 입력 개정 사례
- 후보 개수
- 정답 포함 여부
- 오탐 개수
- 개선 전후 차이
- 남은 한계

## 11. 재검토 결과와 수정 기준

### 11.1 과하게 설계된 부분

현재 설계는 방향은 맞지만 대회 MVP 기준으로는 아래 항목이 과하다.

| 항목 | 기존 설계 | 조정 기준 |
|---|---|---|
| 내부 실무지침 | 실제 내부지침 수집·익명화까지 고려 | 1차 MVP에서 제외 |
| 기획재정부 해석·기본통칙 | 가능하면 수집 | 1차 MVP에서 제외 |
| 벡터 검색 | 매칭 핵심 구성요소처럼 배치 | 조문/논리 매칭 실패 시 보조 검색으로만 사용 |
| 영업·홍보 소재 | 별도 Phase로 생성 | 최종 리포트의 부록 또는 선택 출력으로 축소 |
| 고객군별 영향 요약 | 여러 고객군으로 상세 분리 | 첫 데모는 간이과세자 또는 개인사업자 1개 고객군만 사용 |
| 정답셋 | 2~3개 권장 | 대회 제출 최소 기준은 1개 사례로 충분 |

### 11.2 MVP로 확정할 범위

모호성을 줄이기 위해 1차 구현 범위를 아래로 고정한다.

- 세목: 부가가치세
- 첫 쟁점 후보: 세법해석정비 데이터에서 issue_score가 가장 높은 부가가치세 쟁점 1개
- 법령 범위: 해당 쟁점의 부가가치세법 조문과 직접 연결 시행령 조문
- 문서 범위: 집행기준 관련 기준/문단을 우선 수집하고, 해석례는 세법해석정비 정답셋과 보조 판단용으로만 수집
- 내부자료: 1차 MVP에서 제외
- 결과물: 전문가 검토 리스트 1개를 기본 산출물로 고정
- Agent 가드레일과 영업자료는 예시 출력으로만 둔다.

### 11.3 매칭 로직 보강

점수 합산만으로 후보를 뽑으면 “세금계산서” 같은 범용 키워드 때문에 오탐이 많아진다. 따라서 매칭은 아래 순서로 처리한다.

```text
Hard Filter
  -> Direct Link
  -> Logic Match
  -> Keyword Match
  -> Semantic Match
  -> Evidence Check
  -> Score
```

#### 1. Hard Filter

아래 조건 중 하나라도 실패하면 후보에서 제외하거나 보류한다.

- 세목이 VAT가 아니다.
- 문서유형이 집행기준 또는 보조 해석례가 아니다.
- 법령 변경의 적용 시점과 문서의 판단 시점이 완전히 무관하다.
- 납세자 유형이 명백히 다르다.
- 거래 유형이 명백히 다르다.

#### 2. Direct Link

조문번호가 직접 일치하면 강한 후보로 둔다.

- 법 조문 직접 일치
- 시행령 조문 직접 일치
- 시행령 조문과 위임 법 조문의 연결 일치
- 해석례의 관련 법령 필드 일치

#### 3. Logic Match

키워드보다 아래 논리 단위가 더 중요하다.

| 논리 단위 | 매칭 판단 |
|---|---|
| 대상 | 간이과세자, 개인사업자, 면세사업자 등 |
| 요건 | 공급대가, 매입세액, 발급요건 등 |
| 행위 | 신고, 발급, 수취, 공제, 납부 등 |
| 효과 | 공제 가능, 발급 의무, 가산세 등 |
| 예외 | 제외 업종, 특례, 경과조치 등 |
| 시점 | 시행일, 적용례, 거래시점 등 |

대상과 요건이 모두 맞지 않으면 높은 점수를 줄 수 없다.

#### 4. Keyword Match

키워드는 논리 매칭을 보조하는 용도로만 쓴다.

- 핵심 키워드 2개 이상 일치해야 중간 후보가 될 수 있다.
- 범용 키워드 1개만 일치하면 낮은 후보 또는 제외로 둔다.
- 동의어 사전은 쟁점별로 좁게 만든다.

#### 5. Semantic Match

의미 검색은 누락 방지용이다.

- 조문번호가 누락된 해석례 보완
- 집행기준 조문 누락 문단 보완 검색
- 유사 질의 탐색

의미 검색만으로는 높은 신뢰도를 줄 수 없다.

#### 6. Evidence Check

최종 후보에는 최소 1개 이상의 근거가 있어야 한다.

- 변경 조문 근거
- 관련 조문 근거
- 해석례 회신 근거
- 집행기준 본문 근거
- 해석례 회신 근거는 보조 근거로만 사용

근거가 없으면 `추정`이 아니라 `제외` 또는 `보류`다.

### 11.4 Phase별 실패 예측과 검수 로직

| Step | Phase | 예상 실패 | 검수 로직 |
|---|---|---|---|
| Phase 0 | 세법해석정비 수집 | 정비 전/후 문서가 모두 없음 | 전후 문서가 모두 있는 사례만 정답셋 우선 후보 |
| Phase 0 | 부가가치세 필터링 | 타 세목 또는 조특법 단독 사례 혼입 | 세목 필드와 관련 법령을 동시에 확인 |
| Phase 0 | 쟁점 태그 분류 | 태그가 과다 부여됨 | 주 쟁점 1개와 보조 쟁점 N개로 분리 |
| Phase 0 | 사례 수 집계 | 총건수만 많고 쓸 수 있는 정답이 적음 | usable_count와 law_linked_count를 우선 |
| Phase 0 | 쟁점 확정 | 반례가 없어 precision 검증 불가 | negative 후보 3건 이상 확보 조건 |
| Phase 1 | 수집 범위 확정 | 관련 시행령 누락 | 법 조문에 위임 표현이 있으면 시행령 연결 여부 확인 |
| Phase 1 | 원천 데이터 수집 | 신구조문대비표 누락 | 개정 전/후 문구가 없으면 수동 검토 flag |
| Phase 1 | 조문 구조 파싱 | 조·항·호 분리 오류 | article_path가 원문 조문번호와 일치하는지 샘플 확인 |
| Phase 1 | 변경 전후 비교 | 단순 문구 정비를 실질 변경으로 오판 | 숫자, 의무표현, 대상표현 변경이 없으면 낮은 영향 |
| Phase 1 | 논리 단위 추출 | LLM이 대상/효과를 과잉 추정 | 원문에 없는 논리 단위는 `inferred`로 표시하고 낮은 신뢰도 |
| Phase 1 | 변경 유형 분류 | 여러 유형 중 우선순위 불명확 | 직접 변경 유형 1개와 보조 유형 N개로 분리 |
| Phase 1 | 결과 검수 | 시행일/적용례 누락 | effective_date 또는 application_rule 없으면 통과 불가 |
| Phase 2 | 문서군 범위 확정 | 자료 범위가 계속 확대됨 | 쟁점 1개와 문서 수 상한을 먼저 고정 |
| Phase 2 | 집행기준 수집 | 기준 범위가 계속 확대됨 | Phase 0 확정 쟁점과 관련 조문으로 제한 |
| Phase 2 | 집행기준 구조 파싱 | 문단 chunk가 너무 큼 | 기준번호 또는 소제목 단위로 분리 |
| Phase 2 | 해석례 보조 수집 | 해석례가 주 문서군처럼 확대됨 | 세법해석정비 전후 사례와 부족한 보조 사례로 제한 |
| Phase 2 | 문서 구조 파싱 | 질의와 회신 혼합 | question/answer 필드가 모두 있는지 확인 |
| Phase 2 | 태그 부여 | 태그 과다 부여 | 태그마다 `manual/rule/llm` 출처 기록 |
| Phase 2 | 인덱스 생성 | embedding_text에 잡음 포함 | 제목, 관련 조문, 질의요약, 회신요약만 사용 |
| Phase 2 | 품질 검수 | 조문 없는 문서가 많음 | article_refs 없는 문서는 의미검색 보조군으로 분리 |
| Phase 3 | 조문 직접 매칭 | 시행령-법 연결 누락 | 조문 연결 테이블로 위임 조문 확장 |
| Phase 3 | 키워드 매칭 | 범용 키워드 오탐 | 범용 키워드 단독 일치는 제외 또는 낮음 |
| Phase 3 | 논리 매칭 | 대상은 같지만 요건이 다름 | 대상+요건 동시 일치 없으면 높은 신뢰도 금지 |
| Phase 3 | 의미 검색 | 의미 유사하지만 법적 쟁점 다름 | semantic 후보는 Evidence Check 통과 전까지 보류 |
| Phase 3 | 시간 필터링 | 생산일자 누락 | date_unknown으로 분류하고 높은 신뢰도 금지 |
| Phase 3 | 점수화 | 점수만 높고 근거 없음 | 근거 없는 후보는 점수와 무관하게 제외 |
| Phase 3 | 중복 병합 | 서로 다른 회신을 합침 | 문서번호가 같아도 생산일자/제목이 다르면 별도 유지 |
| Phase 4 | 영향 유형 분류 | 영향 유형 과다 부여 | 주 영향 1개, 보조 영향 N개로 제한 |
| Phase 4 | 신뢰도 산정 | LLM 설명에 의존 | 원문 근거 없는 설명은 신뢰도 산정에서 제외 |
| Phase 4 | 근거 문장 연결 | 근거가 너무 길어짐 | 조문번호·문서번호·요약 근거만 표시 |
| Phase 4 | 낮은 관련성 제거 | 애매한 후보 삭제 | 제외와 보류를 분리하고 보류 사유 기록 |
| Phase 4 | 검토 사유 생성 | 세무 결론처럼 보임 | “가능성”, “검토 필요”, “확인 필요” 표현만 허용 |
| Phase 5 | 내부 검토 리스트 | 출력이 너무 길어짐 | Top 10 또는 점수 55점 이상만 기본 출력 |
| Phase 5 | 문서 변경 예상 목록 | 변경 예상 문서와 보류 문서가 섞임 | 변경 예상/보류/제외를 별도 컬럼으로 분리 |
| Phase 5 | 신규 검토 논리주제 | 해석례 없는 항목을 변경 예상처럼 표현 | “변경 예상 문서”가 아니라 “신규 검토 주제”로 표시 |
| Phase 5 | 선택 활용안 | Agent/영업자료가 기본 산출물처럼 섞임 | 선택 활용안 섹션을 내부 검토리스트 뒤로 분리 |
| Phase 5 | 최종 검수 | 출처 없는 문장 포함 | 모든 항목에 source_id 또는 doc_id 요구 |
| Phase 6 | 사례 선정 | 정답셋이 임의적임 | 왜 정답/반례인지 판단 사유 기록 |
| Phase 6 | 정답셋 구축 | positive만 있고 negative 없음 | 유사하지만 영향 없는 반례를 반드시 포함 |
| Phase 6 | 자동 실행 | 파이프라인 일부만 검증 | Phase 1~5 전체 실행 결과로 평가 |
| Phase 6 | 정답셋 비교 | 정성평가만 남음 | Recall, Precision, Evidence Rate를 수치화 |
| Phase 6 | 실패 분류 | 원인 분류가 모호함 | 누락/오탐/근거부족/안전성 문제로 구분 |
| Phase 6 | 개선 | 프롬프트만 수정 | 룰, 태그, 조문연결, 점수 가중치를 함께 조정 |
| Phase 6 | 재실행 | 개선 효과 추적 불가 | 전후 후보 수와 정답 포함 여부를 기록 |

### 11.5 최종 판단

- 현재 방향은 맞다.
- 다만 1차 MVP는 더 줄여야 한다.
- 핵심은 “많은 데이터”가 아니라 “정규화된 법령 변경과 정규화된 기준문서의 설명 가능한 매칭”이다.
- 대회 제출물에서는 Phase 1~4를 핵심으로 보여주고, Phase 5~6은 결과 활용과 검증으로 짧게 보여주는 구성이 가장 안전하다.
