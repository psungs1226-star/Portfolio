# MVP Phase and Review Plan

## 목적

이 문서는 AX 인재전쟁 예선 제출용 MVP를 만들기 위한 phase-step 구성과 검수자 역할을 정리한다.

대상 기업은 `카카오페이증권` 하나로 고정한다. MVP 주제는 `SCHD 백테스트 수익률 시각화`가 아니라 `해외 ETF 모으기 과거 수익률 분포 기반 참고 범위 UX`로 고정한다.

핵심 문제는 카카오페이증권이 `주식 모으기`와 해외주식 경험을 확장할 때, 초보 사용자가 과거 평균 수익률을 미래 성과나 특정 ETF 추천으로 오해할 수 있다는 점이다. MVP는 과거 3년·5년·10년 일별 시작점 수익률 분포를 계산하고, 과거 최저치·평균·최고치를 앞으로의 매일 적립 참고 범위로 보여준다.

## 고정 원칙

- SCHD는 추천 종목이 아니라 예시 fixture로만 사용한다.
- `예상 수익률`, `95% 확률`, `추천`, `안정적`, `초보자에게 적합`, `장기적으로 유리` 표현을 쓰지 않는다.
- 결과는 `과거 수익률로 잡아본 범위`, `보장 아님`으로 표시한다.
- 첫 화면은 모바일 초보자 UX를 우선한다.
- 평균만 보여주지 않고 과거 최저치와 과거 최고치를 함께 이해시키는 구조를 따른다.
- 실시간 API, API 키, 비밀정보, 개인 투자정보 입력은 MVP 범위에서 제외한다.
- README, SKILL.md, 웹 MVP, 제출 답변 5문항은 같은 문제 정의와 같은 표현 원칙을 따라야 한다.

## 역할 구분

| 역할 | 책임 | 금지 |
|---|---|---|
| 조사자 | 공개 근거, 데이터 출처, 카카오페이증권 서비스 맥락 확인 | 문제 정의 확정, 구현, 최종 평가 |
| 분석자 | 문제 정의, UX 가치, 제출 문항 논리 구조 확정 | 새 근거 생성, 코드 작성, 최종 평가 |
| 실행자 | phase 문서, 웹 MVP, 플러그인 파일, README, 제출 구조 작성 | 문제 정의 임의 변경, 코드 리뷰, 최종 판정 |
| 코드 검토자 | 구조, 빌드, 보안, 표현 위험, README-구현 정합성 검토 | 직접 수정, 새 조사, 최종 제출 판정 |
| 평가자 | 답변 5문항, README, logs, 플러그인, 웹 MVP의 최종 정합성 점검 | 조사, 구현, 코드 수정 |

## Phase

Phase 이름은 `0-mvp-schd-frontend`로 둔다.

목표는 SCHD 예시 데이터를 사용해 과거 3년·5년·10년 수익률 분포와 앞으로의 매일 적립 참고 범위를 모바일 앱형 웹 프론트엔드로 보여주고, 이 UX를 Codex 플러그인 제출물의 실제 동작 예시로 연결하는 것이다.

## Step 0. project-contract

### 실행자 작업

- `CLAUDE.md`, `docs/PRD.md`, `docs/ARCHITECTURE.md`, `docs/ADR.md`를 만든다.
- Harness 실행 기준, 제출 구조, 기술 스택, 모바일 초보자 UX 원칙, 투자추천 금지 규칙을 명시한다.
- 기술 스택은 MVP 범위에서 Vite, React, TypeScript, 고정 fixture 기반 계산으로 제한한다.

### 코드 검토자 검수

- Harness가 요구하는 계약 문서가 존재하는지 확인한다.
- `agents.md`의 제출 조건과 충돌하는 규칙이 없는지 확인한다.
- `추천`, `예상`, `95% 확률` 등 금지 표현이 계약 문서에 허용되어 있지 않은지 확인한다.

### 평가자 검수

- 문제 정의가 카카오페이증권의 `주식 모으기`, 해외주식 확장, 초보자 UX, 금융소비자보호와 연결되는지 확인한다.
- 제출 문항 1~5와 README에 재사용 가능한 핵심 문장이 들어 있는지 확인한다.

### 사용자 확인

- 최종 문제 정의가 `해외 ETF 모으기 과거 수익률 분포 기반 참고 범위 UX`로 충분히 설득력 있는지 확인한다.
- 카카오페이증권 대상 문제로 보이는지, 일반 투자 앱 아이디어처럼 보이지 않는지 확인한다.
- SCHD를 예시 fixture로만 쓰는 방향에 동의하는지 확인한다.
- 이 단계가 끝나면 사용자가 `문제 정의 승인` 여부를 명시한다. 승인 전에는 웹 구현 단계로 넘어가지 않는다.

### Acceptance Criteria

```bash
test -f CLAUDE.md
test -f docs/PRD.md
test -f docs/ARCHITECTURE.md
test -f docs/ADR.md
```

## Step 1. mobile-ux-spec

### 실행자 작업

- 모바일 앱형 UX 명세를 작성한다.
- 입력 화면, 가정 확인, 한 줄 해석, 핵심 결과 카드, 그래프 상세, 위험 설명, 오류 상태를 정의한다.
- 컴포넌트별 상태를 명시한다: 기본, 로딩, 빈값, 오류, 비활성, 확장, 축소.

### 코드 검토자 검수

- UI 명세가 구현 가능한 컴포넌트 단위로 쪼개졌는지 확인한다.
- 390px 모바일 폭에서 한 화면에 과도한 정보가 들어가지 않는지 확인한다.
- CTA가 투자 실행 유도처럼 보이지 않는지 확인한다.

### 평가자 검수

- 초보자가 통계 용어 없이 핵심 의미를 이해할 수 있는지 확인한다.
- `수익률 계산기`가 아니라 `리스크 설명 UX`로 읽히는지 확인한다.

### 사용자 확인

- 모바일 앱 흐름이 초보자에게 과하지 않은지 확인한다.
- 첫 화면, 결과 첫 화면, 상세 화면의 순서가 심사자에게 설명하기 쉬운지 확인한다.
- `추천`, `예상`, `확률`처럼 보이는 UX 요소가 없는지 확인한다.
- 이 단계가 끝나면 사용자가 `UX 흐름 승인` 여부를 명시한다. 승인 전에는 화면 구현을 진행하지 않는다.

### Acceptance Criteria

```bash
test -f docs/UX.md
```

## Step 2. frontend-scaffold

### 실행자 작업

- `submission/src/web/`에 웹 프론트엔드 프로젝트를 만든다.
- 모바일 우선 단일 페이지 앱 구조를 만든다.
- 기본 레이아웃, 디자인 토큰, 공통 컴포넌트 폴더를 만든다.
- 무거운 UI 라이브러리 의존을 피하고, 필요한 접근성 동작은 로컬 컴포넌트로 구현한다.

### 코드 검토자 검수

- `npm run build`가 통과하는지 확인한다.
- 제출 루트인 `submission/src/` 안에 웹 MVP가 포함되어 있는지 확인한다.
- 패키지에 불필요한 의존성이나 외부 API 키가 들어가지 않았는지 확인한다.

### 평가자 검수

- 웹 MVP가 플러그인의 실제 동작 예시로 설명될 수 있는지 확인한다.

### 사용자 확인

- 웹 MVP의 기본 화면 톤이 카카오페이증권/모바일 금융 서비스 맥락과 어긋나지 않는지 확인한다.
- 앱형 화면인지, 데스크톱 대시보드처럼 보이지 않는지 확인한다.
- 이 단계는 구조 확인 단계이므로 세부 문구보다 전체 골격만 승인한다.

### Acceptance Criteria

```bash
cd submission/src/web
npm run build
```

## Step 3. schd-fixture-engine

### 실행자 작업

- SCHD 예시 fixture를 추가한다.
- 과거 3년·5년·10년 일별 시작점 수익률 분포 계산 모듈을 만든다.
- 과거 최저치, 평균, 최고치를 앞으로의 매일 적립 참고 범위로 투영한다.
- fixture의 데이터 기간, 가정, 한계를 문서화한다.

### 코드 검토자 검수

- 계산 로직이 UI 컴포넌트와 분리되어 있는지 확인한다.
- 실시간 외부 API나 API 키가 없는지 확인한다.
- 수익률 예측처럼 보이는 함수명, 변수명, 문구가 없는지 확인한다.

### 평가자 검수

- SCHD가 추천 ETF가 아니라 `분석 대상 예시`로만 설명되는지 확인한다.
- 데이터 출처와 한계가 README와 제출 답변에 반영될 수 있는지 확인한다.

### 사용자 확인

- SCHD fixture의 사용 범위가 제출물에서 부담스럽지 않은지 확인한다.
- 데이터 기간, 환율, 배당 재투자 가정이 과장되어 보이지 않는지 확인한다.
- 숫자가 지나치게 수익률 홍보처럼 보이면 이 단계에서 방향을 되돌린다.

### Acceptance Criteria

```bash
cd submission/src/web
npm run build
npm test
```

## Step 4. beginner-input-flow

### 실행자 작업

- 초보자용 입력 흐름을 구현한다.
- 기본값은 `SCHD`, 매일 `5,000원`, `5년`, `원화 기준`으로 두고, 기간과 하루 금액 선택지를 제공한다.
- 환율과 배당 재투자는 고급 설정으로 접는다.
- `분석 대상 ETF`라는 표현을 사용한다.

### 코드 검토자 검수

- 모든 입력에 label, error text, keyboard focus가 있는지 확인한다.
- 빈값, 잘못된 금액, 지원하지 않는 기간 입력이 깨지지 않는지 확인한다.
- `추천 ETF`, `유망 ETF`, `매수` 같은 표현이 없는지 확인한다.

### 평가자 검수

- 초보자가 첫 화면에서 해야 할 일이 하나로 보이는지 확인한다.
- 입력 화면이 투자 실행 화면이 아니라 분석 조건 설정 화면으로 보이는지 확인한다.

### 사용자 확인

- 입력값 기본값인 `SCHD`, `매일 5,000원`, `5년`, `원화 기준`과 선택지가 MVP 예시로 자연스러운지 확인한다.
- 고급 설정이 초보자에게 부담스럽지 않게 접혀 있는지 확인한다.
- 버튼이나 라벨이 투자 실행을 유도하는 느낌이 없는지 확인한다.

### Acceptance Criteria

```bash
cd submission/src/web
npm run build
```

## Step 5. risk-first-report

### 실행자 작업

- 결과 첫 화면을 구현한다.
- 표시 순서는 `그래프`, `고지 라벨`, `넣는 돈`, `과거 최저치`, `과거 평균`, `과거 최고치`로 한다.
- 모든 결과 화면에 `과거 수익률로 잡아본 범위 · 보장 아님` 라벨을 노출한다.

### 코드 검토자 검수

- 최고 수익률이 첫 KPI로 강조되지 않았는지 확인한다.
- 결과 문구에 금지 표현이 없는지 확인한다.
- 긴 문장이 모바일 카드 밖으로 넘치지 않는지 확인한다.

### 평가자 검수

- 심사자가 보기에 금융소비자보호형 AX 도구로 읽히는지 확인한다.
- 카카오페이증권의 주식 모으기 확장 문제와 연결되는지 확인한다.

### 사용자 확인

- 결과 첫 화면이 `수익률 자랑`이 아니라 `위험과 범위 설명`으로 보이는지 확인한다.
- 한 줄 해석이 초보자에게 바로 이해되는지 확인한다.
- 평균뿐 아니라 과거 최저치와 과거 최고치가 충분히 눈에 들어오는지 확인한다.
- 이 단계는 가장 중요한 사용자 검수 지점이다. 사용자가 `결과 화면 승인`을 명시하기 전에는 시각화 상세를 확장하지 않는다.

### Acceptance Criteria

```bash
cd submission/src/web
npm run build
```

## Step 6. mobile-visualization

### 실행자 작업

- 모바일 기본 그래프를 3개로 제한해 구현한다.
- 그래프는 앞으로의 매일 적립 가정에서 `넣은 돈`, `과거 최저치`, `과거 평균`, `과거 최고치`를 꺾은선으로 보여준다.
- 평균, 분위, 역사적 최고/최저, 상세 통계는 `자세히 보기`로 접는다.

### 코드 검토자 검수

- 390px 모바일 폭에서 그래프, 축, 라벨, 카드 텍스트가 겹치지 않는지 확인한다.
- 히스토그램, 박스플롯, `95% 신뢰구간`이 기본 화면에 직접 노출되지 않는지 확인한다.
- 그래프마다 짧은 해석 문구가 있는지 확인한다.

### 평가자 검수

- 그래프가 수익률 홍보가 아니라 결과 범위와 위험 설명으로 읽히는지 확인한다.
- 과거 최저치와 과거 최고치가 평균과 함께 충분히 보이는지 확인한다.

### 사용자 확인

- 그래프 3개가 모바일에서 읽기 쉬운지 확인한다.
- 그래프 라벨과 색상이 투자 성과를 과도하게 강조하지 않는지 확인한다.
- 상세 통계가 기본 화면에 과하게 노출되지 않고 `자세히 보기`에 들어갔는지 확인한다.
- 390px 모바일 화면 기준으로 텍스트, 그래프, 카드가 겹치지 않는지 확인한다.

### Acceptance Criteria

```bash
cd submission/src/web
npm run build
```

- `submission/src/skills/<name>/SKILL.md`를 만든다.

- `logs/` 제출 위치와 검증 방법을 정리한다.

### 코드 검토자 검수

- 제출 필수 구조가 맞는지 확인한다.
- `plugin.json` 외에 실제 동작 요소가 있는지 확인한다.
- README의 사용 예시와 웹 MVP, SKILL.md의 동작 설명이 일치하는지 확인한다.

- 제출 답변 5문항, README, 로그, 플러그인, 웹 MVP가 같은 문제를 설명하는지 확인한다.
- 공개 근거로 입증 가능한 문제 정의인지 확인한다.
- 정상 입력과 예외 입력 검증 결과가 README 또는 답변에 반영되어 있는지 확인한다.

## 사용자 승인 게이트

사용자 확인은 코드 검토자나 평가자의 검수를 대체하지 않는다. 사용자는 기술적 빌드보다 제출 전략, 문제 정의, UX 설득력, 최종 제출 의사결정을 확인한다.

| 게이트 | 시점 | 사용자 확인 질문 | 다음 단계 |
|---|---|---|---|
| 문제 정의 승인 | Step 0 완료 후 | 이 문제가 카카오페이증권 예선 주제로 충분히 설득력 있는가? | 승인 시 Step 1 진행 |
| UX 흐름 승인 | Step 1 완료 후 | 초보자 모바일 앱 흐름이 과하지 않고 심사자에게 설명 가능한가? | 승인 시 Step 2 진행 |
| SCHD fixture 승인 | Step 3 완료 후 | SCHD가 추천처럼 보이지 않고 예시 데이터로만 보이는가? | 승인 시 Step 4 진행 |
| 결과 화면 승인 | Step 5 완료 후 | 결과 화면이 수익률 홍보가 아니라 리스크 설명으로 보이는가? | 승인 시 Step 6 진행 |
| 제출 승인 | Step 7 완료 후 | README, SKILL.md, 웹 MVP, answers.md, logs가 한 방향으로 정리되었는가? | 승인 시 ZIP 생성 및 제출 준비 |

사용자가 보류하거나 수정 의견을 주면 해당 phase의 실행자에게 되돌린다. 코드 검토자와 평가자는 직접 수정하지 않고, 수정 요청과 재검수 항목만 남긴다.

## 최종 주제 문장

카카오페이증권의 해외 ETF 모으기 확장 과정에서, 초보 사용자가 과거 평균 수익률을 미래 성과로 오해하지 않도록 과거 3년·5년·10년 일별 시작점 수익률 분포와 앞으로의 매일 적립 참고 범위를 모바일 UX로 설명하는 Codex 플러그인이다.
