# Self-Validation and Fix Loop

이 문서는 Codex가 자체검증 후 발견한 문제를 어떻게 수정하고 재검증해야 하는지 고정한다. 목적은 `검토만 하고 넘어가는 것`을 막고, 수정 가능한 문제는 사용자 승인 전에 먼저 해결하는 것이다.

## 핵심 규칙

Codex는 각 phase 산출물을 만든 뒤 아래 루프를 수행한다.

1. 자체검증 실행
2. 이슈 분류
3. 수정 가능 항목 즉시 수정
4. 수정 diff 또는 변경 요약 기록
5. 동일 검증 재실행
6. reviewer 모델 재검수
7. 남은 이슈만 사용자 승인 패키지에 전달

사용자에게 승인 요청을 할 수 있는 조건:

- `blocker` 이슈가 0개다.
- `must_fix` 이슈가 0개이거나, 수정 불가능한 이유와 사용자 판단 질문이 명확하다.
- 수정 후 재검증 결과가 남아 있다.
- reviewer 결과가 `pass`이거나, `revise`가 제출 리스크가 아닌 이유가 명시되어 있다.
- 다음 phase로 넘어가도 데이터/기획/코드 정합성이 깨지지 않는다.

## 이슈 등급

### blocker

다음 phase로 넘어가면 안 되는 이슈다.

예:

- 필수 산출물 누락
- JSON/Markdown/ZIP 형식 검증 실패
- hard exclusion 무시
- 비밀정보, 토큰, API 키, 비공개 개인정보 포함
- 내부 매출 데이터 없이 매출/ROAS 확정
- 제출 요구 파일 누락

처리:

- 사용자 승인 요청 금지
- 즉시 수정
- 수정 후 동일 검증 재실행
- 해결 불가능하면 phase를 `blocked`로 표시하고 사용자에게 원인만 보고

### must_fix

제출 품질이나 기획 정합성에 직접 영향을 주는 이슈다.

예:

- 추천 점수와 자연어 설명 충돌
- 제품 리스크 태그 누락
- 후보 데이터 부족인데 고신뢰 추천
- README와 로그 설명 불일치
- reviewer `fail`

처리:

- 원칙적으로 사용자 승인 전 수정
- 수정 후 reviewer 재검수
- 수정하지 않고 넘길 경우 사용자에게 명시적 승인 필요

### should_fix

수정하면 품질이 좋아지지만 다음 phase를 막지는 않는 이슈다.

예:

- 문장 표현이 약함
- 샘플 수가 최소 기준은 넘지만 균형이 아쉬움
- 로그 설명이 짧음
- 출력 예시가 더 명확해질 수 있음

처리:

- 시간이 허용되면 수정
- 남길 경우 승인 패키지의 `남은 리스크`에 포함

### note

기록만 필요한 관찰이다.

예:

- 내부 데이터 부재 한계
- 공개 데이터 기반 추론 한계
- 다음 반복에서 개선할 후보

처리:

- 로그 또는 reviewer report에 남김
- 승인 차단 사유는 아님

## 수정 루프 표준 포맷

각 phase 수정 루프는 아래 형식으로 로그를 남긴다.

```json
{
  "phase_id": "phase_4_product_influencer_matching",
  "validation_run_id": "phase_4_run_001",
  "issues": [
    {
      "severity": "blocker | must_fix | should_fix | note",
      "finding": "",
      "affected_files": [],
      "fix_action": "",
      "status": "open | fixed | deferred | blocked",
      "revalidation_result": ""
    }
  ],
  "can_request_user_approval": false
}
```

## Phase별 수정 루프

### Phase 0. 문제와 공개 근거 고정

자체검증:

- 공개 근거 URL 수 확인
- 문제 정의 문장 일관성 확인
- 매출 단정 표현 검색

수정 루프:

- 근거 부족이면 문제 범위를 축소한다.
- 문서 간 문제 문장이 다르면 하나로 통일한다.
- 단정 표현은 `가설`, `가능성`, `내부 데이터 연결 시 검증`으로 바꾼다.

재검증:

- `PLUGIN_PLAN.md`, README 초안, 최신 검증 로그의 문제 문장 재검색

### Phase 1. 제품 온톨로지 고정

자체검증:

- MVP 제품 9개 필드 완성도 확인
- 리스크 태그 누락 확인
- 성별 기반 추천 규칙 검색

수정 루프:

- 누락 필드는 제품 JSON에 추가한다.
- 의료적 표현은 cosmetic/appearance 수준으로 낮춘다.
- 근거 부족 제품은 `needs_more_product_evidence`로 표시하거나 MVP에서 제외한다.

재검증:

- JSON 문법 검사
- 제품별 필수 필드 개수 확인

### Phase 2. 인플루언서 후보 수집

자체검증:

- 후보 수, 세그먼트 수, 콘텐츠 관찰치 수 집계
- URL 누락 확인
- 댓글 원문/민감정보 저장 여부 확인
- 필수 필드 충족률 계산

수정 루프:

- URL 없는 후보는 보완하거나 제외한다.
- 원문 댓글은 삭제하고 의도 테마만 남긴다.
- 세그먼트 부족 시 검색어를 확장해 대체 후보를 수집한다.
- 필수 필드 부족 후보는 `needs_more_data`로 낮춘다.

재검증:

- 후보 30명 중 24명 이상 필수 필드 충족 여부 재계산
- 세그먼트별 80% 기준 재확인

### Phase 3. 인플루언서 파라미터 정규화

자체검증:

- primary concern 근거 수 확인
- `unknown` 임의 보완 여부 확인
- hard exclusion 분류 확인

수정 루프:

- 근거 1회 고민은 secondary로 낮춘다.
- 추정값은 `unknown`으로 되돌린다.
- hard exclusion이 약화되었으면 차단 규칙으로 복구한다.

재검증:

- 정규화 샘플 5명 재검토
- 원천 데이터 추적 가능성 확인

### Phase 4. 제품-인플루언서 매칭

자체검증:

- hard exclusion 선적용 확인
- 점수와 설명 일치 확인
- `no_seed` 가능성 확인
- 제품별 추천 쏠림 확인

수정 루프:

- hard exclusion 무시 추천은 제거한다.
- 점수/설명 충돌은 점수 계산 또는 설명을 수정한다.
- 데이터 부족 추천은 `needs_more_data` 또는 `no_seed`로 낮춘다.
- 추천 쏠림이 심하면 대조군/실험군 설계를 재검토한다.

재검증:

- 대표 정상 케이스와 위험 케이스 재실행
- reviewer 모델 재검수

### Phase 5. 시딩 수행 브리프

자체검증:

- 브리프 필수 항목 존재 확인
- 금지 표현 검색
- KPI와 결과 수집 연결 확인

수정 루프:

- 과장 문구를 체감/루틴/외관 표현으로 낮춘다.
- 누락 KPI를 추가한다.
- 제품 사용 주의 문구를 추가한다.
- 결과 수집 필드와 브리프를 연결한다.

재검증:

- 가장 리스크 높은 브리프 2-3개 재리뷰
- reviewer 모델 재검수

### Phase 6. 결과 수집 및 성과 해석

자체검증:

- 공개 KPI와 내부 KPI 분리 확인
- 사후 KPI 변경 여부 확인
- 실패 사례 누락 확인

수정 루프:

- 출처가 섞인 지표를 분리한다.
- 매출 단정 표현을 제거한다.
- 실패 케이스를 복원하고 원인 태그를 붙인다.
- 사후 변경 KPI는 별도 `post_hoc_note`로 기록한다.

재검증:

- 정상 예시와 예외 예시 모두 제출 답변에 남는지 확인

### Phase 6A. 신제품 입력 기반 기존 DB 랭킹

자체검증:

- 신제품 입력 JSON 필수 필드 존재 확인
- 신제품 태그가 기존 제품 온톨로지 필드로 매핑되는지 확인
- 기존 인플루언서 DB 전체를 대상으로 랭킹했는지 확인
- hard exclusion이 점수 계산보다 먼저 적용되는지 확인
- `ready_for_matching`, `review_required_before_matching`, `needs_more_data` 표시 우선순위 확인
- 점수 trace와 자연어 추천 사유 일치 확인

수정 루프:

- 필수 필드가 누락되면 신제품 입력을 보완하거나 `insufficient_product_input`으로 중단한다.
- 온톨로지 매핑이 약하면 새 태그를 임의 생성하지 않고 기존 태그 중 가장 가까운 항목과 `mapping_confidence`를 함께 남긴다.
- DB 일부만 랭킹했다면 전체 `influencer_profiles.jsonl` 기준으로 재실행한다.
- hard exclusion 후보가 상위 추천으로 올라오면 추천에서 제거하고 `no_seed` 또는 `review_required`로 낮춘다.
- `needs_more_data` 후보가 고신뢰 추천처럼 보이면 표시 그룹과 설명을 수정한다.
- 팔로워 수 중심 설명은 피부 고민, 콘텐츠 형식, 시장, 리스크 근거 중심으로 다시 쓴다.

재검증:

- 상위 후보, 보류 후보, 데이터 부족 후보가 각각 분리되어 보이는지 확인
- `new_product_matching_trace.jsonl`의 점수 항목과 랭킹 결과를 대조
- reviewer 모델 재검수

### Phase 6B. 신제품 리서치 갭 판단

자체검증:

- ready 후보 수, 핵심 세그먼트 커버리지, 데이터 freshness 계산 여부 확인
- 추가 리서치 트리거가 사전 조건과 연결되는지 확인
- 검색 쿼리가 신제품 피부 고민, 콘텐츠 형식, 시장 태그와 연결되는지 확인
- 기존 DB 기반 랭킹 결과가 보존되는지 확인
- 리서치 범위가 부족 세그먼트로 제한되는지 확인

수정 루프:

- 정량 근거 없이 리서치 필요 여부를 판단했다면 `research_optional`로 낮추고 기준을 다시 계산한다.
- 검색어가 광범위하면 신제품 태그와 부족 세그먼트 기준으로 좁힌다.
- 기존 DB 결과를 덮어썼다면 원본 랭킹을 복원하고 리서치 계획을 별도 파일로 분리한다.
- 공개 데이터 접근 불안정성이나 출처 리스크가 빠졌으면 리스크 항목에 추가한다.

재검증:

- 리서치 필요/불필요/선택 가능 판단 중 하나로 명확히 분류되었는지 확인
- 제안 검색어가 신제품 태그와 연결되는지 재확인
- 사용자 승인 전 실행 금지 조건이 남아 있는지 확인

### Phase 6C. 신제품 추가 리서치 및 재랭킹

자체검증:

- 신규 후보 출처 URL과 콘텐츠 관찰치 추적 가능성 확인
- 댓글 원문과 민감 개인정보 미저장 확인
- 기존 후보와 신규 후보 중복 제거 확인
- 신규 후보가 Phase 3 정규화 규칙을 통과했는지 확인
- 리프레시 전후 랭킹 diff와 변경 사유 존재 확인

수정 루프:

- 출처 URL이 없는 신규 후보는 `needs_more_data`로 낮추거나 제외한다.
- 댓글 원문 또는 민감 개인정보가 저장되었으면 삭제하고 의도 테마만 남긴다.
- 중복 후보는 기존 후보 ID에 merge하고 신규 후보로 중복 추천하지 않는다.
- 정규화 기준을 통과하지 못한 후보는 `review_required_before_matching` 또는 `needs_more_data`로 표시한다.
- 랭킹 변화 설명이 없으면 점수 trace와 변경 사유를 추가한다.
- 공개 후보 발견이나 조회수만으로 매출 효과를 주장하는 표현은 제거한다.

재검증:

- merge 전후 후보 수와 상태 분포를 재계산
- 리프레시 전후 상위 랭킹 diff 재확인
- reviewer 모델 재검수

### Phase 7. 5.4 Mini 리뷰어 검수

자체검증:

- reviewer report 존재 확인
- `fail`, `revise`, `pass` 분리
- required fixes 추적 확인

수정 루프:

- `fail`은 해당 phase로 되돌려 수정한다.
- `must_fix`는 수정 후 reviewer를 다시 실행한다.
- `revise`는 수정 또는 명시적 한계로 분류한다.

재검증:

- reviewer report를 재생성한다.
- `fail` 0개가 될 때까지 반복한다.

### Phase 8. 반복 학습

자체검증:

- 결과 기반 룰 변경과 가설 구분 확인
- 과잉 일반화 확인
- 다음 실험 질문 존재 확인

수정 루프:

- 근거 약한 변경은 `hypothesis_only`로 낮춘다.
- 실패 원인 없는 룰 변경은 되돌린다.
- 다음 실험 질문을 명확히 쓴다.

재검증:

- 변경된 룰이 기존 제품/후보 파라미터와 충돌하지 않는지 확인

### Phase 9. 제출 패키징

자체검증:

- 필수 파일 존재 확인
- ZIP 생성 및 압축 해제 검증
- JSON 문법 검증
- 비밀정보 검색
- README와 로그 충돌 확인

수정 루프:

- 누락 파일을 생성하거나 패키징에서 제외 사유를 기록한다.
- 깨진 JSON을 수정한다.
- 비밀정보가 발견되면 즉시 제거하고 로그를 재생성한다.
- 답변과 구현 범위가 다르면 답변을 낮추거나 구현을 보강한다.

재검증:

- ZIP 압축 해제 후 필수 파일 재확인
- 최종 reviewer 재검수

## 승인 요청 금지 조건

아래 중 하나라도 있으면 사용자에게 “승인해도 되나요?”라고 묻지 않는다.

- `blocker`가 남아 있음
- reviewer `fail`이 남아 있음
- 필수 산출물 누락
- 형식 검증 실패
- 비밀정보 또는 비공개 개인정보 발견
- hard exclusion 위반
- 내부 데이터 없이 매출/ROAS 확정
- 수정 후 재검증 기록 없음
