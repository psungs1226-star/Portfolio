# Pre-Approval Protocol

이 문서는 사용자가 승인하기 전에 Codex가 반드시 먼저 수행해야 하는 자체 검토 절차를 고정한다. 사용자는 원자료를 처음부터 다시 뒤지지 않고, Codex가 준비한 검토 패키지를 보고 승인/수정/보류를 판단할 수 있어야 한다.

## 승인 요청 전 원칙

Codex는 어떤 phase에서도 바로 사용자 승인을 요청하지 않는다. 먼저 아래 6단계를 끝낸 뒤 승인 요청을 한다.

1. 산출물 존재 확인
2. 스키마/형식 검증
3. 내용 정합성 검토
4. 리스크/과장/누락 검토
5. reviewer 모델 검수 결과 정리
6. 사용자용 승인 패키지 작성

자체검증에서 문제가 발견되면 바로 승인 요청으로 넘어가지 않는다. `submission/SELF_VALIDATION_FIX_LOOP.md`의 이슈 등급과 수정 루프를 적용해 수정 가능한 문제를 먼저 고치고, 같은 검증을 다시 실행한 뒤 사용자에게 전달한다.

승인 요청 메시지에는 반드시 아래 5가지를 포함한다.

- 무엇을 승인해야 하는지
- Codex가 먼저 검토한 항목과 결과
- 발견된 리스크와 수정/보류 판단
- 사용자가 봐야 할 핵심 샘플 또는 파일 위치
- 사용자가 답해야 할 구체 질문

## 승인 패키지 표준 형식

사용자에게 승인을 요청할 때는 아래 형식을 따른다.

```markdown
## 승인 요청: Phase N - 이름

### Codex 사전 검토 결과
- 산출물:
- 형식 검증:
- 내용 정합성:
- 리스크 검토:
- reviewer 결과:

### 사용자가 확인할 핵심
- 확인 1:
- 확인 2:
- 확인 3:

### 남은 리스크
- 리스크 1:
- 리스크 2:

### 제안 판단
- Codex 권고: 승인 | 수정 후 승인 | 보류
- 이유:

### 사용자에게 필요한 결정
1. ...
2. ...
```

`Codex 권고`는 근거 없이 “승인”으로 쓰지 않는다. 아래 조건을 만족할 때만 승인 권고를 낼 수 있다.

- 필수 산출물이 존재한다.
- JSON/Markdown/zip 등 형식 검증이 통과했다.
- reviewer 결과가 `pass`이거나, `revise` 항목이 제출 리스크를 만들지 않는다고 설명했다.
- hard exclusion, 개인정보, 비밀정보, 매출 과장 이슈가 없다.
- 사용자가 판단해야 하는 비즈니스 선택지가 명확하다.
- 수정이 발생한 경우 수정 후 재검증 결과가 남아 있다.

## Phase별 Codex 사전 검토

### Phase 0. 문제와 공개 근거 고정

Codex가 먼저 검토할 것:

- 공개 근거 URL이 실제로 문제 정의와 연결되는지 확인
- `PLUGIN_PLAN.md`, README 초안, 최신 검증 로그의 문제 문장이 충돌하지 않는지 확인
- “메디테라피가 실제로 겪는 문제”와 “공개 자료로 추론한 문제”를 구분했는지 확인
- 매출 효과를 검증 전 사실처럼 쓰지 않았는지 확인

사용자에게 전달할 것:

- 최종 문제 정의 1문장
- 사용할 공개 근거 URL 목록
- 말할 수 있는 범위와 말하면 안 되는 범위
- Codex 권고: 문제 정의 유지/축소/수정

승인 요청 전 차단 조건:

- 공개 근거가 3개 미만
- 문제 정의가 문서마다 다름
- 내부 자료 없이 매출 성과를 단정

### Phase 1. 제품 온톨로지 고정

Codex가 먼저 검토할 것:

- MVP 제품 9개가 JSON에 존재하는지 확인
- 제품별 피부 고민, 콘텐츠 적합성, 리스크 태그가 빠지지 않았는지 확인
- 레티날/AHA-BHA/눈가/텐션/민감피부 리스크가 감점 또는 차단 규칙에 들어갔는지 확인
- 성별이 1차 추천 기준이 아닌지 확인
- 신제품이 들어왔을 때 매핑 가능한 필드가 있는지 확인

사용자에게 전달할 것:

- MVP 제품 9개 목록
- 제품별 핵심 추천 대상
- 제품별 주요 리스크
- 변경이 필요한 제품 후보

승인 요청 전 차단 조건:

- 제품 리스크 태그 누락
- 의료적 효능 단정 표현
- 특정 성별 기반 추천 규칙

### Phase 2. 인플루언서 후보 수집

Codex가 먼저 검토할 것:

- 후보 수, 세그먼트별 수, 콘텐츠 관찰치 수를 집계
- 후보별 필수 필드 누락률 계산
- 후보당 콘텐츠 10개 또는 부족 사유 존재 확인
- 피부 고민이 최소 2개 관찰 근거에 기반하는지 샘플 확인
- 댓글 원문 저장 없이 테마만 저장했는지 확인
- 협찬/필터/의료 주장/과도한 before-after 리스크가 기록되었는지 확인
- 후보 데이터의 `source_confidence` 분포 확인

사용자에게 전달할 것:

- 후보 수집 현황 표
- 세그먼트별 충족률
- 후보 10명 샘플 요약
- 제외/보류 후보와 사유
- 추가 수집이 필요한 세그먼트

승인 요청 전 차단 조건:

- URL 없는 후보가 포함됨
- 댓글 원문 또는 민감 개인정보 저장
- 후보 30명 중 필수 필드 충족 후보가 24명 미만
- 특정 세그먼트가 목표의 80% 미만인데 보완 계획 없음

### Phase 3. 인플루언서 파라미터 정규화

Codex가 먼저 검토할 것:

- primary/secondary 피부 고민이 근거 수 기준을 따르는지 확인
- 콘텐츠 도메인 primary가 최근 10개 중 3개 이상 기준을 따르는지 확인
- `unknown`을 임의 추정으로 채우지 않았는지 확인
- hard exclusion, soft penalty, review note 분류가 맞는지 확인
- 프로필 필드가 원천 URL 또는 관찰 데이터로 추적 가능한지 확인

사용자에게 전달할 것:

- 정규화 프로필 5명 샘플
- `unknown` 비율
- hard exclusion 후보 목록
- 정규화에서 애매했던 판단

승인 요청 전 차단 조건:

- 추측으로 피부 타입/피부 고민 확정
- hard exclusion이 soft penalty로 약화됨
- 추천에 필요한 핵심 필드가 추적 불가

### Phase 4. 제품-인플루언서 매칭

Codex가 먼저 검토할 것:

- hard exclusion이 점수 계산보다 먼저 적용되었는지 확인
- 결과 표시 우선순위가 `ready_for_matching`, `review_required_before_matching`, `needs_more_data` 순서인지 확인
- `needs_more_data` 후보가 상단 추천처럼 보이지 않는지 확인
- 추천 점수 trace와 자연어 사유가 일치하는지 확인
- 추천 상위 3개 제품과 `no_seed` 옵션이 있는지 확인
- 점수 높은 후보라도 리스크가 크면 보류되는지 확인
- 제품별 추천 쏠림이 있는지 확인
- 대조군 3명 선정 기준이 남는지 확인

사용자에게 전달할 것:

- 시딩 추천 6명 요약
- 대조군 3명 요약
- 후보별 추천 제품과 핵심 가설
- 리스크 때문에 보류한 후보
- 제품별 추천 분포

승인 요청 전 차단 조건:

- hard exclusion 무시
- 단순 팔로워 수 기반 추천
- 점수와 설명 충돌
- `no_seed`를 낼 수 없는 구조

### Phase 5. 시딩 수행 브리프

Codex가 먼저 검토할 것:

- 후보별 브리프에 제품, 가설, 콘텐츠 각도, KPI, 리스크가 모두 있는지 확인
- 금지 표현과 주의 문구가 제품 리스크와 맞는지 확인
- 광고/협찬 고지 필요성이 빠지지 않았는지 확인
- KPI가 사후 결과 수집 가능하게 정의되었는지 확인
- 실험군/대조군 구분이 유지되는지 확인

사용자에게 전달할 것:

- 후보별 시딩 브리프 요약
- 가장 리스크가 큰 브리프 2-3개
- 수정이 필요한 문구
- Codex가 권하는 최종 실행안

승인 요청 전 차단 조건:

- 의료/효능/영구 개선 단정
- KPI 없음
- 제품 사용 주의 누락
- 시딩 기록과 결과 수집이 연결되지 않음

### Phase 6. 결과 수집 및 성과 해석

Codex가 먼저 검토할 것:

- 공개 KPI와 내부 KPI가 분리되었는지 확인
- 게시 후 24시간, 72시간, 7일, 14일 지표 구조가 있는지 확인
- 사전에 정한 KPI가 사후에 바뀌지 않았는지 확인
- 댓글 원문 없이 의도 테마만 집계했는지 확인
- 성과가 낮은 케이스도 실패 원인으로 기록했는지 확인

사용자에게 전달할 것:

- 제출에 사용할 정상 예시
- 제출에 사용할 예외/차단 예시
- 공개 데이터로 말할 수 있는 성과 범위
- 내부 데이터가 있어야만 말할 수 있는 범위

승인 요청 전 차단 조건:

- 공개 조회수만으로 매출 성공 주장
- 데이터 출처 구분 없음
- 실패 사례 삭제
- 사후 KPI 변경

### Phase 6A. 신제품 입력 기반 기존 DB 랭킹

Codex가 먼저 검토할 것:

- 신제품 입력 JSON이 필수 필드를 모두 갖췄는지 확인
- 신제품 태그가 기존 제품 온톨로지에 매핑되는지 확인
- hard exclusion이 랭킹보다 먼저 적용되는지 확인
- 기존 인플루언서 DB 전체가 대상인지 확인
- 표시 우선순위가 `ready_for_matching`, `review_required_before_matching`, `needs_more_data` 순서인지 확인
- 점수 trace와 추천 사유가 일치하는지 확인
- 추가 리서치 필요 여부가 별도 필드로 남는지 확인

사용자에게 전달할 것:

- 신제품 입력 요약
- 기존 DB 기반 상위 후보 랭킹
- `no_seed` 또는 `review_required` 후보와 사유
- 추가 리서치 필요 여부와 근거
- Codex 권고: 기존 DB 랭킹으로 충분/리서치 갭 판단 필요

승인 요청 전 차단 조건:

- 신제품 필수 필드 누락
- 제품 리스크 태그 누락
- hard exclusion 후보가 상위 추천으로 표시됨
- `needs_more_data` 후보가 고신뢰 추천처럼 표시됨
- 팔로워 수만으로 랭킹됨

### Phase 6B. 신제품 리서치 갭 판단

Codex가 먼저 검토할 것:

- ready 후보 수, 핵심 세그먼트 커버리지, 데이터 freshness를 계산했는지 확인
- 추가 리서치 트리거가 정량 조건과 연결되는지 확인
- 검색 쿼리가 신제품 피부 고민/콘텐츠/시장 태그와 연결되는지 확인
- 기존 DB 랭킹을 보존한 상태에서 리서치 계획만 제안하는지 확인

사용자에게 전달할 것:

- 추가 리서치 필요/불필요 판단
- 부족한 후보 세그먼트
- 제안 검색어
- 예상 수집 규모와 중단 조건
- 기존 DB 랭킹을 유지할지, 리서치를 실행할지 선택지

승인 요청 전 차단 조건:

- 리서치 필요 판단 근거 없음
- 신제품과 무관한 검색어 제안
- 공개 데이터 접근 불안정성을 리스크로 표시하지 않음
- 기존 DB 결과를 삭제하거나 덮어씀

### Phase 6C. 신제품 추가 리서치 및 재랭킹

Codex가 먼저 검토할 것:

- 신규 후보 출처 URL과 콘텐츠 관찰치가 추적 가능한지 확인
- 댓글 원문과 민감 개인정보가 저장되지 않았는지 확인
- 기존 후보와 신규 후보 중복 제거가 되었는지 확인
- 신규 후보가 Phase 3 정규화 규칙을 통과했는지 확인
- 리프레시 전후 랭킹 차이와 변경 사유가 남는지 확인

사용자에게 전달할 것:

- 신규 후보 수집 요약
- merge 전후 후보 수
- 리프레시 전후 상위 랭킹 diff
- 신규 후보 중 `ready`, `review_required`, `needs_more_data` 분포
- Codex 권고: 재랭킹 채택/기존 DB 랭킹 유지/추가 보류

승인 요청 전 차단 조건:

- 신규 후보 URL 추적 불가
- 댓글 원문 또는 민감 개인정보 저장
- 신규 후보 데이터 부족인데 고신뢰 추천으로 표시
- 리프레시 결과가 왜 바뀌었는지 설명 없음
- 내부 데이터 없이 매출/ROAS/주문 증가 주장

### Phase 7. 5.4 Mini 리뷰어 검수

Codex가 먼저 검토할 것:

- reviewer report가 실제 산출되었는지 확인
- `fail`, `revise`, `pass` 항목을 분리
- `fail`은 Phase 3/4/5 중 어디로 되돌릴지 지정
- `revise` 중 제출 전 반드시 고칠 항목과 한계로 남길 항목을 구분
- README, JSON, 로그가 서로 충돌하지 않는지 확인

사용자에게 전달할 것:

- reviewer 요약
- 반드시 고쳐야 할 항목
- 시간상 한계로 남겨도 되는 항목
- Codex의 처리 권고

승인 요청 전 차단 조건:

- reviewer report 없음
- `fail`이 있는데 다음 phase 진행
- 위험 케이스 테스트 없음
- 제출 답변이 구현보다 과장됨

### Phase 8. 반복 학습

Codex가 먼저 검토할 것:

- 결과 기반 룰 변경과 가설을 구분했는지 확인
- 단일 사례를 전체 룰로 과잉 일반화하지 않았는지 확인
- 다음 실험 질문이 구체적인지 확인
- 실패 사례가 반복 루프에 남아 있는지 확인

사용자에게 전달할 것:

- 실제 룰에 반영할 후보
- `hypothesis_only`로 남길 후보
- 다음 실험 질문
- 제출 답변에 넣을 반복 루프 요약

승인 요청 전 차단 조건:

- 결과가 없는데 학습 완료로 표현
- 실패 원인 없이 룰 변경
- 다음 실험 질문 없음

### Phase 9. 제출 패키징

Codex가 먼저 검토할 것:

- `submission.zip` 필수 구조 확인
- 압축 해제 후 파일 존재 확인
- README와 로그 충돌 확인
- JSON 문법 검증
- 로그 내 비밀정보/민감정보 검색
- 제출물이 구현하지 않은 기능을 구현했다고 말하지 않는지 확인

사용자에게 전달할 것:

- 최종 파일 트리
- 검증 명령 결과 요약
- 최종 답변 요약
- 남은 한계
- 최종 제출 승인 질문

승인 요청 전 차단 조건:

- 필수 파일 누락
- zip 압축 해제 검증 실패
- 비밀정보 발견
- 답변과 구현 범위 불일치

## 사용자 승인 요청 전 체크리스트

Codex는 승인 요청 전 아래 체크리스트를 채운다.

```markdown
- [ ] 필수 산출물 존재 확인
- [ ] 형식 검증 완료
- [ ] 내용 정합성 검토 완료
- [ ] 리스크/과장/누락 검토 완료
- [ ] reviewer 결과 확인
- [ ] 사용자 판단 포인트 1-3개로 압축
- [ ] Codex 권고와 이유 작성
- [ ] 다음 phase 진입 조건 명시
```

이 체크리스트가 비어 있거나 실패 항목이 설명되지 않은 상태에서는 사용자에게 승인을 요청하지 않는다.
