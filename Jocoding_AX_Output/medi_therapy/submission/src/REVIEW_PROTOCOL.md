# Reviewer Protocol and Human Checkpoints

이 문서는 phase별로 `5.4 mini reviewer`가 검수해야 하는 항목과, 사용자가 직접 검토해야 하는 지점을 고정한다. 목적은 자동 리뷰어에게 맡길 수 있는 정합성 검수와 사람이 판단해야 하는 전략/윤리/제출 판단을 분리하는 것이다.

사용자 승인 요청 전에 Codex가 먼저 수행해야 하는 자체 검토 절차는 `submission/PRE_APPROVAL_PROTOCOL.md`에 고정한다. 사용자에게 넘기는 승인 요청은 항상 사전 검토 결과, 남은 리스크, Codex 권고, 사용자 결정 질문을 포함해야 한다.

자체검토에서 문제가 발견된 뒤의 수정/재검증 루프는 `submission/SELF_VALIDATION_FIX_LOOP.md`에 고정한다. reviewer `fail` 또는 blocker 이슈가 남아 있으면 사용자 승인 요청 전 먼저 수정 루프를 수행한다.

## 공통 원칙

리뷰어 모델이 항상 확인할 것:

- 입력 데이터와 산출물이 같은 phase의 목적과 맞는가
- 근거 없는 단정이 없는가
- 내부 매출 데이터 없이 매출/ROAS/전환 효과를 확정하지 않았는가
- 성별, 외모, 민감 정보가 제품 추천의 1차 기준으로 쓰이지 않았는가
- 피부 고민, 콘텐츠 형식, 팔로워 니즈, 제품 리스크가 분리되어 설명되는가
- hard exclusion이 recommendation 단계에서 무시되지 않았는가
- 누락 데이터가 `unknown`, `needs_more_data`, `insufficient_public_data`로 남는가
- 추천 사유와 점수, 콘텐츠 브리프, KPI가 서로 충돌하지 않는가
- 로그와 산출물에 API 키, 토큰, 비밀번호, 비공개 개인정보가 없는가

사용자가 직접 확인할 것:

- 이 phase의 산출물이 대회 제출 전략에 맞는가
- 메디테라피 문제 정의와 어긋나는 방향으로 과확장되지 않았는가
- 공개 자료 근거로 말할 수 있는 범위를 넘지 않았는가
- 후보 선정과 제품 추천이 납득 가능한 비즈니스 판단인가
- 최종 답변 문장이 심사위원에게 명확하고 방어 가능한가

## Phase 0. 문제와 공개 근거 고정

리뷰어 모델 검수:

- 문제 정의가 “매출로 이어지는 인플루언서 시딩 시스템 설계”에서 벗어나지 않는가
- 공개 근거 URL이 문제 정의를 뒷받침하는가
- 메디테라피의 니즈가 `글로벌`, `TikTok/인플루언서`, `제품별 메시지`, `데이터 분석`, `반복 루프`로 분해되어 있는가
- 내부 자료가 없는 상태에서 내부 성과를 단정하지 않았는가
- README, `PLUGIN_PLAN.md`, 최신 검증 로그의 문제 설명이 서로 충돌하지 않는가

리뷰어 실패 조건:

- 공개 근거 없이 “메디테라피가 반드시 이 문제를 겪고 있다”고 단정
- 매출 기여를 검증 전 사실처럼 표현
- 문제 범위가 CRM, 광고 자동화, 상품기획 등으로 흐려짐

사용자 검토 필요:

- 이 문제 정의로 끝까지 밀고 갈지 승인
- 공개 근거 중 제출 답변에 반드시 넣을 URL 선택
- 문제 범위가 너무 넓거나 약하지 않은지 판단

사용자 검토 타이밍:

- Phase 0 종료 직후
- README 문제 정의와 공개 근거 확정 전

## Phase 1. 제품 온톨로지 고정

리뷰어 모델 검수:

- MVP 제품 9개가 실제 제품군 분포를 대표하는가
- 각 제품에 `best_for_concerns`, `skin_type_fit`, `skin_type_caution`, `content_fit`, `risk_flags`가 있는가
- 레티날, AHA/BHA, 눈가, 텐션, 민감피부 관련 리스크가 누락되지 않았는가
- 제품 설명이 의료적 치료 단정으로 바뀌지 않았는가
- 제품 추천 기준에서 성별이 1차 기준으로 쓰이지 않았는가
- 신제품 입력 시 기존 태그 체계에 매핑 가능한가

리뷰어 실패 조건:

- 위험 성분/사용 부위 리스크가 없는 제품처럼 처리
- 효능을 치료, 완치, 영구 개선으로 표현
- 제품군별 KPI가 모두 동일해 제품별 검증이 불가능함

사용자 검토 필요:

- MVP 제품 9개가 제출 시연에 적절한지 승인
- 메디테라피 주력 제품으로 더 강조할 제품이 있는지 판단
- 리스크를 보수적으로 잡는 수준이 적절한지 확인

사용자 검토 타이밍:

- 제품 JSON 수정 완료 후
- 인플루언서 후보 수집 시작 전

## Phase 2. 인플루언서 후보 수집 Harness

리뷰어 모델 검수:

- 후보 30명 수집 목표와 세그먼트별 목표가 지켜졌는가
- 각 후보의 필수 필드가 채워졌는가
- 후보당 최근 콘텐츠 10개 또는 부족 사유가 기록되었는가
- 최근 30일 스킨케어 콘텐츠 3개 이상 조건이 확인되었는가
- 피부 고민이 단일 게시물이나 추측만으로 primary가 되지 않았는가
- 댓글 원문을 저장하지 않고 의도 테마만 저장했는가
- 협찬, 필터, 의료 주장, 과도한 before/after 리스크가 기록되었는가
- 후보 URL과 콘텐츠 URL이 추적 가능한가
- `source_confidence`가 후보별로 부여되었는가

리뷰어 실패 조건:

- 후보 출처 URL이 없거나 추적 불가
- 후보 데이터 부족 상태인데 추천 대상으로 통과
- 댓글 원문이나 민감 개인정보 저장
- 세그먼트가 한쪽으로 몰려 MVP 실험 설계가 무너짐

사용자 검토 필요:

- 후보 세그먼트 구성이 비즈니스적으로 납득되는지 확인
- 실제 제출 시 후보 실명을 얼마나 노출할지 판단
- 공개 후보를 사용하는 방식이 대회 제출 윤리와 맞는지 확인
- 후보 수가 부족할 때 범위를 확장할지, MVP를 축소할지 결정

사용자 검토 타이밍:

- 후보 10명 수집 후 1차 샘플 리뷰
- 후보 30명 수집 완료 후 최종 수집 승인
- `insufficient_public_data` 후보가 6명 이상일 때 즉시

## Phase 3. 인플루언서 파라미터 추출 및 정규화 Harness

리뷰어 모델 검수:

- `skin_concerns` primary/secondary 분류가 관찰 근거 수와 맞는가
- `content_domains` primary 분류가 최근 10개 중 3개 이상 기준을 지키는가
- `audience_intent_themes`가 댓글 원문이 아니라 테마/카운트로만 남는가
- `commercial_signals`와 `risk_signals`가 별도 필드로 분리되는가
- `unknown` 값을 모델이 임의로 추정해 채우지 않았는가
- hard exclusion, soft penalty, review note 구분이 명확한가
- 추천에 쓰일 필드가 수집 원천으로 역추적 가능한가

리뷰어 실패 조건:

- 시각적 추측만으로 피부 타입을 확정
- 1회 언급된 고민을 primary concern으로 승격
- hard exclusion을 soft risk로 낮춤
- 부족한 데이터를 그럴듯한 문장으로 보완

사용자 검토 필요:

- 정규화 기준이 너무 엄격하거나 느슨하지 않은지 확인
- 후보 프로필이 실제 마케터가 읽어도 납득되는지 샘플 검토
- `unknown`이 너무 많을 경우 추가 수집 또는 후보 제외 결정

사용자 검토 타이밍:

- 정규화된 후보 5명 샘플 생성 후
- 전체 `influencer_profiles.jsonl` 생성 후
- hard exclusion 후보가 예상보다 많을 때

## Phase 4. 제품-인플루언서 매칭 Harness

리뷰어 모델 검수:

- hard exclusion이 점수 계산보다 먼저 적용되었는가
- 결과 표시가 `ready_for_matching`, `review_required_before_matching`, `needs_more_data` 순서로 정렬되는가
- `needs_more_data` 후보가 고신뢰 추천처럼 상단에 노출되지 않는가
- 점수 항목이 self/audience/content/market/risk로 분리되는가
- 높은 총점이 리스크를 덮어버리지 않는가
- 추천 상위 3개 제품과 `no_seed` 가능성이 함께 고려되는가
- 추천 문장과 점수 trace가 서로 일치하는가
- 제품 리스크와 후보 리스크가 충돌할 때 보류 또는 대체 제품이 나오는가
- 대조군 3명 선정 기준이 남아 있는가

리뷰어 실패 조건:

- 임신/수유/강한 민감/상처 신호가 있는데 레티날 또는 산 제품 추천
- 후보 콘텐츠와 맞지 않는 제품을 높은 점수로 추천
- 단순 팔로워 수만으로 추천
- 점수는 낮은데 자연어 설명은 강력 추천처럼 작성

사용자 검토 필요:

- 상위 추천 6명과 대조군 3명이 실제 시딩 실험으로 납득되는지 판단
- 제품별 추천 분포가 한 제품으로 쏠리지 않는지 확인
- 사람이 보기에 창발적 콘텐츠 각도가 있는 후보인지 판단

사용자 검토 타이밍:

- 첫 매칭 결과 5건 생성 후
- 최종 시딩 추천 6명/대조군 3명 확정 전

## Phase 5. 시딩 수행 Harness

리뷰어 모델 검수:

- 시딩 브리프가 후보, 제품, 콘텐츠 각도, KPI, 리스크를 모두 포함하는가
- 콘텐츠 문구가 의료/효능/영구 개선을 단정하지 않는가
- 광고/협찬 고지 필요성이 빠지지 않았는가
- 후보가 실제로 만들 수 있는 콘텐츠 형식인가
- KPI가 제품/콘텐츠 가설과 연결되는가
- 금지 표현과 주의 표현이 제품 리스크와 맞는가
- 실험군/대조군 구분이 유지되는가

리뷰어 실패 조건:

- 브리프가 “좋은 리뷰를 만들어라” 수준으로 모호함
- KPI가 사후 성과 측정과 연결되지 않음
- 위험 제품인데 사용법/주의 문구 없음
- 매출 목표를 크리에이터에게 단정적으로 요구하는 표현

사용자 검토 필요:

- 실제 마케터가 사용할 수 있는 브리프인지 확인
- 후보별 콘텐츠 각도가 브랜드 톤과 맞는지 판단
- 시딩 제품 수량과 대조군 설계가 현실적인지 승인

사용자 검토 타이밍:

- 후보별 브리프 초안 생성 후
- 최종 시딩 실행안 확정 전

## Phase 6. 결과 수집 및 성과 테이블 Harness

리뷰어 모델 검수:

- 게시 여부, 24시간, 72시간, 7일, 14일 관찰값이 분리되는가
- 공개 KPI와 내부 KPI가 섞이지 않는가
- 매출 데이터가 없는데 매출 성공/실패로 단정하지 않는가
- 댓글 원문이 저장되지 않고 의도 테마로만 집계되는가
- 실패 원인이 후보/제품/콘텐츠/시장/리스크/데이터 부족으로 태그화되는가
- 사전에 정한 KPI가 사후에 유리하게 바뀌지 않았는가

리뷰어 실패 조건:

- 공개 조회수만으로 매출 성공 주장
- 클릭/쿠폰/주문 데이터 출처가 불명확
- 실패 케이스를 누락하거나 삭제
- 결과가 낮은 후보를 근거 없이 “부적합”으로 영구 분류

사용자 검토 필요:

- 공개 KPI만으로 제출에서 어디까지 주장할지 결정
- 실패 원인 해석이 비즈니스적으로 맞는지 판단
- 내부 데이터가 없다는 한계를 어떻게 설명할지 확정

사용자 검토 타이밍:

- 첫 결과 테이블 생성 후
- 제출용 검증 예시 선정 전

## Phase 6A. 신제품 입력 기반 기존 DB 랭킹 Harness

리뷰어 모델 검수:

- 신제품 입력값이 기존 제품 온톨로지 필드로 정규화되는가
- 기존 인플루언서 DB 전체를 대상으로 랭킹했는가
- hard exclusion과 제품 리스크 충돌이 점수보다 먼저 적용되는가
- 점수 항목이 self/audience/content/market/risk로 분리되는가
- `ready_for_matching` -> `review_required_before_matching` -> `needs_more_data` 표시 우선순위를 지키는가
- `needs_more_data` 후보가 고신뢰 상위 추천처럼 보이지 않는가
- 추천 사유가 단순 팔로워 수가 아니라 피부 고민, 콘텐츠 형식, 시장, 리스크 근거를 포함하는가
- 추가 리서치 필요 여부가 정량 조건으로 남는가

리뷰어 실패 조건:

- 신제품 리스크 태그 없이 랭킹
- hard exclusion 후보를 상위 시딩 후보로 추천
- 기존 DB 일부만 임의로 골라 랭킹
- 점수와 자연어 설명 충돌
- 추가 리서치가 필요한데 충분하다고 단정

사용자 검토 필요:

- 신제품 입력 필드가 실제 제품 맥락을 충분히 반영하는지 확인
- 기존 DB 기반 상위 후보가 비즈니스적으로 납득되는지 판단
- 추가 리서치 없이 바로 브리프 단계로 갈지 결정

사용자 검토 타이밍:

- 신제품 DB 랭킹 1차 결과 생성 후
- 추가 리서치 필요 여부 결정 전

## Phase 6B. 신제품 리서치 갭 판단 Harness

리뷰어 모델 검수:

- ready 후보 수, 세그먼트 커버리지, 데이터 freshness가 계산되는가
- 추가 리서치 트리거가 사전에 정한 조건과 일치하는가
- 검색 쿼리가 제품 태그와 연결되는가
- 리서치 범위가 부족 세그먼트로 제한되는가
- 기존 DB 랭킹 결과가 삭제되지 않고 보존되는가

리뷰어 실패 조건:

- 정량 기준 없이 “리서치 필요” 또는 “리서치 불필요”로 판단
- 신제품과 무관한 광범위 검색어 생성
- 공개 데이터 접근 리스크를 누락
- 기존 DB 랭킹을 덮어써 비교 불가능하게 만듦

사용자 검토 필요:

- 추가 리서치를 실행할지, 기존 DB 랭킹으로 제출할지 판단
- 리서치 범위와 수집 규모가 해커톤 일정에 맞는지 확인
- 후보 실명/URL 사용 방식이 제출 윤리에 맞는지 확인

사용자 검토 타이밍:

- 리서치 갭 리포트 생성 후
- 공개 리서치 실행 전

## Phase 6C. 신제품 추가 리서치 및 재랭킹 Harness

리뷰어 모델 검수:

- 신규 후보 출처 URL과 콘텐츠 관찰치가 추적 가능한가
- 댓글 원문과 민감 개인정보가 저장되지 않았는가
- 신규 후보가 기존 후보와 중복 제거되었는가
- 신규 후보 정규화가 Phase 3 기준을 지키는가
- 리프레시 전후 랭킹 diff가 설명되는가
- 데이터 부족 신규 후보가 고신뢰 추천으로 승격되지 않는가

리뷰어 실패 조건:

- 신규 후보 출처가 불명확함
- 댓글 원문 또는 민감 개인정보 저장
- low-confidence 신규 후보를 ready 추천으로 표시
- 리프레시 후 랭킹 변화 근거 없음
- 공개 KPI나 후보 발견만으로 매출 효과를 단정

사용자 검토 필요:

- 신규 후보를 DB에 merge할지 승인
- 리프레시 랭킹을 최종 추천으로 채택할지 판단
- 공개 리서치 결과가 기존 DB보다 실제로 나은지 검토

사용자 검토 타이밍:

- 신규 후보 정규화 후
- 리프레시 전후 랭킹 diff 생성 후

## Phase 7. 5.4 Mini 리뷰어 검수 Harness

리뷰어 모델 검수:

- Phase 0-6 산출물이 서로 충돌하지 않는가
- 코드 스키마와 문서의 출력 계약이 같은가
- 추천 알고리즘이 문서에 쓴 가중치와 일치하는가
- hard exclusion 테스트가 실제로 실패 조건을 잡는가
- `no_seed`, `needs_more_data`, `inconclusive`가 정상 동작하는가
- 답변 초안이 구현 범위를 과장하지 않는가
- README, 데이터 JSON, 로그가 같은 이야기를 하는가

리뷰어 실패 조건:

- 문서에는 검수한다고 했지만 산출물에 reviewer report가 없음
- 추천 결과와 코드/스키마가 맞지 않음
- 위험 케이스 테스트가 없음
- 제출 답변이 실제 구현보다 크게 말함

사용자 검토 필요:

- reviewer의 `revise` 또는 `fail` 항목 중 어떤 것을 반드시 고칠지 결정
- 제출 시간 안에 고칠 항목과 명시적 한계로 남길 항목 구분
- 최종 제출 문구가 과장 없이 설득력 있는지 확인

사용자 검토 타이밍:

- reviewer report 최초 생성 후
- 모든 `fail` 수정 후 재검수 결과 확인 시

## 사용자 필수 검토 요약

사용자는 아래 지점에서 한 번씩 판단해야 한다.

1. Phase 0 종료: 문제 정의와 공개 근거 승인
2. Phase 1 종료: MVP 제품 9개와 리스크 기준 승인
3. Phase 2 중간: 후보 10명 샘플 품질 확인
4. Phase 2 종료: 후보 30명 수집 결과 승인
5. Phase 3 중간: 정규화 프로필 5명 샘플 확인
6. Phase 4 종료: 시딩 추천 6명과 대조군 3명 승인
7. Phase 5 종료: 후보별 시딩 브리프 승인
8. Phase 6 종료: 검증 예시와 성과 해석 범위 승인
9. Phase 7 종료: reviewer `fail`/`revise` 처리 결정
10. Phase 9 직전: 최종 답변과 제출 ZIP 승인

단, 사용자가 검토하기 전에 Codex는 `submission/PRE_APPROVAL_PROTOCOL.md`의 사전 검토 체크리스트를 먼저 완료해야 한다. 사용자는 원자료 전체를 다시 검토하는 것이 아니라, Codex가 압축한 승인 패키지를 기준으로 승인/수정/보류를 판단한다.

## Reviewer 출력 포맷

각 phase 리뷰어는 아래 JSON 형식으로 결과를 남긴다.

```json
{
  "phase_id": "phase_0_problem_evidence_lock",
  "review_status": "pass | revise | fail",
  "score": 0,
  "checked_items": [],
  "findings": [],
  "required_fixes": [],
  "human_review_required": true,
  "human_review_questions": [],
  "can_proceed_to_next_phase": false
}
```

`can_proceed_to_next_phase`는 `review_status`가 `pass`이고 사용자 필수 검토가 끝난 경우에만 `true`로 둔다.

단, 수정이 발생한 phase는 수정 후 동일 검증과 reviewer 재검수를 다시 수행해야 한다. 재검증 기록 없이 `can_proceed_to_next_phase`를 `true`로 둘 수 없다.
